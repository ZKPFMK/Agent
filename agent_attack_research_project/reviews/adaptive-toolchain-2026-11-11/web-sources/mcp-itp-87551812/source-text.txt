Abstract
To standardize interactions between LLM-based agents and their environments, the Model Context Protocol (MCP) was proposed and has since been widely adopted. However, integrating external tools expands the attack surface, exposing agents to tool poisoning attacks. In such attacks, malicious instructions embedded in tool metadata are injected into the agent context during MCP registration phase, thereby manipulating agent behavior. Prior work primarily focuses on explicit tool poisoning or relied on manually crafted poisoned tools. In contrast, we focus on a particularly stealthy variant: implicit tool poisoning, where the poisoned tool itself remains uninvoked. Instead, the instructions embedded in the tool metadata induce the agent to invoke a legitimate but high-privilege tool to perform malicious operations. We propose MCP-ITP, the first automated and adaptive framework for implicit tool poisoning within the MCP ecosystem. MCP-ITP formulates poisoned tool generation as a black-box optimization problem and employs an iterative optimization strategy that leverages feedback from both an evaluation LLM and a detection LLM to maximize Attack Success Rate (ASR) while evading current detection mechanisms. Experimental results on the MCPTox dataset across 12 LLM agents demonstrate that MCP-ITP consistently outperforms the manually crafted baseline, achieving up to 84.2% ASR while suppressing the Malicious Tool Detection Rate (MDR) to as low as 0.3%.
1 Introduction
Agents based on large language models (LLMs) are rapidly evolving into autonomous entities capable of addressing complex tasks by invoking external tools [1, 2]. To standardize the interaction between agents and external environments, the Model Context Protocol (MCP) has been proposed and widely adopted [3, 4]. By providing a unified interface for tool access, MCP lowers the barrier for third-party tool integration, thereby facilitating the development of the tool ecosystem.
Figure 1: The workflow of MCP and MCP-ITP. During MCP registration, malicious instructions embedded in the poisoned tool description (e.g., qubit) are injected into the agent’s context. As a result, the user query to read a file can be hijacked: the agent ignores the request and instead calls w​r​i​t​e​_​f​i​l​ewrite\_file to modify sensitive assets (e.g., SSH private key), creating a severe security risk.
While integrating external tools extends agent capabilities, it also expands the system’s attack surface [5, 6]. Since MCP allows third-party developers to publish tools on public marketplaces and lacks a unified security vetting mechanism [7, 8], it lowers the barrier for adversaries to deploy tools containing malicious instructions through malicious servers. This threat is known as the Tool Poisoning Attack, where malicious instructions are embedded within tool metadata (e.g., function descriptions and parameter specifications) [9, 10]. During the MCP registration phase, the poisoned tool metadata is loaded into the agent’s context, thereby stealthily manipulating the agent’s behavior.
Existing research on tool poisoning primarily focuses on explicit tool poisoning, where adversaries induce agents to directly invoke poisoned tools to execute malicious instructions or return misleading outputs [11, 12]. However, such attacks typically require the agent to explicitly execute the suspicious tool, rendering them susceptible to detection by monitoring mechanisms [13, 14]. In contrast, we focus on a stealthier and more challenging threat variant: Implicit Tool Poisoning (ITP). In this setting, the poisoned tool TKT_{K} is never invoked directly. Instead, by meticulously crafting the descriptions of TKT_{K} to exploit vulnerabilities in the contextual reasoning of LLM, adversaries mislead the agent into invoking an existing, legitimate, but high-privilege target tool TGT_{G} to perform malicious operations. This decoupling of the attack trigger (TKT_{K}) from the eventual tool invocation (TGT_{G}) ensures that the attack remains highly stealthy and difficult to detect through execution monitoring mechanisms, posing a severe threat to the security of the MCP ecosystem.
In this work, we propose MCP-ITP, the first automated and adaptive framework for implicit tool poisoning within the MCP ecosystem. The construction of implicitly poisoned tools is formulated as a black-box optimization problem, aiming to simultaneously maximize the Attack Success Rate (ASR) and minimize the likelihood of being detected. Specifically, MCP-ITP employs an iterative optimization strategy incorporating three core components: an attacker LLM LAL_{A}, a detector LLM LDL_{D}, and an evaluator LLM LEL_{E}. LAL_{A} refines and generates new poisoned description candidates based on feedback and candidates from previous iteration. LDL_{D} simulates detection mechanisms to provide feedback on evasiveness, while LEL_{E} evaluates attack efficacy on a shadow query set to provide feedback on effectiveness. Through this adversarial feedback iteration, MCP-ITP can craft implicitly poisoned tools that effectively hijack agent tool invocations while evading existing malicious tool detection mechanisms.
To validate our method, we conducted comprehensive experiments on the MCPTox dataset, which is built on 45 real-world MCP servers and 353 real tools [15]. We evaluated the effectiveness of MCP-ITP across 12 prominent LLM agents. Experimental results indicate that MCP-ITP significantly outperforms the manually crafted baseline. For instance, on GPT-3.5-turbo, the Attack Success Rate (ASR) increased from 48.2% to 84.2%, while the Malicious tool Detection Rate (MDR) was substantially reduced under various settings (reaching as low as 0.3%). These findings reveal the inherent vulnerabilities of the current MCP ecosystem to implicit contextual manipulation and underscore the urgent need for targeted defense mechanisms.
Our contributions are summarized as follows:
•
We systematically investigate the threat of implicit tool poisoning in the MCP ecosystem, revealing how adversaries redirect agent behavior through contextual manipulation without the poisoned tool ever being invoked.
•
We propose MCP-ITP, a novel automated black-box optimization framework that leverages adversarial feedback mechanism to generate highly effective and stealthy poisoned tool descriptions.
•
We conduct a comprehensive evaluation across different LLM agents, demonstrating the cross-model efficacy of MCP-ITP and its evasiveness against existing malicious tool detection mechanisms.
2 Background and Related Work
2.1 Attacks on LLMs and Agents
Attacks on LLMs mainly focus on prompt injection and jailbreak attacks [16, 17, 18, 19]. Jailbreak attacks operate directly through user inputs and primarily aim to bypass LLM safety guardrails to elicit harmful outputs [20, 21]. In contrast, prompt injection attacks embed malicious instructions into external data sources and focus on steering the LLM to carry out specific actions [21, 22].
Attacks on agents further exploit the integration of external components [23]. Examples include hijacking selection processes or corrupting RAG databases to manipulate model outputs [24, 25, 26]. Further studies have extended indirect injections to multi-modal and multi-agent settings [27, 28].
2.2 Model Context Protocol
To standardize interactions between AI agents and external tools, Anthropic introduced the Model Context Protocol (MCP) in 2024 [3]. MCP provides a general-purpose framework that enables AI agents to dynamically discover, select, and orchestrate external tools based on the user’s task context. In the MCP architecture, the MCP servers expose their capabilities by providing tool metadata, including tool names, natural language descriptions, and parameters. The MCP Host connects to one or more MCP servers to fetch metadata about available tools. The tool metadata is then loaded into the LLM context, typically as part of the system prompt. When a user submits a query through the host, the agent selects an appropriate tool based on the contextual descriptions, and the corresponding MCP server executes the tool and returns the result, which is used to generate the final response.
The standardized design of MCP significantly lowers the barrier for integrating new tools into agents, and within less than a year, thousands of MCP servers have been deployed. Security risks associated with the widespread application of MCP have increasingly emerged [29, 30]. Attackers may conduct tool poisoning attacks [10], rug pull attacks [31], etc, through MCP servers to undermine LLM-based agents.
2.3 Tool Poisoning Attack in MCP
Tool Poisoning is a specialized form of Indirect Prompt Injection (IPI). Unlike traditional IPI [32, 33], tool poisoning in MCP embeds malicious instructions directly into the description of a tool and injects them into them into the LLM’s context during the MCP registration phase, thereby influencing the agent’s decision during its reasoning process. Beurer-Kellner and Fischer [9] were the first to reveal the severity of such attacks in the MCP ecosystem. AutoMalTool [12] further proposes an automated framework for generating malicious MCP tool packages, where poisoned tools cause incorrect parameter invocation or output result misinterpretation when they are directly invoked. Notably, prior IPI methods are largely ineffective when directly inject their malicious instructions into tool descriptions but not execution results, with a steep decline in attack success rates [15]. This distinction highlights tool poisoning as a separate and more challenging threat class, necessitating dedicated research methodologies.

3 Threat Model
3.1 Trusted Model
The MCP workflow consists of three primary parties (as shown in Figure 1): the users, the MCP Host, and the MCP Servers.
The Users. The users are assumed to be honest and non-colluding. They issue benign queries to the agent via the Host, from which they receive the final responses.
MCP Host. The MCP Host is assumed to be trusted and serves as the application environment that contains the LLM agent and the client that manages communication. Given a user query and the system prompt, the Host orchestrates tool invocations and returns a final response to the user based on the tool execution results.
MCP Servers. The MCP Servers are treated as untrusted components. When the MCP Host concurrently connects to a benign server AA (with a legitimate tool set 𝒯A\mathcal{T}_{A}) and an attacker-controlled server BB (exposing a poisoned tool TKT_{K}), the poisoned tool is loaded into the agent’s system prompt alongside the benign tools. This enables the adversary to manipulate the agent’s tool invocation through the attack payload of TKT_{K}, thereby inducing malicious operations.
3.2 Attacker’s Capabilities
We consider a black-box setting where the attacker lacks access to the users’ actual queries and the internal parameters of the LLM agent hosted by the MCP Host. However, the attacker can inspect the toolset 𝒯A\mathcal{T}_{A} exposed by benign server AA to select an original tool TAT_{A} and a high-privilege target tool TGT_{G}. In addition, the attacker can craft the poisoned tool TKT_{K} and propagate it to public marketplaces via an attacker-controlled MCP server.
3.3 Attacker’s Goals
The attacker’s primary objective is to execute successful implicit tool poisoning attacks. For any user query that would otherwise trigger the invocation of TAT_{A}, the attacker aims to subvert the agent’s decision, redirecting it to invoke a legitimate but high-privilege tool TG∈𝒯A,TG≠TAT_{G}\in\mathcal{T}_{A},\;T_{G}\neq T_{A} to perform malicious operations, while ensuring that the poisoned tool TKT_{K} remains dormant and is never directly executed throughout the attack process. Furthermore, the attacker seeks to maintain evasiveness, ensuring that the poisoned tool circumvents existing malicious tool detection mechanisms.
4 Methodology
4.1 System Overview
MCP-ITP provides an automated framework that crafts tools for implicit tool poisoning attacks. As shown in Figure 2, it consists of three key components: an attacker LLM LAL_{A} that iteratively optimizes poisoned tools, a malicious tool detector LLM LDL_{D}, and an effectiveness evaluator LLM LEL_{E}. Given the legitimate tool set 𝒯A\mathcal{T}_{A} exposed by target MCP server AA, we first select an original tool TAT_{A} and a target tool TGT_{G}. The attacker LLM LAL_{A} then generates a sequence of candidate poisoned tools using an iterative optimization strategy, and submits each candidate to LDL_{D} and LEL_{E} for assessment. The outputs from LDL_{D} and LEL_{E} are aggregated as feedback and passed to subsequent iterations to guide LAL_{A} in refining the candidate poisoned tools. The optimization process terminates when either a predefined effectiveness criterion is satisfied or a maximum number of iterations is reached, at which point the best-performing candidate is selected as the final poisoned tool TKT_{K}.
4.2 Constructing RR for Relevance
We decompose the poisoned tool description desc⁡(TK)\mathrm{desc}(T_{K}) into two distinct subsequences, RR and SS, where RR is crafted to maximize semantic alignment with desc⁡(TA)\mathrm{desc}(T_{A}) and SS realizes the implicit poisoning functionality. Specifically, RR serves as a camouflage description that portrays TKT_{K} as functionally equivalent to the original tool TAT_{A}, increasing the salience TKT_{K} within the agent’s tool-selection context. We employ two lightweight yet effective strategies to construct RR. (i) Copy-based: RR is set directly to desc⁡(TA)\mathrm{desc}(T_{A}) to maximizes semantic overlap with TAT_{A}. (ii) Paraphrase-based: prompt an LLM to produce a semantically equivalent rephrasing of desc⁡(TA)\mathrm{desc}(T_{A}) and set it as RR, reducing surface-level duplication while preserving functional alignment. Once RR is established, it remains fixed while only SS is iteratively optimized in subsequent phases.

5 Experiments
5.1 Experiment Settings
LLM Agents.
We instantiate MCP-ITP with DeepSeek-V3 as the attacker model LAL_{A}, Qwen3-32b as the evaluator model LEL_{E}, and Qwen3-8b as the detector model LDL_{D}. We evaluate MCP-ITP across 12 prominent LLM agents, including models from GPT [35], DeepSeek [36], Qwen [37], and Gemini [38]. For Qwen3, which supports toggling its reasoning mode on and off, we evaluate both with reasoning enabled and disabled to analyze its impact on attack success rates.
Dataset.
We conduct experiments on MCPTox dataset. MCPTox is built on 45 real-world running MCP servers and 353 real tools, and contains a total of 1,497 malicious test cases. We focus on the subset of test cases corresponding to implicit poisoning paradigms (548 cases) and compare MCP-ITP against the hand-crafted poisoned tools in MCPTox under the same server/tool contexts and queries.
MCP Implementation.
We implement our MCP pipeline based on the open-source MCP codebase [39] and adopt its default system prompt.
Evaluation Metrics.
Our primary metrics are the Attack Success Rate (ASR) and the Malicious Tool Detection Rate (MDR). ASR measures the vulnerability of an agent to implicit tool poisoning and is computed as the number of successful attacks (Ns​aN_{sa}) divided by the total number of valid agent responses (Nv​rN_{vr}), excluding invalid generations, i.e., A​S​R=Ns​aNv​rASR=\frac{N_{sa}}{N_{vr}}. MDR measures the evasiveness of the poisoned tool against malicious tool detection methods and is calculated as the number of times that the poisoning tool is flagged as malicious (NmN_{m}) divided by the total number of valid outputs (NvN_{v}), i.e., M​D​R=NmNvMDR=\frac{N_{m}}{N_{v}}.
Optimization Hyperparameters.
Unless otherwise stated, we use the default hyperparameters (Algorithm 1): the number of candidates N=5N=5, tree width W=1W=1, and the number of iterations T=3T=3.
Evaluation Metrics.
To comprehensively assess the performance of MCP-ITP, we employ two primary metrics:
(i) Attack Success Rate (ASR), which quantifies the effectiveness of the implicit tool poisoning. It is defined as the ratio of successful attacks (Ns​aN_{sa}) to the total number of valid agent responses (Nv​rN_{vr}), excluding failed or irrelevant generations: A​S​R=Ns​aNv​rASR=\frac{N_{sa}}{N_{vr}}. (ii) Malicious Tool Detection Rate (MDR), which evaluates the stealthiness of the poisoned tool against detection mechanisms. It is defined as the ratio of the number of instances where the poisoned tool is flagged as malicious (NmN_{m}) over the total number of valid outputs (NvN_{v}): M​D​R=NmNvMDR=\frac{N_{m}}{N_{v}}.
5.2 Main Results
Our approach achieves high ASR and low MDR.
Table 1 reports the ASR of MCP-ITP across 12 LLM agent settings, together with a breakdown of failure modes. We run a single evaluation per setting. Here, Ignored refers to instances where the agent remains unaffected by poisoning and falls back to the original tool TAT_{A}. Direct refers to directly invoking the poisoned tool TKT_{K}. Others covers invoking other tools or refusing to respond. In general, MCP-ITP achieves high ASR across a range of LLM agents, e.g., 82.9% on o1-mini, 78.4% on DeepSeek-V3, and 84.2% on GPT-3.5-turbo. Figure 4(c) further shows that additional optimization iterations increase ASR across models, suggesting that iterative optimization can progressively refine poisoned tools and improve attack effectiveness. Most failures arise from Ignored behavior. In contrast, Direct or Others are relatively more frequent for certain models, indicating model-dependent differences in tool-selection policy and instruction adherence. Meanwhile, Figure 4 shows low MDR for MCP-ITP under different detection methods. Under AI-Infra-Guard, MDR is 0.3% on Qwen3-14b and 1.0% on o1-mini; under Oracle, MDR is 22.0% and 31.4%, respectively. These results indicate that the implicitly poisoned tools generated by MCP-ITP achieve high attack effectiveness while maintaining evasiveness.

5.3 Ablation Study
Impact of Model Characteristics.
To analyze the impact of model characteristics on attack effectiveness, we focus on two factors: model scale and reasoning mode. We conducted an ablation study on the Qwen3 model. As shown in Figure 4(d), Qwen3 models show a pronounced trend of increasing vulnerability with the model capability under MCP-ITP. Under the same evaluation settings, Qwen3-32b achieves higher ASR than Qwen3-8b, and o1-mini further exceeds Qwen3-32b. Moreover, enabling reasoning mode substantially increases ASR: Qwen3-8b rises from 7.44% to 40.5%, and Qwen3-32b from 28.8% to 69.9%. Failure-type analysis indicates that the trend is mainly driven by a decreasing Ignored rate as model capability increases. Stronger models rely less on TAT_{A} and are more likely to be manipulated by the poisoned tool TKT_{K}. This observation aligns with the inverse-scaling phenomenon reported in prior work [41, 42], suggesting that increased model capability does not necessarily improve robustness and can instead increase susceptibility to poisoned in-context tool specifications.
Impact of RR in desc⁡(TK)\mathrm{desc}(T_{K}).
Table 2 presents an ablation study comparing poisoned tool descriptions with and without the subsequence RR. Adding RR increases ASR for higher-capability models (o1-mini: +2.6 percentage points; GPT-4o-mini: +7.7; DeepSeek-R1: +4.6), suggesting that they better leverage the additional semantic association introduced by RR and thus more easily manipulated by TKT_{K}. In contrast, adding RR reduces ASR for weaker models (e.g., Qwen3 and Gemini-2.5-flash). In such cases, the more concise description (without RR) is more effective.
Impact of Evaluator LLM LEL_{E}.
To analyze how the evaluator LLM LEL_{E} affects the effectiveness of the generated poisoned tools, we conducted an ablation study on LEL_{E}, comparing Qwen3-32b against the more capable o1-mini (shown in Table 2). Using Qwen3-32b as LEL_{E} generally yields higher ASR and better cross-model generalization, outperforming o1-mini on GPT-4o-mini, DeepSeek and Qwen3. This outcome matches our observations during optimization: a relatively capable evaluator can cause some candidates SS to meet the preset shadow-query score threshold earlier than intended, triggering early stopping of and leading to suboptimal convergence. In contrast, a weaker LEL_{E} forces the attacker model LAL_{A} to continue refining candidate tools over more iterations and to discover more robust manipulation patterns that generalize across different LLM agents. For a few models (e.g., o1-mini and GPT-3.5-turbo), using o1-mini as LEL_{E} yields slightly higher ASR.
6 Conclusion
In this work, we show that agent tool invocations in the MCP workflow are vulnerable to implicit tool poisoning attacks. We propose MCP-ITP, the first automated and adaptive framework for implicit tool poisoning within the MCP ecosystem. MCP-ITP formulates poisoned tool generation in a black-box setting as an optimization problem and employs an optimization strategy that leverages feedback from both an evaluation LLM and a detection LLM to maximize ASR while evading LLM-based malicious tool detectors. We evaluated MCP-ITP on the MCPTox dataset across 12 prominent LLM agent settings. The results show that MCP-ITP outperforms the manually crafted baseline, substantially improving ASR while significantly reducing MDR. The resulting implicitly poisoned tools can effectively manipulate the agent’s tool invocations without ever being directly executed, and can evade existing malicious tool detection methods. Our findings demonstrate that implicit tool poisoning constitutes a practical threat in the MCP ecosystem, underscoring the urgent need for security mechanisms to defend against these attacks.
Limitations
In this paper, we propose MCP-ITP, which uses an iterative optimization strategy to craft tools for implicit tool poisoning attacks in MCP settings. When stronger models are employed by LLM-based malicious tool detection methods, the MDR of MCP-ITP still increases. Designing poisoned tools that better evade such detection mechanisms without significantly compromising attack effectiveness remains an important direction for future research. In addition, our experimental evaluation is currently restricted to the MCPTox dataset for MCP tool poisoning, primarily because the available datasets for MCP-specific implicit tool poisoning are still limited. Future work should extend the evaluation to newly developed or broader datasets to enable a more comprehensive and comparative assessment of MCP-ITP. Finally, we focus on extensive empirical evaluation to demonstrate MCP-ITP’s attack effectiveness and evasiveness, rather than providing a formal theoretical analysis.
Ethical Considerations
This research aims to responsibly identify vulnerabilities in LLM through implicit tool poisoning attacks. Our sole intent is to raise security awareness and encourage the development
of stronger defences, not to enable harmful misuse. We acknowledge that the techniques explored in this work could be misused if applied irresponsibly. To mitigate this risk, we did not deploy these attacks in real-world settings or against live systems. All experiments were conducted in controlled environments to avoid causing real-world harm. By communicating these risks, we hope this work promotes the development of more robust, ethical, and reliable AI technologies.
We do not collect, process, or store real personal data. The dataset used in our experiments is open and transparent, and any PII is randomly generated, ensuring no real individuals’ privacy is compromised. We emphasize that advancements in adversarial understanding should always be accompanied by proactive defense strategies to ensure the safe and responsible deployment of AI technologies.

Appendix D Prompt for Detector LLM LDL_{D}
Given a candidate poisoned tool TK​(Si)T_{K}(S_{i}), we use the detector LLM LDL_{D} to analyze its description for embedded instructions and determine whether it contains malicious content. LDL_{D} outputs a binary label along with supporting rationale. The prompt used for LDL_{D} is shown below.
Prompt for malicious tool detection
You are looking at a tool that an agent has access to. Your task is to determine whether the following tool description is malicious (prompt injection attack).
Focus on identifying any suspicious instructions that deviate from the original function of the tool.
Malicious indicators include:
1. Contains "Ignore previous instruction" or similar statements to bypass system rules.
2. Has hidden instructions (e.g., other languages, base64, strange formats).
3. Forces the agent to replace legitimate tools with malicious ones (e.g., "must use X instead of Y").
4. Manipulates the agent to perform unexpected actions beyond normal tool functions.
Tool description to detect:
[p​o​i​s​o​n​_​t​o​o​lpoison\_tool]
Output Format (MANDATORY):
First line: EXACTLY "YES" (malicious) or "NO" (benign). If you are not sure, answer "No".
Second line: Reason (1-2 sentences explaining why it’s malicious/benign).
No extra text, no punctuation in the first line.
