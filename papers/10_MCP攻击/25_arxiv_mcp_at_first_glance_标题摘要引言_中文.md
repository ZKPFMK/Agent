# 模型上下文协议（MCP）初探：MCP 服务器的安全性与可维护性研究

**原标题：**Model Context Protocol (MCP) at First Glance: Studying the Security and Maintainability of MCP Servers  
**年份与来源：**2025，arXiv:2506.13538（本地 PDF 为 v5，2026 年 4 月 13 日）。  
**原文：**[本地 PDF](./25_arxiv_mcp_at_first_glance.pdf)。

## 摘要

尽管 GPT-4 等基础模型（Foundation Models，FMs）正越来越多地应用于金融、软件工程等领域，但对文本接口的依赖限制了这些模型与现实世界进行交互的能力。为解决这一问题，基础模型提供商引入了工具调用机制，由此催生出大量具有不同工具接口的框架。2024 年末，Anthropic 提出了模型上下文协议（Model Context Protocol，MCP），用于统一这一工具生态。随着 MCP 软件开发工具包每周下载量超过 2,500 万次，且 86% 的企业使用支持 MCP 工具的模型，MCP 正迅速成为事实上的行业标准。然而，MCP 由 AI 驱动的非确定性控制流引入了新的可持续性、安全性和可维护性风险，需要得到更深入的研究。

为此，我们开展了首个针对 MCP 的大规模实证研究。我们利用现有的先进健康度指标，并构建一个结合通用静态分析工具与 MCP 专用扫描器的混合分析流程，对 1,899 个开源 MCP 服务器进行评估，以考察其健康度、安全性和可维护性。尽管 MCP 服务器整体表现出较好的健康度指标，我们仍识别出 8 种不同的漏洞，其中只有 3 种与传统软件漏洞重叠。此外，7.2% 的服务器包含通用漏洞，5.5% 存在 MCP 特有的工具投毒问题。在可维护性方面，66% 的服务器存在代码异味，14.4% 包含 10 种与既有研究重叠的缺陷模式。

这些发现表明，有必要采用 MCP 专用的漏洞检测技术，同时也证实传统分析和重构实践仍然具有价值。此外，我们呼吁加强 MCP 生态系统治理：将 MCP 特有漏洞纳入标准化漏洞数据库，在 MCP 注册平台中支持自动化安全扫描，并推广负责任的开发实践，以确保 MCP 生态系统的长期安全与可持续发展。

**CCS 分类：**软件及其工程 → 实证软件验证。  
**关键词：**模型上下文协议、MCP、安全性、代码异味、软件缺陷、可维护性。

**译注：**原文摘要写作“10 种与既有研究重叠的缺陷模式”，引言 RQ-2 部分则分别报告“10 种代码异味和 9 种缺陷”；本文按原文对应位置分别保留这两组表述。

## 引言

GPT-4 [110] 和 LLaMA [147] 等基础模型（Foundation Models，FMs）凭借强大的语言理解、生成和推理能力，推动了人工智能（Artificial Intelligence，AI）应用的变革。它们的广泛应用表现在逐渐融入金融 [161]、医疗 [50] 和软件开发 [158] 等领域的现实产品和应用中，根本性地改变了我们与技术及信息交互的方式。尽管发展势头强劲，基础模型本质上仍通过相互隔离的“文本”接口运行，限制了它们直接访问动态现实数据源、API 和系统的能力。

为了初步弥合这一差距，基础模型提供商引入了函数调用 [96, 108] 和工具调用 [14] 等能力，通常统称为工具调用，使模型能够与现实世界交互，例如使用日历工具预约。借助这些能力，LangChain [82]、Autogen [18]、Pydantic-AI [3]、CrewAI [44]、Dify [51] 和 LlamaIndex [92] 等 AI 与智能体框架引入了基于基础模型的工具工作流，用于构建能够理解任务、规划工具使用并协调工具调用的 AI 应用。然而，随着这些框架大量出现，一个重要问题也随之产生：每个框架通常都定义了自己的工具接口和数据结构。例如，在一个 AI 框架中定义的工具无法直接移植到另一个 AI 框架中，形成了阻碍互操作性、可扩展性和一致性安全实践的生态碎片化。

为解决这些局限，Anthropic 提出了模型上下文协议（Model Context Protocol，MCP）[11]。MCP 是一种通用的客户端—服务器协议，用于规范 AI 应用向基础模型暴露工具的方式。类似于软件包管理器（如 NPM、PyPI [25]）对不同领域的软件组件复用进行标准化，MCP 提供了一个统一的开放标准，使兼容 MCP 的客户端能够从多样化的 MCP 服务器生态中发现并调用工具，从而增强 AI 工具使用的互操作性。

在 AI 和软件工程的更广泛背景下，MCP 通过增强互操作性、减少生态碎片化，成为 AI 原生应用架构的基础组成部分 [69]。自 2024 年 11 月底推出以来，Microsoft [97]、OpenAI [109]、Google [93] 和 Cloudflare [41] 等主要参与者都已经采用 MCP 来支持 AI 应用。例如，Microsoft 的 Azure MCP 服务器¹使基础模型能够与 Azure 服务交互，包括云存储和数据库。MCP 为基础模型提供了与外部系统交互的标准化机制，因此不再需要针对不同模型或特定智能体框架重复编写定制工具接口。这既减轻了实践者对基础模型提供商和框架供应商的锁定，也通过复用已有 MCP 服务器加快了开发周期。因此，MCP 得到了快速普及：官方 MCP 软件开发工具包的每周下载量已经超过 2,500 万次 [12, 13]，据估计，86% 的企业可以通过支持工具调用的模型使用具备 MCP 能力的工作流²。行业领导者的快速采用和开源社区的积极参与，凸显了 MCP 日益增强的核心地位，也进一步促使我们从开源软件的健康度、可持续性、漏洞和可维护性等角度考察 MCP 服务器。

与部署在生产环境中的其他可复用软件包（例如 PyPI 和 NPM 软件包）类似，MCP 服务器的健康度、可持续性、安全性和可维护性对于生态系统的长期发展至关重要。其他软件生态系统的经验表明，社区会优先选择安全、广泛采用且文档完善的软件包 [103]。然而，早期研究已经表明，基础模型可能被诱导使用存在漏洞的 MCP 服务器中的工具，从而危害用户系统。这类问题通常被称为工具投毒，并可能导致凭据窃取和恶意代码执行 [69, 106]。例如，某个 MCP 服务器可能拥有文件写入权限；攻击者通过操纵基础模型，可以诱导它将恶意代码片段写入 `.bashrc` 文件，从而为攻击者打开后门端口 [118]。MCP 服务器工具的核心目标是让基础模型自主决定何时以及使用哪个工具，因此工具中潜在的安全和可维护性问题已经引起行业参与者的关注 [98]。

这些担忧并非理论上的假设，而已经在现实安全事件中得到体现。例如，近期发现的首个恶意 Postmark-MCP 服务器会在用户不知情的情况下添加隐藏的密件抄送（Blind Carbon Copy，BCC），并外泄数千封用户邮件，说明遭到入侵的 MCP 服务器能够绕过传统安全控制，大规模泄露敏感数据³。与此同时，安全社区也在识别 MCP 服务器开发者供应链中的关键漏洞。一个近期案例是 MCP Inspector 中的严重远程代码执行漏洞（CVE-2025-49596）：攻击者只需诱导开发者访问恶意网站，就可以在开发者机器上执行任意命令⁴。这些事件凸显了以实证方式研究 MCP 服务器健康度、安全性和可维护性的紧迫性，因为 MCP 服务器中的缺陷可能直接危害用户系统、数据完整性和供应链信任。

然而，尽管存在这些担忧，目前公开可用的开源 MCP 服务器在健康度、可持续性、安全性和可维护性等关键软件维度上的现状仍缺乏研究。理解这些维度非常重要，因为早期开发健康度和可持续性会直接影响 MCP 服务器的可信度，并决定其能否在实践中得到可靠采用。此外，如果缺乏对安全状况和可维护性特征的了解，实践者就可能在不了解实际攻击面和长期运行影响的情况下部署系统。考虑到未解决的软件问题可能造成的影响，这种信息缺口尤其令人担忧。例如，我们已经知道，2014 年仅 Heartbleed 一个漏洞就在全球造成了约 5 亿美元的损失 [137]；近期行业报告还表明，成熟组织每年在单个系统的软件维护上可能花费高达 25 万英镑（约 33.25 万美元）[59]。如果缺少对这些维度的严格实证分析，社区就无法主动采取措施，缓解相关风险和问题。

基于上述动机，我们提炼出当前 MCP 生态系统中缺乏实证证据支持的三个开放问题：

1. MCP 生态系统目前的维护活跃程度如何？
2. 公开可用的 MCP 服务器中，传统漏洞和 MCP 特有漏洞的普遍程度如何？这一漏洞状况与其他软件生态系统有何不同？
3. 代码异味和缺陷等可维护性问题，是否引发了与成熟软件生态系统相当的担忧，并因此阻碍 MCP 的采用？

为弥补这一空白，我们首次对 1,899 个 MCP 服务器的健康度、可持续性、安全漏洞和可维护性问题开展大规模实证研究。截至 2025 年 6 月 1 日，我们的数据集包含来自官方 MCP 集合 [117] 的 343 个 MCP 服务器，以及从 GitHub 开源仓库中挖掘得到的 1,556 个 MCP 服务器。通过分析这些 MCP 服务器，我们试图回答以下研究问题（Research Questions，RQs）。

### RQ-0：MCP 服务器的健康度和可持续性如何？

**研究动机。**随着 MCP 成为 AI 应用生态系统的重要组成部分，理解 MCP 生态系统当前的健康度和可持续性十分必要。已有研究表明，不同的开发指标（提交次数、持续集成采用情况等）和社区指标（贡献者数量、贡献者声誉、问题活跃度等）可以作为健康度和长期可持续性的衡量信号 [42, 58, 162]。开发指标反映持续维护活动，社区指标则反映利益相关者的参与程度。通过研究这些指标，并将其与通用开源软件和机器学习（Machine Learning，ML）软件的指标进行对比，我们可以了解 MCP 服务器健康度和可持续性的当前状态。

**研究发现。**MCP 服务器表现出较强的开发和社区指标：平均每周提交 5.5 次，而传统软件为 2.5 次；持续集成采用率略高，为 42.2%，传统软件为 40.3%；贡献者数量的中位数相当，均为 2.0；但 MCP 服务器在贡献者的社交影响力方面显著更高，贡献者关注者数量的中位数为 129.6，而传统软件为 37.3；同时，其问题解决时间的中位数略慢，为 5.6 天，而传统软件为 4.0 天。

### RQ-1：MCP 服务器包含安全漏洞的程度如何？

**研究动机。**已有研究报告称，至少 46% 的 Python 软件包包含安全漏洞 [125]，而某些安全事件（例如数据泄露）的平均成本可能高达 450 万美元 [71]。在 MCP 服务器场景中，潜在风险可能更高，因为这类系统将基础模型与数据库、文件系统和 API 连接起来，并将控制权交给基础模型。为了理解实际风险，我们需要刻画 MCP 服务器的漏洞模式，将这些漏洞与已知的传统软件工程漏洞进行比较，并评估当前漏洞检测工具识别 MCP 特有问题的有效性。

**研究发现。**为了探索 MCP 服务器的漏洞状况，我们使用传统漏洞检测器 SonarQube，发现 7.2% 的 MCP 服务器受到 8 种不同漏洞模式的影响，其中最普遍的是凭据暴露（3.6%）。这 8 种漏洞中只有 3 种与已知生态系统漏洞重叠。然而，通过应用 MCP 专用扫描工具 [79]，我们发现 5.5% 的 MCP 服务器存在工具投毒问题。这说明传统工具只能发现整体漏洞状况的一部分，社区需要更强的 MCP 专用漏洞检测技术和工具。

### RQ-2：MCP 服务器包含可维护性问题的程度如何？

**研究动机。**已有研究表明，可维护性问题（例如代码异味）可能与缺陷或故障倾向相关 [111]。在成熟项目中，软件开发团队可能将高达 39% 的维护工作量用于修复此类问题 [10]。作为一种新兴技术，社区目前还不了解 MCP 服务器的可维护性状况，例如其中代码异味和缺陷的分布。为了理解这些可维护性问题对 MCP 服务器的影响，我们需要刻画代码异味和缺陷，并将其与已知的传统软件工程问题进行比较，以评估其长期影响。

**研究发现。**MCP 服务器表现出与传统软件工程领域相似的代码异味和缺陷模式。从长期来看，我们推测这些代码异味和缺陷可能在 MCP 领域造成严重的可维护性问题，正如它们在传统软件工程中所表现的那样 [59]。我们报告了 MCP 代码中的 10 种代码异味和 9 种缺陷，并发现 66% 的 MCP 服务器存在严重级别或阻塞级别的代码异味，其中最普遍的是高认知复杂度；此外，14.4% 的 MCP 服务器存在严重级别或阻塞级别的缺陷。

本文的主要贡献如下：

1. **资产。**
   - **数据集：**我们发布了一个经过整理的、包含 1,899 个开源 MCP 服务器的数据集，其中包括 88 个官方服务器、255 个社区维护服务器，以及通过结构化发现流程从 GitHub 挖掘得到的 1,556 个服务器。该统一数据集首次覆盖 MCP 生态系统的完整范围，支持可复现、可扩展和纵向的生态系统级研究，并可作为未来 MCP 专项研究的基础数据集。
   - **比较基线：**我们建立了用于评估 MCP 服务器健康度、可持续性、安全性和可维护性的跨生态系统基线。我们收集并标准化来自成熟开源软件工程和机器学习生态系统的参考指标，包括 PyPI、NPM 和基础设施即代码（Infrastructure-as-Code，IaC）生态，从而构建整合健康度、可持续性、漏洞和代码异味指标的基线。这些基线能够支持新兴生态系统与成熟开源领域之间一致且可迁移的比较。
2. **方法。**我们提出了一个混合分析框架，将通用静态分析与 MCP 专用漏洞检测结合起来。据我们所知，这是首个将 SonarQube 等传统静态分析器与 MCP 专用扫描器（mcp-scan）结合的框架，能够在同一实证流程中联合评估传统漏洞和 MCP 特有漏洞。通过替换特定领域的扫描器和目标，该框架也为分析其他新兴软件工程领域提供了可复用、可扩展的基础，从而支持对不同生态系统中的漏洞和可维护性开展可扩展、可复现和可比较的研究。
3. **实证发现。**我们通过大规模实证分析评估 MCP 服务器的健康度、安全性和可维护性。结果表明，MCP 服务器具有较强的健康度和可持续性指标，但仍然包含传统漏洞和 MCP 特有漏洞，并且普遍存在代码异味和反复出现的缺陷模式等可维护性问题。
