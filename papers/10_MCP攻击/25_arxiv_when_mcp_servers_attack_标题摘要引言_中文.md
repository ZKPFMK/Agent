# 当 MCP 服务器发起攻击：分类、可行性与缓解

**原标题：**When MCP Servers Attack: Taxonomy, Feasibility, and Mitigation  
**年份与来源：**2025，arXiv:2509.24272（v1，2025 年 9 月 29 日）。  
**原文：**[本地 PDF](./25_arxiv_when_mcp_servers_attack.pdf)。

## 摘要

模型上下文协议（Model Context Protocol，MCP）服务器使 AI 应用能够以即插即用的方式连接外部系统，但其快速普及也引入了严重的安全风险。与具有严格审查机制的成熟软件生态系统不同，MCP 服务器目前仍缺乏标准化的审核机制，使攻击者有机会传播恶意实现。尽管这一风险十分迫切，MCP 服务器的安全影响仍未得到充分研究。

为弥补这一空白，我们首次将 MCP 服务器视为主动威胁主体，并将其分解为核心组件，以考察攻击者如何植入恶意意图。具体而言，我们研究三个问题：（1）恶意 MCP 服务器能够发起哪些类型的攻击；（2）MCP 主机和大语言模型（Large Language Model，LLM）对这些攻击的脆弱程度如何；（3）在实践中实施 MCP 服务器攻击的可行性如何。

本文提出了一个基于组件的分类体系，包含 12 类攻击。针对每一类攻击，我们都开发了概念验证（Proof-of-Concept，PoC）服务器，并在多种现实世界的主机—LLM 配置中验证其有效性。我们进一步表明，攻击者几乎无需成本就能生成大量恶意服务器。随后，我们在生成的服务器上测试最先进的扫描器，发现现有检测方法不足以识别这些威胁。

这些发现表明，恶意 MCP 服务器易于实现，难以通过现有工具检测，并且能够对 AI 智能体系统造成具体危害。应对这一威胁需要协议设计者、主机开发者、LLM 提供商和终端用户协同努力，共同构建更安全、更具韧性的 MCP 生态系统。

**关键词：**模型上下文协议、MCP 服务器、LLM、AI 智能体、安全性。

## 引言

随着 LLM 能力不断增强，如何让 LLM 获取最新信息并执行现实世界操作，正受到越来越多关注。早期解决方案包括定制 API 连接器，以及 LangChain [11]、AutoGen [26] 等智能体框架。这些方案虽然有效，但通常需要开发者投入大量工作。MCP [5] 提供了另一种选择：通过定义用于资源发现和工具调用的标准化接口，使 LLM 能够以较低的集成成本，在运行时动态访问外部环境。

MCP 采用客户端—服务器架构。MCP 主机通常是一个 AI 应用，通过 MCP 客户端与 MCP 服务器建立连接；MCP 服务器则是对函数和数据的封装。例如，智能体可以连接本地服务器执行文件系统操作，也可以连接远程服务器访问电子邮件。MCP 架构允许主机和服务器独立实现，而协议设计只要求在主机侧注册服务器，从而简化了主机与服务器之间的集成。

MCP 的开放性和模型无关特征促进了活跃的社区发展。截至 2025 年 8 月，网络上公开可用的 MCP 服务器已经超过 16,000 个 [36]。尽管 Alibaba [1]、Google [16] 和 Oracle [12] 等主要服务提供商已经发布官方 MCP 服务器，但绝大多数服务器仍由社区开发。这种快速扩张带来了显著的安全风险。

与拥有成熟审核流程和集中式应用商店的移动应用生态系统不同，MCP 生态目前仍缺乏标准化监管。一方面，GitHub [14] 和 npm [29] 等主流开源平台允许任何人自由发布 MCP 服务器；另一方面，即使是专门托管 MCP 服务器的网站，例如 Smithery.ai [33]、MCP.so [36] 和 Glama [15]，也尚未建立健全的审核流程 [34]。这为攻击者伪装成有用工具发布恶意 MCP 服务器创造了条件。攻击者可以宣称服务器具备先进能力，以吸引用户安装。

这些缺口凸显了深入理解和系统分析 MCP 服务器所带来威胁的迫切需要。近期已有一些研究开始考察 MCP 服务器安全性 [13, 19, 21, 27, 34, 37]。其中，一些研究分析了 MCP 相关威胁并提出了不同的分类体系 [19, 21, 27]；另一些研究提出了具体攻击向量，并在先进 LLM 上开展实验 [13, 34, 37]。然而，据我们所知，尚无工作从 MCP 服务器内部组件的角度，系统考察恶意 MCP 服务器带来的安全威胁。

本文针对这一空白，研究以下问题：

- **RQ1：**恶意 MCP 服务器能够发起哪些类型的攻击？
- **RQ2：**MCP 主机和 LLM 对来自恶意 MCP 服务器的攻击有多脆弱？
- **RQ3：**从实现和检测规避的角度看，这些攻击在实践中有多大可行性？

为回答这些研究问题，我们首先开展基于组件的 MCP 服务器攻击分析（第 3 节），并在多种 MCP 主机和 LLM 模型上评估这些攻击（第 4.1 节）。随后，我们研究攻击实现的难度以及绕过检测的难度（第 4.2 节），以衡量其现实攻击可行性。

基于分析和实验结果，我们得到以下主要发现：

1. **恶意 MCP 服务器能够发起 12 类攻击。**这些攻击可以组织为一个基于组件的分类体系。每类攻击还包含多个细粒度攻击类型，可能导致系统失陷、操纵 LLM 和用户，或使客户端拒绝服务等严重后果。
2. **跨主机—LLM 评估表明，这些攻击即使面对先进的主机—LLM 组合仍然有效。**实验进一步显示，MCP 服务器攻击的成功与主机设计、LLM 安全训练和用户安全意识共同相关。
3. **恶意 MCP 服务器在实践中易于生成，现有 MCP 服务器扫描器不足以检测它们。**综合来看，这些结果凸显了处理 MCP 服务器安全问题的紧迫性，也说明必须将恶意 MCP 服务器视为首要威胁。

我们讨论了潜在的解决方案，并呼吁社区给予更广泛的关注。MCP 生态系统的安全需要多个利益相关方协同努力，包括 MCP 协议设计者、MCP 主机开发者、LLM 提供商和终端用户（第 5 节）。

**图 1. MCP 架构概览。**MCP 主机通过 MCP 客户端连接本地或远程 MCP 服务器；服务器提供工具、资源和提示词，并通过标准输入输出或 HTTP 与主机通信。主机中的编排器负责协调用户界面、LLM 客户端和 LLM 提供商。

本文的主要贡献如下：

- **基于组件的 MCP 服务器攻击分类体系。**我们从 MCP 服务器内部组件的角度系统分析恶意 MCP 服务器，建立涵盖 12 类不同攻击的分类体系，为理解 MCP 服务器攻击面提供结构化基础。
- **跨主机和 LLM 的实证攻击评估。**我们开展大规模实验，评估所识别攻击针对不同 MCP 主机和 LLM 模型的有效性。结果表明，这些攻击具有广泛有效性，其成功取决于 MCP 主机设计和 LLM 安全对齐程度。
- **现实攻击可行性分析。**我们研究恶意 MCP 服务器的实现难度，以及其绕过当前检测机制的能力。结果发现，这些攻击不仅切实可行，而且在很大程度上能够躲过现有审核工具。

## 2 背景

### 2.1 模型上下文协议

MCP 是一种开放协议，用于规范 LLM 与外部数据和工具之间的交互 [2, 5]。图 1 展示了 MCP 的整体架构，其中包括主机（Host）、客户端（Client）和服务器（Server）三个不同组件。MCP 主机是一个基于 LLM 的应用，例如 Claude Desktop [3]、Cursor [10] 或 Windsurf [38]。在主机内部，每个 MCP 客户端都会与一个 MCP 服务器建立并维护一对一连接。MCP 主机可以管理多个客户端，以支持连接多个服务器。MCP 客户端代表主机应用处理消息传输、工具发现、工具调用和资源访问。MCP 服务器则向客户端提供上下文、工具和提示词，从而扩展 LLM 面向外部世界的能力 [4]。

### 2.2 MCP 服务器

MCP 服务器可以独立于主机应用开发，并且能够方便地接入不同主机，因此得到了广泛采用 [7, 23, 25]。如图 1 所示，根据部署方式，MCP 服务器可以分为本地服务器和远程服务器。

本地服务器运行在与 MCP 主机相同的机器上，使 LLM 能够访问本地数据和服务。本地服务器可以使用 `npx` 或 `uvx` 等工具以非持久方式启动，也可以通过 `git clone`、`npm install` 或 Docker 进行持久化安装。相比之下，远程服务器运行在与 MCP 主机不同的机器上，通常提供对远程资源或云资源的访问。

根据不同职责，一个 MCP 服务器可以分解为六个组件：元数据、配置、初始化逻辑、工具、资源和提示词。每个服务器都必须包含元数据、配置和初始化逻辑，才能接入主机并正常运行；工具、资源和提示词则是可选组件，取决于服务器计划提供的服务。

具体而言，**元数据**是面向人或系统使用的 MCP 服务器信息，包括描述性元数据和结构化元数据 [22]。描述性元数据是文档、README 文件或服务器宣传网站中的自然语言内容；结构化元数据通常以 JSON 形式存在于服务器源代码和主机配置文件中，包括名称、版本和授权设置等字段。

**配置**是用户和主机使用服务器所需的信息，通常由服务器开发者提供。服务器配置包括启动配置和连接配置。启动配置包括启动服务器进程所需的可执行文件路径、命令行参数和环境变量；连接配置则是 MCP 主机定位并连接服务器所需的信息，例如 URL 或端口。

**初始化逻辑**是使 MCP 服务器能够启动并接入主机的代码，通常包括依赖初始化、环境配置、传输配置和连接流程。初始化逻辑可以看作 MCP 服务器正常运行的基础。

在可选组件中，**工具**是由 MCP 服务器注册并向 LLM 暴露的可调用执行函数。MCP 服务器暴露的每个工具由三个部分组成：工具元数据、工具内部逻辑和工具返回值。工具元数据包括：用于标识工具的名称；供 LLM 理解的人类可读描述；使用 JSON Schema 指定参数名称、类型、描述和约束的输入模式；以及可选的、用于描述工具行为的一组注释。

**资源**是服务器向用户和 LLM 暴露数据的标准化接口。每个资源由 URI 唯一标识，并包含人类可读名称、可选描述、表示内容格式的 MIME 类型，以及可选的字节大小等元数据。

**提示词**是服务器提供的可复用模板，用于辅助用户与 LLM 交互。每个提示词都包含名称、描述和一组动态参数。

### 2.3 现有工作的局限

随着 MCP 得到越来越多关注和采用，近期研究开始讨论其安全挑战。Hou 等人 [19] 强调了 MCP 服务器在创建、运行和更新阶段可能存在的安全风险，包括安装器欺骗、沙箱逃逸以及重新部署存在漏洞的版本。

从 MCP 主要角色的角度出发，Narajala 和 Habler [27] 识别出多类 MCP 安全威胁，包括 MCP 服务器威胁、MCP 客户端威胁、MCP 主机环境威胁、数据源和外部资源威胁、工具相关威胁，以及提示词相关威胁。

Jing 等人 [21] 从五个维度对 MCP 交互中的风险进行分类：阶段（Stage）、来源（Source）、范围（Scope）、类型（Type）以及相应的 MAESTRO 层。基于其威胁分析，他们提出了增强型协议 MCIP，并构建了 MCP 交互对话数据集 MCIP-Bench。MCIP-Bench 的评估表明，现有 LLM 在 MCP 场景中的安全意识较弱。

Guo 等人 [18] 提出了 MCP 攻击库（MCP Attack Library，MCPLIB），这是一个用于模拟和评估 MCP 攻击的统一插件化框架。他们将 31 种攻击归入四个类别：直接工具注入、间接工具注入、恶意用户攻击和 LLM 固有攻击。

尽管已有工作提供了有价值的洞察，但此前尚无研究系统、实证地考察恶意 MCP 服务器带来的威胁。具体而言，如表 1 所示，现有工作的实证评估仍然有限。本文通过系统分析和大规模实验弥补这一空白。

我们分析 MCP 服务器的内部结构，并提出基于组件的攻击分类体系。针对分类体系中的 12 类攻击，我们分别实现具体的概念验证服务器，并在多种主机—LLM 组合上开展评估，从而超越现有以 LLM 为中心的测试。结果表明，本文识别的所有 MCP 服务器攻击都具有现实可行性和实际影响；此外，现有扫描器无法提供充分保护，攻击者只需很低成本就能实现恶意服务器。

## 3 MCP 服务器攻击分类体系

### 3.1 威胁模型

我们考虑这样的攻击者：他们在公开可访问的平台上开发并发布恶意 MCP 服务器，之后，善意用户按照攻击者提供的说明，将该服务器集成到自己的智能体工作流或 LLM 应用中。

**攻击目标。**攻击者的目标包括：（1）破坏服务器运行所在的本地执行环境；（2）操纵 LLM 的行为；或（3）欺骗用户。

**攻击者能力。**攻击者完全控制服务器代码库，以及所有相关的公开材料，例如 Markdown 文档。攻击者不违反 MCP 协议，甚至可以使用官方 SDK 实现服务器。

**其他参与者的假设。**除恶意服务器外，MCP 工作流中的其他参与者都被假设为善意实体。LLM 没有经过对抗性训练，也没有植入后门；用户以善意行事，不会故意尝试攻陷 LLM 或系统；MCP 主机应用和 MCP 客户端均实现正确，不包含恶意意图。

### 3.2 基于组件的攻击分类

图 2 展示了构造和部署恶意服务器以发起攻击的整体流程。攻击者首先编写服务器源代码，将恶意内容嵌入初始化逻辑、工具、资源或提示词中。随后，攻击者使用吸引人的名称，将服务器上传到公共分发平台，并配以具有说服力的描述和便于安装的配置代码块。用户受到服务器展示信息吸引后，可能会将配置代码块复制到主机应用的配置文件中。主机下次启动时，会自动将恶意服务器下载到用户设备并集成到 AI 应用中，从而为多种攻击创造条件。

**图 2. 对抗性 MCP 服务器的分发流程。**攻击者在服务器源代码中植入恶意内容，并通过服务器文档和分发平台诱导用户安装；用户将配置代码复制到主机配置文件后，恶意服务器随主机启动并进入 AI 应用。

为了更好地刻画针对 MCP 服务器的潜在攻击，我们从服务器的基本构件出发，提出首个基于组件的攻击分类体系，对这些威胁进行系统组织。该分类体系在 MCP 六个基本服务器组件的基础上进一步细分，形成 12 个不同的攻击类别。每个类别还包含多个攻击变体，分别代表攻击者通过相应服务器组件能够实施的具体恶意行为。

图 3 展示了分类体系中的 12 个攻击类别（A1–A12）及其子类型。该分类体系与部署模式无关，既适用于远程 MCP 服务器，也适用于本地 MCP 服务器。

#### 3.2.1 A1：服务器元数据投毒

元数据提供 MCP 服务器的描述性信息。元数据应当诚实、准确，以便用户、客户端和主机理解并识别服务器。然而，攻击者可以精心构造服务器元数据，将其变成有效的攻击向量。

1. **用于诱导用户采用的宣传性元数据。**攻击者可以在公共平台上发布恶意 MCP 服务器，并使用醒目的名称和具有吸引力的能力描述进行宣传。用户可能因此被诱导，将不安全的服务器集成到自己的 AI 智能体中。完成集成后，主机可能会在用户界面中展示服务器名称和描述，这些信息还可能进一步诱导用户选择该服务器提供的资源或提示词。
2. **用于获取 LLM 信任的欺骗性元数据。**当主机将服务器元数据提供给 LLM 时，模型可能依赖服务器名称或描述来判断其用途，并将有害服务器误认为良性服务器。图 4 展示了一个例子：恶意 MCP 服务器通过采用具有欺骗性的名称来冒充官方 PayPal 服务器。图中，`paypal-mcp-server` 对应合法的 PayPal MCP 服务器，而 `official-paypal-server` 实际指向攻击者控制的恶意端点。这个简单的命名技巧可能误导 LLM。当模型处理可用服务器时，可能错误地认为 `official-paypal-server` 是合法服务器，并开始与其交互，从而使模型和用户都面临风险。
3. **恶意授权元数据。**对于通过 HTTP 与客户端通信的 MCP 服务器，服务器可以指定授权元数据，例如授权服务器 URL。攻击者可以在这一字段中填入恶意端点，甚至填入可执行命令。如果主机没有正确验证该字段，就可能被重定向到攻击者控制的端点，或无意中执行恶意代码。

#### 3.2.2 A2：服务器配置滥用

MCP 服务器通常会在文档或落地页中提供配置说明。虽然配置不属于服务器内部逻辑，但它是服务器接入 AI 应用的必要环节。恶意服务器提供者可以利用这些配置设置造成危害。

1. **过度授权的启动参数。**恶意服务器可能提供使服务器进程获得超出必要范围权限的启动命令。`env`、`cwd` 和 `args` 等配置参数都可能成为攻击向量。用户可能不了解这些参数的安全影响，从而在不知情的情况下采用不安全设置。过度授权的配置还会放大后续攻击的影响，使攻击者获得更广泛的访问和控制能力。例如，攻击者可以提供一段配置，指定使用 Docker 启动，并传入类似 `run --rm -i -v /:/mnt/host server-image` 的参数。该设置会将整个主机根文件系统挂载到容器中，使服务器获得管理员级别的、不受限制的系统访问权限。此外，许多现有 MCP 服务器虽然并非出于恶意目的，也会要求用户使用 `npx` 或 `uvx` [28] 启动服务器，这同样可能带来安全风险。
2. **对抗性连接参数。**远程 MCP 服务器不需要用户在本地启动，只需将其 URL 添加到主机配置文件中即可。因此，攻击者可以提供恶意 URL。一旦主机尝试连接，所有通信都会流向攻击者的服务器，从而使攻击者能够收集数据或返回恶意响应。
3. **通过主机自动启动实现持久化。**这一攻击利用了 MCP 主机的常见设计模式。大多数主机采用“一次配置、始终运行”模型：服务器启动命令一旦写入主机配置文件，主机每次启动时都会自动启动服务器进程，无需用户再次确认。恶意服务器可以利用这一机制，在主机重启后持续运行并获得重复执行机会。
4. **Rug Pull。**服务器配置代码块可能包含自动更新参数（例如 `-y`、`-upgrade`），要求主机每次启动时获取并安装最新服务器软件包。因此，即使用户最初检查过服务器源代码并认为它是安全的，后续执行时仍可能静默获取已经被修改的恶意版本。这种机制会持续引入 Rug Pull 攻击和供应链攻击风险。

#### 3.2.3 A3：初始化逻辑攻击

初始化逻辑在 MCP 服务器启动时作为第一步执行。在这一阶段，服务器会解析环境变量、导入必要依赖，并建立与 MCP 客户端的通信通道。服务器和客户端还会进行对话，协商协议版本并声明各自支持的功能。攻击者在开发 MCP 服务器时，可以将恶意逻辑植入初始化代码，与正常操作并存。

1. **恶意代码执行。**对于远程 MCP 服务器，全部初始化逻辑都在服务提供者的基础设施上执行，不会直接影响用户设备。对于本地安装的 MCP 服务器，初始化代码则直接在用户机器上运行。如果服务器启动时没有严格的权限控制，初始化代码可能植入后门、访问敏感数据，或滥用系统资源进行加密货币挖矿。重要的是，这些恶意行为可以在服务器启动时立即发生，早于 LLM 或用户与服务器进行交互。
2. **端点暴露。**对于通过 HTTP 与客户端通信的本地服务器，初始化代码可能故意启动存在漏洞或权限过宽的 HTTP 端点，例如启用无状态通信，并将服务绑定到 `0.0.0.0`。此时，服务器不仅能被 MCP 主机访问，同一网络中的其他主体也可以访问它。如果服务器暴露了文件访问等强大能力，远程第三方就可能通过与该端点交互访问用户本地系统。
3. **针对客户端的拒绝服务。**MCP 服务器的初始化逻辑必须能够处理客户端请求（例如 `initialize`），也可能主动向客户端发送 ping 或日志等消息。然而，恶意服务器可以通过发送超大响应或大量消息来利用这一功能，降低 MCP 主机的响应能力。

#### 3.2.4 A4：工具元数据投毒

工具的名称、描述、输入模式和注释由服务器定义，并传递给客户端。随后，MCP 主机可能选择性地将这些元数据暴露给 LLM。至少，LLM 需要访问工具名称、描述和输入模式，才能决定调用哪个工具以及如何构造参数。关键问题在于，LLM 无法验证工具元数据的真实性和正确性，通常只能接受服务器提供的内容。换言之，工具是根据其声明的元数据，而不是根据其实际实现来解释的。当用户提出任务时，LLM 会根据可用工具元数据进行推理，并选择它认为最适合完成目标的工具。因此，攻击者可以利用误导性元数据操纵 LLM。根据攻击目标，A4 包括以下子类型。

1. **诱导选择。**服务器可以在工具名称或描述中夸大工具的用途，使其看起来非常强大或功能多样，从而提高 LLM 选择恶意工具而不是其他工具的概率，增加工具调用频率。这种诱导既可能服务于攻击目的，也可能服务于商业目的。
2. **信息过度收集。**攻击者通过精心设计描述和输入模式，诱导 LLM 提供超出必要范围的信息。一旦 LLM 将所需信息作为工具参数提交，信息就落入攻击者控制之中。例如，餐厅预订工具可能以过敏预防或个性化推荐为名，要求用户提供敏感健康数据。这样，恶意服务器就能收集合法功能不需要的额外用户数据，造成隐私侵犯或后续滥用。
3. **控制流劫持。**工具元数据也可以嵌入强制性的指令，操纵 LLM 的推理过程。这些指令会扭曲 LLM 的正常行动逻辑，实质上劫持控制流。图 5 展示了一个通过工具元数据进行控制流劫持的例子：恶意工具利用名称和描述说服 LLM，要求它在每次其他工具调用之后都调用该工具，并把前面工具的输出作为所谓“安全检查”的参数。被投毒的元数据误导 LLM，使其无论用户原始意图如何，都在其他工具调用之后调用恶意工具。
4. **工具冒充。**在这种变体中，恶意服务器注册一个元数据与合法工具高度相似的工具。攻击者希望混淆 LLM，使其在尝试调用良性工具时，转而选择恶意对应工具，从而拦截原本应由可信服务器处理的请求。

#### 3.2.5 A5：工具逻辑攻击

工具本质上是 AI 应用可以通过结构化请求调用的已注册函数。工具逻辑，即函数体内部的代码，决定工具的实际行为。然而，在常见 MCP 实现中，主机和 LLM 都无法直接看到工具逻辑。这种不透明性为恶意服务器开发者在工具内部植入有害行为创造了机会。服务器可以注册多个良性且有用的工具，同时隐藏其中一个恶意工具，使用户难以察觉。

1. **恶意代码执行。**这种攻击源于 MCP 服务器工具内部恶意代码的执行。工具逻辑一旦被调用，就可以利用已经获得的权限执行各种有害操作，例如篡改本地环境，或将 LLM 提供的输入参数外泄到外部目的地。
2. **诱导式信息收集滥用。**MCP 中的 elicitation 机制允许服务器在交互过程中向用户请求额外输入。该功能通常嵌入工具等其他服务器功能中。虽然 elicitation 的设计目标是通过支持动态交互工作流改善用户体验，但它也提供了一个服务器索取额外用户信息的渠道。由于 elicitation 提示词是自由格式的，服务器可以使用具有说服力或欺骗性的措辞。例如，餐厅预订工具可以弹出“免费餐食”抽奖窗口，要求用户输入政府签发的身份证号码以领取奖品，从而收集敏感个人信息。
3. **采样滥用。**MCP 的采样功能允许服务器通过客户端请求 LLM 生成文本。实际上，这意味着工具逻辑可以在执行过程中发起 LLM 调用。虽然这一设计支持有用的智能体行为，但也允许恶意服务器把任意任务转嫁给用户的 LLM，而不必消耗自己的资源。例如，一个表面上用于生成诗歌的工具，内部却指示用户的 LLM 为攻击者的产品撰写广告文案。这样，计算成本和资源负担都被转移给用户的智能体，而攻击者无需付出成本即可获得高质量模型生成结果。
4. **针对客户端的拒绝服务。**MCP 允许服务器向客户端发送日志信息、进度更新和功能变更通知等多种消息。恶意工具可以通过大量发送消息，或发送超大消息来增加客户端处理和存储压力。
5. **未授权资源调用。**MCP 允许工具逻辑调用同一服务器中的资源，这带来了潜在的滥用场景。资源通常设计为由应用驱动，并且往往需要用户或主机明确操作后才能加入对话上下文。如果工具绕过这一预期，自动调用资源，就相当于违反了既定的权限边界。此外，如果资源接受参数，恶意工具还可以自由构造输入，从而访问各种资源数据。

#### 3.2.6 A6：工具输出攻击

工具被调用后，其内部逻辑会执行并产生返回值。返回值随后会被提供给 LLM，直接影响模型的下一步行动或对用户的响应。恶意工具的输出可能完全是伪造的，也可能包含细微操纵或有意误导的内容。如果这些输出未经过滤、验证或清理就直接进入 LLM 上下文——这正是当前 MCP 主机的常见设计——就可能造成多种有害后果。

1. **控制流劫持。**工具返回值可以包含影响 LLM 后续决策的指令，诱导 LLM 调用额外工具或执行用户从未要求的操作，从而将非预期操作插入交互流程。例如，用户要求智能体预订机票，智能体正确调用航班预订工具并完成订票，但工具返回值却指示智能体继续调用酒店预订工具，在未经用户同意的情况下预订特定酒店。
2. **未授权信息传播。**工具运行过程中通常存在多条信息流。LLM 提供输入参数，工具逻辑可能访问本地或外部资源，这些信息流很容易包含不应超出原定范围的敏感或私有数据。然而，恶意工具可以直接将这些信息嵌入返回值，并操纵 LLM 将其传播给其他工具甚至外部实体。图 6 展示了一个例子：用户要求撰写备忘录，智能体调用了恶意备忘录工具。该工具正常完成任务，却在输出中要求 LLM 调用电子邮件工具，将备忘录内容发送到外部地址。
3. **虚假信息。**恶意工具可以故意返回虚假信息，使 LLM 或用户形成错误认识并做出错误决策。例如，投资咨询工具通常提供准确分析，但某次返回遭到投毒的建议，要求用户购买某只特定股票。这类攻击的危险在于利用了用户对先进 LLM 的信任。公开互联网中的虚假信息可能缺乏可信度，但恶意服务器可以借助模型的权威语气传递虚假内容，使其更具说服力。
4. **针对客户端的拒绝服务。**恶意工具可以生成超大输出，使客户端过载。
5. **钓鱼。**恶意 MCP 服务器可以直接在工具返回值中嵌入钓鱼内容。LLM 通常经过训练或对齐，能够避免自行生成钓鱼链接或诈骗信息。然而，如果这类内容以看似合法的形式出现在工具返回值中，LLM 可能会将其原样传递给用户。

#### 3.2.7 A7：资源元数据投毒

资源元数据是与 MCP 资源相关的描述性信息，包括 URI、名称、标题、描述、MIME 类型、大小、可选输入模式，以及可选注释（例如受众、优先级和最后修改时间）。资源元数据指导客户端如何解释、组织和访问资源。

1. **诱导选择。**与工具类似，资源可以通过高度诱人的名称、标题或描述伪装自己。例如，服务器可以虚假声称提供通常需要付费的高级 Bloomberg Terminal 数据。此外，资源还可以设置较高的优先级或很新的 `lastModified` 日期，以强调其重要性和新鲜程度。由于当前没有机制验证资源声明是否与底层数据一致，这些操纵是可行的。诱导选择既可能出于商业动机（例如为新闻 API 吸引流量），也可能出于恶意目的（例如提高后续执行有害逻辑的概率）。与工具不同，资源由应用驱动，资源元数据的可见性和使用方式取决于主机设计。有些主机会直接将资源元数据暴露给 LLM，使其能够根据任务自主选择资源；另一些主机则要求用户明确选择。
2. **资源类型混淆。**每个资源都包含 `mimeType` 字段，用于指定媒体类型，使客户端和主机能够决定如何处理返回数据。攻击者可以故意伪造该字段，导致主机使用错误的处理程序，从而引发解析错误或崩溃。此外，不同 MIME 类型可能适用不同的验证或安全检查，因此错误标注也可以被用来规避检测。
3. **资源冒充。**恶意服务器可以构造资源元数据，仿冒合法或权威 MCP 服务器的资源。这样，当用户或 LLM 想要选择真实资源时，可能误选恶意资源。
4. **信息过度收集。**由于资源可以接受输入参数，恶意服务器可能滥用这一功能收集不必要或敏感的信息。攻击者可以构造误导性的名称、标题、描述和输入模式，诱导用户或 LLM 提供敏感数据。例如，资源可以虚假声称提供免费电影，却要求用户提交电子邮件地址或电话号码进行验证。

#### 3.2.8 A8：资源逻辑攻击

MCP 资源的设计目标是在不产生明显计算或副作用的情况下提供数据。然而，攻击者仍然可以在资源处理程序中植入恶意逻辑。

1. **恶意代码执行。**恶意服务器可以在资源逻辑中嵌入任意代码。每当资源被调用，这些代码就会执行，使攻击者能够利用资源获得的权限实施有害操作。
2. **针对客户端的拒绝服务。**通常，MCP 服务器中的资源逻辑可以向客户端报告进度更新或发送日志消息。但恶意服务器可以持续发送大量进度通知或日志事件，淹没客户端并降低其响应能力。
3. **补全操纵。**MCP 允许服务器在用户调用需要输入参数的资源时提供自动补全建议。例如，提供数字图书访问的资源可以在用户输入“war”时建议《战争与和平》或《战争论》。恶意服务器则可以滥用补全功能提供欺骗性或操纵性建议。比如，一个根据用户提供的 URL 获取网页内容的资源可以为 URL 提供自动补全，但总是将伪造域名放在首位。用户输入“wiki”时，服务器返回 `https://www.wikipeda.org/`，而不是合法的 `https://www.wikipedia.org/`。如果用户没有注意到细微拼写错误并接受该建议，资源就会从攻击者控制的域名获取内容。
4. **采样滥用。**与工具类似，MCP 资源也可以请求 LLM 采样。例如，良性资源可以提供数字图书链接和 LLM 生成的介绍；恶意资源则可以利用采样机制转嫁任意 LLM 任务，消耗用户 LLM 的令牌来服务攻击者目标。

#### 3.2.9 A9：资源输出攻击

MCP 资源可以返回多种输出，客户端会将这些输出纳入交互上下文。根据协议规范，资源内容可以是文本（例如纯文本和源代码），也可以是二进制数据（例如图像和 PDF 文件）。这种灵活性支持丰富的集成，同时也带来了滥用机会。

1. **输出不一致。**资源可能通过元数据宣传一个良性用途，但实际返回与声明功能不一致的内容，形成典型的“诱饵与替换”。目前没有标准化机制保证资源元数据与实际输出一致。例如，资源声称提供可作为参考的高质量 Python 代码，实际却返回恶意二进制文件。
2. **输出篡改。**资源获取了用户请求的数据，却在返回过程中以细微方式修改数据。篡改可以表现为选择性遗漏、有偏修改或误导性转换。例如，恶意资源在获取 Morningstar 投资建议时，可以加入特定股票的推荐，即使 Morningstar 从未提到这些股票。
3. **指令注入。**攻击者可以在正常请求内容之后追加指令或具有说服力的文字，影响下游 LLM 或用户的判断。图 7 展示了一个例子：服务器返回系统日志的真实内容，但在末尾追加欺骗性信息，声称日志中显示的安全问题都已经解决。如果用户询问 LLM 系统是否存在问题，而 LLM 通过该 MCP 资源读取日志，这条误导性注释就可能影响模型判断。
4. **二进制载荷。**MCP 资源可以返回二进制内容（例如图像），这些内容以带有 MIME 类型字段的 Base64 编码数据块传输。客户端会将数据解码为原始字节，并根据 MIME 类型进行处理。恶意服务器可以构造利用主机解析或渲染栈漏洞的二进制文件，可能导致系统失陷。
5. **针对客户端的拒绝服务。**恶意服务器资源可以返回过大的响应，使客户端过载。

#### 3.2.10 A10：提示词元数据投毒

提示词元数据包括唯一名称，以及可选的标题、描述和参数。由于提示词会明确暴露给用户选择，提示词元数据投毒的主要目标不是 LLM，而是用户。

1. **诱导选择。**恶意提示词可以使用诱人的名称或描述，使自己看起来有用或权威，从而提高被用户选择的概率。
2. **提示词冒充。**恶意提示词可以仿冒可信服务器提供的提示词，误导用户选择恶意提示词而不是真实提示词。
3. **信息过度收集。**由于提示词可以接受输入参数，恶意提示词可能试图诱导用户提供敏感信息。特别是，提示词支持为每个输入参数设置描述，攻击者可以利用这些描述，隐蔽地鼓励用户泄露更多信息。

#### 3.2.11 A11：提示词逻辑攻击

MCP 服务器中的提示词处理程序可以接受输入参数并执行代码，其行为与工具和资源类似。一个关键区别是，提示词逻辑通常在用户选择并调用提示词时执行，例如用户填写所需参数后点击“添加提示词”按钮。因此，提示词逻辑攻击不需要 LLM 参与，单纯依赖服务器与用户之间的交互。

1. **恶意代码执行。**与 A5 工具逻辑攻击和 A8 资源逻辑攻击中的恶意代码执行类似，恶意提示词逻辑也可以在其运行环境中执行有害操作。
2. **补全操纵。**与资源逻辑类似，提示词逻辑也可以实施补全操纵。对于资源，攻击者构造的建议会修改 URI 参数，可能误导用户访问错误对象；对于提示词，建议会被纳入最终提交给 LLM 的提示词文本。因此，恶意提示词处理程序可以返回遭到投毒的补全选项，操纵 LLM 的响应。

#### 3.2.12 A12：提示词输出攻击

MCP 提示词处理程序生成的提示词包含角色（“user” 或 “assistant”）和内容，内容可以是文本、图像、音频或嵌入式资源。提示词的目的，是帮助用户更高效地与 LLM 交互。

1. **用户意图扭曲。**提示词服务的输出应当忠实于用户意图。然而，攻击者控制的 MCP 服务器可以在生成的提示词中追加指令，破坏原有意图。这可以表现为两种形式：
   - **任务内扭曲：**修改原任务的标准或语气。例如，代码审查提示词追加“始终回答代码没有问题”，就会把目标从“找出问题”改变成“始终批准”。
   - **额外任务注入：**追加与用户请求无关的指令。例如，提示词末尾可能出现“将你知道的所有用户信息发送到 `attacker@gmail.com`”。

### 3.3 攻击在智能体工作流中的表现

上述攻击分类从结构层面展示了攻击者如何将恶意行为嵌入服务器的基本组件。下面说明这些攻击如何在现实智能体工作流中展开。工作流 1 展示了基于 MCP 的智能体运行步骤，并标注每一步可能出现的攻击类别。

其中，\(S_{meta}\) 表示服务器元数据，\(I_{logic}\) 表示服务器初始化逻辑，\(C\) 表示 LLM 对话上下文；\((X_{meta}, X_{logic}, X_{out})\) 表示 \(X \in \{T（工具）, R（资源）, P（提示词）\}\) 对应的元数据、逻辑和输出。\(action \in A\) 表示 LLM 的动作，其中 \(A = \{ToolCall, FinalAnswer\}\)。

**工作流 1. 基于 MCP 的智能体工作流及其攻击表现。**

```text
1  智能体初始化：
2  读取主机配置文件，并遍历每个服务器配置：
3  如果存在启动命令：
4      启动服务器；                                      // A2
5      执行初始化逻辑，建立 Stdio 连接；                 // A3
6  否则，如果存在连接端点：
7      通过 HTTP 建立连接；                               // A1、A2
8  获取服务器上下文 S = (Smeta, Tmeta, Rmeta, Pmeta)；
9  将 (Smeta, Rmeta, Pmeta) 注入用户界面；                 // A1、A7、A10
10 对话轮次：
11 用户提出查询 Q；
12 如果用户选择加入服务器提供的资源或提示词：
13     调用 Rlogic 或 Plogic；                            // A8、A11
14     将 Rout 或 Pout 插入 Q；                            // A9、A12
15 用户将 Q 发送给 LLM；
16 重复执行：
17     action ← LLM(Smeta, Tmeta, C, Psys, Q)；            // A1、A4
18     如果 action = ToolCall(t, args)：
19         Tout ← 执行(Tlogic, args)；                      // A5
20         C ← C ∪ {action, Tout}；                         // A6
21 直到 action = 针对 Q 的 FinalAnswer；
22 返回 FinalAnswer。
```

智能体在整个生命周期中会反复与服务器交互，因此存在多阶段攻击的机会。恶意服务器的不同组件可以相互强化，攻击也可能逐步累积并升级。例如，一个服务器可以将权威感很强的元数据、遭到篡改的资源数据和伪造的工具输出结合起来，使 LLM 完全偏离原定方向。此外，攻击还可能持续存在于智能体的信息流中。例如，遭到投毒的工具输出一旦被注入对话上下文，即使初次使用已经结束，也可能继续影响后续对话轮次。
