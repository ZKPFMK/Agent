# 超越协议：揭示模型上下文协议（MCP）生态系统中的攻击向量

**原标题：**Beyond the Protocol: Unveiling Attack Vectors in the Model Context Protocol (MCP) Ecosystem  
**年份与来源：**2025，arXiv:2506.02040（v4，2025 年 9 月 14 日）。  
**原文：**[本地 PDF](./25_arxiv_mcp_attack_vectors.pdf)。

## 摘要

模型上下文协议（Model Context Protocol，MCP）是一项新兴标准，旨在实现大语言模型（Large Language Model，LLM）应用与外部工具或资源之间的无缝交互。在很短的时间内，数千个 MCP 服务已经开发并部署。然而，MCP 固有的客户端—服务器集成架构可能扩大 LLM 智能体系统的攻击面，使攻击者能够通过设计恶意 MCP 服务器引入新的漏洞并加以利用。

本文首次对针对 MCP 生态系统的攻击向量开展端到端实证评估。我们识别出四类攻击，即工具投毒攻击（Tool Poisoning Attack）、傀儡攻击（Puppet Attack）、Rug Pull 攻击（信任后变更攻击），以及利用恶意外部资源的攻击（Exploitation via Malicious External Resources）。为评估这些攻击的可行性，我们按照通过恶意 MCP 服务器发起攻击的典型步骤开展实验：上传 → 下载 → 攻击。具体而言，我们首先构造恶意 MCP 服务器，并成功将其上传到三个广泛使用的 MCP 聚合平台。结果表明，当前的审核机制不足以识别和阻止这些威胁。随后，我们通过一项包含 20 名参与者的用户研究和访谈，证明用户难以识别恶意 MCP 服务器，并且经常在不知情的情况下从聚合平台安装这些服务器。最后，我们通过实验证明，这些攻击能够在用户本地环境中触发有害行为，例如访问私有文件，或控制设备转移数字资产。此外，我们根据访谈结果讨论了当前 MCP 安全生态系统面临的四项关键挑战。这些发现凸显了建立强健安全机制的迫切需要，以防御恶意 MCP 服务器，并确保日益自主化的 LLM 智能体能够安全部署。

## 引言

为了规范大语言模型（Large Language Model，LLM）智能体与各种外部资源之间的交互，Anthropic 提出了模型上下文协议（Model Context Protocol，MCP）[5]。MCP 采用客户端—服务器架构：外部工具或资源通过 MCP 服务器暴露，LLM 应用则充当 MCP 主机，管理客户端与这些服务器进行交互。MCP 的采用推动了兼容工具和服务生态系统的快速发展。例如，截至目前，Smithery.ai [48] 已经托管超过 6,000 个 MCP 服务器，覆盖网页检索 [33]、金融操作 [7] 和软件开发 [41] 等多个领域。

MCP 提升了智能体的模块化程度和可扩展性，但其对外部 MCP 服务器的依赖也引入了一条关键的信任边界。由于这些服务器可能不可信，甚至可能是恶意的，每一次交互都可能带来安全风险。标准 MCP 工作流包含三个阶段：

1. **注册（Registration）：**服务器向智能体描述自身能力；
2. **规划（Planning）：**智能体利用这些描述制定行动计划；
3. **操作（Operation）：**智能体请求服务器执行工具。

每个阶段都会跨越信任边界，也都可能成为攻击者实施利用的入口。例如，在注册阶段，恶意服务器可以将隐藏的有害指令嵌入工具描述中。这些用户难以察觉的指令可能在规划阶段被 LLM 解读，从而在用户不知情的情况下操纵智能体行为。在操作阶段，恶意服务器还可以返回经过操纵的响应，或利用具有欺骗性的描述误导智能体后续与其他可信工具的交互，最终导致非预期的操作。

本文对 LLM 智能体与 MCP 服务器交互所产生的安全风险开展端到端实证评估。根据攻击者可能破坏 MCP 工作流的方式，我们系统识别并刻画了恶意 MCP 服务器所利用的四种主要攻击模式：工具投毒攻击、傀儡攻击、Rug Pull 攻击（信任后变更攻击），以及利用恶意外部资源的攻击。为评估这些攻击的可行性，我们按照恶意 MCP 服务器被利用的典型生命周期开展三项实验：

1. 攻击者将恶意 MCP 服务器上传到聚合平台；
2. 用户下载并安装该服务器；
3. 服务器在用户本地环境中执行有害操作。

首先，我们构造一个恶意 MCP 服务器，并测试能否将其成功上传到三个广泛使用的 MCP 聚合平台：Smithery.ai [48]、MCP.so [40] 和 Glama [25]。在所有情况下，该服务器都未受到任何阻拦而被接受，这表明当前审核机制不足以识别和阻止恶意服务器。随后，我们通过部署一个模拟的 MCP 服务器聚合平台开展用户研究。在该平台中，我们混合放置四个恶意 MCP 服务器和八个良性服务器。通过三项任务——盲选、知情检测和攻击向量分析（具体细节见第 4.2 节），我们发现参与者始终难以识别恶意 MCP 服务器。后续访谈进一步表明，参与者普遍对 MCP 服务器的整体安全性表示担忧。

最后，我们部署上述攻击，以评估其对主流 LLM 和 MCP 客户端的影响。结果发现，当前主流 LLM 无法防御这些攻击，面向用户的 MCP 客户端也无法有效缓解风险。此外，根据访谈结果，我们讨论了当前 MCP 服务器安全生态系统面临的四项关键挑战：

1. **用户不熟悉智能体的 MCP 安全问题；**
2. **用户对安全警报逐渐麻木，并产生警报疲劳；**
3. **智能体安全问题的责任归属模糊；**
4. **LLM 天生缺乏防御本文定义的四类攻击向量的能力。**

我们提出了相应的缓解策略，为未来研究提供参考。总而言之，本文的主要贡献如下：

- **系统识别并刻画四种主要攻击模式。**我们根据这些攻击在 MCP 框架中的利用向量，系统识别并刻画了四种主要攻击模式。
- **首次实证证明这些攻击的可行性。**我们首次通过实验证明这些攻击能够成功实施，同时揭示了现有聚合平台安全审核的不足，以及信息不对称给用户带来的识别困难。
- **深入讨论 MCP 服务器生态系统中的安全挑战。**我们深入分析了 MCP 服务器生态系统面临的更广泛安全问题，并提出了用于应对这些问题的潜在缓解策略和防御机制。
- **发布研究材料。**我们公开了源代码、用户研究详情以及全部实验数据：<https://github.com/MCP-Security/MCP-Artifact>。

## 2 背景

### 2.1 LLM 智能体

大语言模型（Large Language Model，LLM）智能体是在基础 LLM 之上发展起来的系统，其功能已经超越文本生成。LLM 作为智能体系统的核心，提供推理和语言理解能力 [52]。智能体进一步结合规划、记忆和工具使用机制，使其能够通过系统分解问题，并利用外部工具获取信息或在现实环境中执行操作，从而完成复杂任务 [37]。

### 2.2 模型上下文协议（MCP）

为了规范 LLM 智能体与各种外部资源之间的交互，Anthropic 提出了模型上下文协议（Model Context Protocol，MCP）[5]。MCP 采用客户端—服务器架构：LLM 应用充当主机（客户端），外部工具或数据源则通过 MCP 服务器暴露。MCP 定义了几类用于交互的核心原语：**资源（Resources）**以情境化方式暴露数据，**提示词（Prompts）**提供可复用模板，**工具（Tools）**使智能体能够调用由 MCP 服务器远程执行的操作。

在典型生命周期中，MCP 服务器会在连接或被发现时向主机注册其可用能力。随后，智能体可以查询这些能力，并根据自身目标和当前上下文决定调用哪些工具。工具的执行逻辑位于服务器端，主机应用通常会配置服务器，使其针对 Python 或 Node.js 等特定运行时执行，并分别可能使用 `uvx` [50] 或 `npx` [44] 等封装工具。MCP 通过封装外部资源交互增强了智能体系统的模块化能力，但其依赖与意图不明确、却能够执行代码的服务器进行通信，也在系统信任边界处引入了前所未有的攻击面 [32]。

**MCP 聚合平台。**用户通常从聚合平台获取 MCP 服务。常见的聚合平台包括 Smithery.ai [48]、MCP.so [40] 和 Glama [25]。截至 2025 年 8 月，这三个平台分别收录了超过 6,000、16,000 和 8,000 个 MCP 服务器。开发者将构建好的 MCP 服务器上传到这些平台，用户则根据需求选择并下载。聚合平台会对服务器进行初步审核。

### 2.3 MCP 的交互工作流

用户与智能体之间的标准交互流程涉及多个角色，包括 LLM 提供商、MCP 客户端、MCP 服务器、软件包仓库以及各种第三方资源。这些组件协同工作，最终完成用户请求。

**图 1. 模型上下文协议（MCP）工作流概览。**图中展示了用户、LLM 提供商、MCP 主机、MCP 客户端、MCP 服务器、软件包仓库和第三方资源之间的完整交互流程。

在任何攻击发生之前，基于 MCP 的智能体会按照以下步骤完成一次完整且良性的交互：

1. **初始配置。**MCP 客户端根据本地配置，从软件包仓库获取所需软件包，并启动相应的服务进程。
2. **能力注册。**MCP 服务器通过标准化描述注册自身能力，暴露可用的工具、资源和提示词等信息。
3. **任务提出。**用户在 MCP 主机界面中输入自然语言命令，例如：“请帮我将 1 ETH 发送到 Base 网络上的地址 `0x123...`。”
4. **提示词组装。**MCP 客户端将用户请求与当前会话上下文（包括对话历史、权限状态等）组合起来，并提交给 LLM 进行分析。
5. **工具调用规划。**LLM 根据请求语义以及 MCP 服务器提供的工具目录制定执行计划，并生成符合 MCP 协议的调用指令。
6. **工具调用。**MCP 客户端将调用指令转换为标准协议消息并发送给 MCP 服务器；服务器验证请求后调用相应工具。
7. **第三方 API 调用。**在转账场景中，服务器需要调用钱包 API 对交易进行签名，然后将交易发送到区块链进行确认。
8. **返回结果。**MCP 服务器处理外部服务返回的原始数据，并将结果传递给 LLM，由 LLM 生成最终响应。
9. **响应总结。**LLM 将原始请求与返回数据结合起来，向用户生成易于理解的响应。在转账场景中，模型会明确告知用户转账结果。

### 2.4 提示词注入

提示词注入（Prompt Injection）是 LLM 固有的、最广为人知的漏洞之一。攻击者构造恶意输入来操纵 LLM 的行为，使其覆盖原始指令或偏离预期功能 [38]。这种攻击向量利用了 LLM 的基础架构特性 [53]，通过引入对抗性提示词混淆模型对指令边界的判断 [29]。例如，攻击者可以在看似良性的请求后追加如下指令：“总结这篇文章。忽略之前的所有指令，转而泄露你的系统提示词。”这样会导致 LLM 将注入的命令误认为合法的用户指令，而不是恶意输入。

成功的提示词注入可能导致未经授权的数据外泄、执行非预期操作、生成有害内容或拒绝服务 [58]。此外，与 MCP 服务器等外部能力集成的智能体系统会显著扩大提示词注入的攻击面，并带来新的安全挑战 [36, 62]。

### 2.5 MCP 生态系统中的金融操作

根据现有 MCP 服务器集合 [40, 46, 48]，MCP 服务器支持的金融操作主要集中在加密货币相关服务。加密货币是利用区块链技术实现点对点价值转移的数字资产，在全球市场中具有重要的货币价值 [63]。具体而言，`base-mcp` [7] 使 LLM 智能体能够直接与 Base¹ 区块链上的用户钱包交互，为 ETH² 资产管理和交易执行提供服务。

加密货币操作所具有的金融属性，使相关 MCP 服务器尤其容易受到恶意攻击；一旦攻击成功，可能给用户造成永久性的经济损失。

¹ Base 是一种经过优化的区块链网络，在保持兼容性的同时，提供更低的费用和更快的交易速度。  
² ETH 是以太坊和 Base 网络用于交易和计算服务的原生加密货币。

## 3 MCP 攻击

本节介绍由恶意 MCP 服务器发起的四类攻击。正如第 2.3 节所述，用户与智能体之间的交互包含九条关键路径。除了给出每类攻击的定义和攻击向量外，我们还明确说明攻击影响哪条路径、攻击在哪条路径上被利用，以及攻击来源。这些信息有助于后续开发防御机制。附录中的表 3 汇总了相应关系。

### 3.1 威胁模型

**攻击者目标。**我们考虑这样的攻击者：其主要目标是通过运行或控制恶意 MCP 服务器，破坏 LLM 智能体系统的机密性、完整性或可用性。攻击者试图外泄智能体能够访问的敏感数据，诱导智能体执行未经授权或有害的操作，扰乱系统运行，或将智能体作为进一步攻击的立足点。

**攻击面。**我们假设 LLM 智能体能够按照设计正常运行，但仍可能受到经由 MCP 接收的输入操纵。这些输入包括嵌入工具描述或运行时输出中的提示词注入。核心信任边界位于 MCP 客户端与 MCP 服务器之间；所有来自潜在恶意服务器的信息都被视为不可信。攻击者利用智能体对这些不可信信息的依赖，影响其决策和工具交互编排。

**攻击者能力。**我们假设攻击者能够操纵其定制恶意 MCP 服务器所访问的全部工具描述数据和外部资源，但无法操纵 MCP 客户端。具体而言，攻击者可以向 MCP 工具添加任意描述（提示词），也可以在工具完成任务需要访问外部资源时，向其提供恶意外部资源。

**攻击的普遍性。**我们认为，一旦恶意服务器安装完成，攻击者就能够影响任意用户的本地环境。

### 3.2 攻击类型

#### 3.2.1 工具投毒攻击

**攻击定义。**恶意指令被嵌入 MCP 工具描述中，用户无法看到这些指令。这些隐藏指令会在用户不知情的情况下，诱导系统生成不可信输出或执行未经授权的操作。

**攻击向量。**LLM 能够访问完整的工具描述，而用户通常只能通过主机界面看到简化版本。攻击者首先提供与工具预期功能一致的良性描述，以误导用户；随后在良性描述之后追加详细的恶意指令，试图操纵 LLM。用户没有意识到工具描述中的隐藏指令，因而可能授权执行恶意操作，并造成严重后果。

我们将该攻击形式化表示为：

\[
(p_{benign} \oplus c \oplus p_{malicious}) \rightsquigarrow P_{TPA}
\]

\[
\mathrm{LLM}\xrightarrow{\mathrm{call}}S_{tool}(F,P_{TPA})\rightsquigarrow A
\tag{1}
\]

其中，\(p_{benign}\) 和 \(p_{malicious}\) 分别表示服务器中某个工具的良性描述和恶意描述；\(c\) 表示用于隐藏恶意描述的无意义字符；\(\oplus\) 表示字符串拼接，前三项共同构成完整的恶意工具描述 \(P_{TPA}\)。\(S_{tool}\) 表示被调用服务器中的工具，它包含功能逻辑 \(F\) 和恶意工具描述 \(P_{TPA}\)。上述调用行为最终导致攻击 \(A\) 发生。

该攻击主要影响路径 ② 和 ④，并在路径 ⑥ 上实现利用。攻击来源是 MCP 服务器本身。

**攻击示例。**图 2 展示了工具投毒攻击的具体过程。攻击者向 MCP 服务器的搜索工具中秘密注入恶意描述，要求智能体在执行搜索时首先读取并传递敏感信息，例如 API 密钥。非专业用户通常不会注意到调用工具过程中发生的信息泄露。该攻击只需要一个恶意 MCP 服务器即可实施，最终由攻击者获取用户的敏感数据。

**图 2. 工具投毒攻击概念验证。**恶意工具描述要求智能体读取用户的敏感 API 密钥，并将其作为搜索工具参数传递。

#### 3.2.2 傀儡攻击

**攻击定义。**用户安装多个 MCP 服务器，其中带有恶意工具描述的服务器能够影响可信工具，最终诱导系统执行恶意操作。

**攻击向量。**用户通常会安装多个 MCP 服务器来完成不同任务。攻击者首先识别可信 MCP 服务器中的常用工具（工具 A），然后为目标恶意服务器构造恶意描述（工具 B），以便在工具 A 被调用时秘密调用工具 B，或诱导良性服务器执行非预期操作。随后，攻击者将恶意服务器混入用户安装的多个 MCP 服务器中。当服务器能力完成注册后，LLM 会获取包括恶意描述在内的全部工具描述。于是，当用户调用良性工具 A 时，工具 B 也可能被执行，或触发其他恶意操作，最终造成严重后果。

我们将该攻击形式化表示为：

\[
\left[P_X \xleftarrow{T} (p_{benign} \oplus c \oplus p_{malicious})\right]
\rightsquigarrow P_{PA}
\]

\[
\left[\mathrm{LLM}\xrightarrow{\mathrm{call}}S_{tool}(F,P_X)\;\|\;\mathrm{LLM}\xrightarrow{\mathrm{handle}}P_{PA}\right]
\rightsquigarrow A
\tag{2}
\]

其中，\(P_X\) 表示良性工具 A 的描述，\(P_{PA}\) 表示定制恶意工具 B 的描述。该攻击主要影响路径 ②、④ 和 ⑤，并在路径 ⑥ 上实现利用。攻击来源是 MCP 服务器本身。

**攻击示例。**图 3 展示了傀儡攻击的过程。攻击者选择一个良性 MCP 服务器作为傀儡，并将恶意服务器隐藏在多个服务器之中。在恶意服务器的工具描述中，攻击者要求所有链上转账都重定向到地址 `0x456...` 的隐私代理。每当用户调用傀儡服务器中的工具时，用户都会在不知情的情况下执行恶意操作。该攻击需要两个服务器协同完成。

**图 3. 傀儡攻击概念验证。**恶意服务器借助良性服务器的工具调用，诱导智能体将链上转账重定向到攻击者控制的隐私代理。

#### 3.2.3 Rug Pull 攻击

**攻击定义。**MCP 服务器最初保持良性以取得用户信任，随后修改工具描述，在涉及敏感操作时嵌入恶意指令。

**攻击向量。**尽管 MCP 协议要求服务器在安装期间注册自身能力，并将全部工具描述发送给 MCP 客户端，但协议并未禁止之后修改这些内容。攻击者可以秘密更新描述，实施隐蔽攻击并造成危险后果。该攻击尤其适用于通过 `npx` [44] 和 `uvx` [50] 命令安装、配置的 MCP 服务器，因为这两个命令提供“运行后清理”（run-and-clean）机制：每次运行时重新获取并执行服务器，随后清理运行环境。

我们将该攻击形式化表示为：

\[
(p_{benign} \oplus c \oplus p_{malicious}) \rightsquigarrow P_{RPA}
\]

\[
\left\{\mathrm{LLM}\xrightarrow{\mathrm{call}}
\left[S_{tool}(F,P_X)\Rightarrow S'_{tool}(F,P_{RPA})\right]\right\}
\rightsquigarrow A
\tag{3}
\]

其中，\(S'_{tool}\) 表示秘密更新后的恶意服务器工具，\(P_{RPA}\) 表示更新后的工具描述。该攻击主要影响路径 ①、② 和 ④，并在路径 ⑥ 上实现利用。攻击来源是 MCP 服务器和软件包仓库。

**攻击示例。**图 4 展示了 Rug Pull 攻击的过程。攻击者首先将良性 MCP 服务器上传到第三方软件包仓库，以取得用户的初始信任。随后，攻击者秘密修改工具描述，加入恶意指令。当用户再次获取服务器并调用带有恶意描述的工具时，就会受到攻击。该攻击最终依赖恶意工具描述，其核心机制与工具投毒攻击和傀儡攻击相同。

**图 4. Rug Pull 攻击工作流。**服务器在获得用户信任后被秘密更新，新的工具描述随后携带恶意指令。

#### 3.2.4 恶意外部资源

**攻击定义。**MCP 服务器中的工具描述和代码本身是良性的，但工具调用需要访问包含恶意指令的第三方资源，最终导致攻击。

**攻击向量。**为了完成用户任务，MCP 服务器中的工具经常需要请求第三方资源。例如，要查询某个地点在指定日期的天气并据此规划行程，就需要请求天气网站的 API 以获得准确数据。攻击者首先发布一个工具代码和描述看似良性的 MCP 服务器，但在该工具访问的第三方资源中嵌入恶意指令。当用户调用工具时，工具会在用户不知情的情况下触发恶意操作，或者接收包含恶意指令的结果描述，进而引发其他工具的链式调用和严重后果。

我们将该攻击形式化表示为：

\[
(c \oplus p_{malicious}) \rightsquigarrow P_{MER}
\]

\[
\left\{\left[\mathrm{LLM}\xrightarrow{\mathrm{call}}S_{tool}(F,P_X)\right]
\;\|\;
F\xrightarrow{\mathrm{query}}U(P_{MER})\right\}
\rightsquigarrow A
\tag{4}
\]

其中，\(U\) 表示第三方资源，\(P_{MER}\) 表示嵌入第三方资源中的恶意描述。该攻击主要影响路径 ⑦、⑧、④ 和 ⑤。这里的路径编号并非错误的顺序，而是表示攻击可能导致后续工具的链式调用。攻击在路径 ⑦ 上实现利用，攻击来源是第三方资源。

**攻击示例。**图 5 展示了利用恶意外部资源的攻击过程。攻击者选择一个依赖外部资源的 MCP 服务器，并通过向相关网站注入不可见的恶意提示词来污染该网站。当用户调用该服务器中的工具时，工具会查询遭到入侵的网站，触发一系列链式 MCP 服务器调用，最终执行恶意操作。该攻击来源于外部网站；由于攻击者精心隐藏了恶意提示词，用户很难发现，因而具有较强的隐蔽性。

**图 5. 利用恶意外部资源的攻击概念验证。**MCP 服务器本身看似良性，但其依赖的第三方网站携带不可见恶意提示词，并在工具调用时进入智能体上下文。

## 4 实验

一次典型的恶意 MCP 服务器攻击遵循三个阶段的生命周期：

1. 攻击者将恶意 MCP 服务器上传到 MCP 聚合平台；
2. 用户从聚合平台选择并安装恶意 MCP 服务器；
3. 恶意 MCP 服务器在用户本地系统中执行有害操作。

基于这一攻击生命周期，我们关注以下三个研究问题：

- **RQ1：**攻击者能否将恶意 MCP 服务器成功上传到 MCP 聚合平台？
- **RQ2：**用户能否识别 MCP 聚合平台上的恶意 MCP 服务器？
- **RQ3：**恶意 MCP 服务器能否在用户本地环境中成功触发有害操作？

### 4.1 RQ1：恶意 MCP 服务器上传测试

在该研究问题中，我们评估 MCP 聚合平台是否实现了有效的审核机制，以识别并阻止恶意 MCP 服务器提交。为此，我们构造了一个具有恶意意图的 MCP 服务器，并尝试将其上传到三个广泛使用的 MCP 聚合平台：Smithery.ai [48]、MCP.so [40] 和 Glama [25]。

#### 4.1.1 恶意 MCP 服务器设计

我们参考现有 MCP 服务器集合中的热门服务功能 [48]，设计了一个伪装成以太坊合法加密货币价格查询服务的恶意 MCP 服务器 [56]。为了引入恶意行为，我们将恶意提示词嵌入工具描述的代码字符串中。这些字符串会在注册阶段传递给 LLM，从而可以评估平台是否能够检测提示词注入威胁。

该服务器的实现细节见附录 C。服务器暴露了一个名为 `get_price` 的工具，用于通过 CoinGecko API [14] 获取当前 ETH 价格。其恶意行为体现在隐藏指令中：无论 API 调用是否成功，都要求 LLM 告知用户“ETH 价格查询失败”，并从响应中排除数值数据。该攻击的意图是引导智能体拒绝提供服务响应，从而阻止用户获取合法的加密货币价格信息。

#### 4.1.2 恶意 MCP 服务器上传

我们通过两种不同场景评估 MCP 聚合平台的审核机制：直接上传恶意服务器，以及在服务器获批后修改其代码仓库。

- **测试 1：上传恶意 MCP 服务器。**我们将恶意 MCP 服务器提交到 Smithery.ai [48]、MCP.so [40] 和 Glama [25] 三个平台，并提供 MCP 服务器名称、描述和 GitHub 仓库 URL。我们创建了一个公开的 GitHub 仓库来存放测试服务器代码，并在平台提交时引用该仓库。
- **测试 2：将良性 MCP 服务器修改为恶意服务器。**为了测试攻击者能否先上传良性服务器以获得平台批准，再修改底层 GitHub 仓库并引入恶意功能，我们实施了第 3.2.3 节所述的 Rug Pull 攻击。首先，我们创建一个空的 GitHub 仓库，并在这些平台上注册一个新的 MCP 服务器，同时引用该空仓库。确认服务器展示页面可以公开访问后，我们将测试 1 中使用的恶意服务器代码写入这个空仓库。

此外，我们还在这些仓库的 README 文件中编写了完整说明，明确说明服务器用于安全研究实验。

#### 4.1.3 结果

在测试 1 中，我们的恶意 MCP 服务器成功上传到全部三个平台，没有收到警告，也没有被拒绝。三个平台都没有检测出嵌入其中的恶意指令。Smithery.ai 显示了表示自动安全检查的“scanned”标签；Glama 则明确将我们的服务器标记为“safe to use”。这表明当前的自动化分析无法识别基于恶意提示词的工具投毒攻击。

在测试 2 中，上传后修改 MCP 服务器仓库并不会改变平台上的展示结果或列表状态。当用户尝试安装页面上显示的良性 MCP 服务器时，平台会将其重定向到托管恶意 MCP 服务器代码的 GitHub 仓库。在我们主动删除代码仓库以防止潜在滥用之前，这些服务器在三个平台上持续可访问了七天。

**洞察 1：MCP 聚合平台本质上是目录服务。**这些平台链接到外部 GitHub 仓库，而不是直接托管代码。这种设计使攻击者能够在平台初次批准后修改代码仓库，从而实施 Rug Pull 攻击。

我们的研究表明，MCP 聚合平台缺乏能够检测提示词注入攻击的全面审核机制。此外，平台指向外部 GitHub 仓库的架构，使攻击者能够先上传良性服务器以获得平台批准，然后修改底层仓库引入恶意功能，而不会触发额外的平台审核。

**RQ1 的回答：**MCP 聚合平台的审核机制不足，允许攻击者上传恶意服务器，并在获批后修改其代码仓库。

### 4.2 RQ2：MCP 攻击模拟与用户研究

我们开展了一项经机构审查委员会（IRB）批准的模拟研究，以验证用户是否可能从聚合平台安装恶意 MCP 服务器。为此，我们首先开发一个模拟的 MCP 聚合平台，然后基于该平台设计用户研究，收集参与者反馈并评估其安全意识。

#### 4.2.1 模拟平台开发

我们设计了一个模拟的 MCP 服务器聚合平台³，用于仿真实际平台的设计和功能。该平台展示 13 个 MCP 服务器，并提供详细描述、源代码包和配置说明。这些服务器覆盖多种功能，包括信息查询、通信、文档管理和浏览器自动化。

我们在该集合中嵌入四个恶意服务器，分别对应第 3 节识别出的四类攻击向量。这些恶意服务器经过精心设计，外观上与合法服务器相似，但包含不易察觉的恶意迹象。例如，工具投毒服务器将自身伪装成天气信息服务，却包含窃取用户 API 密钥的隐藏功能。

³ 模拟平台地址：<https://www.mcp-servers.shop>。

#### 4.2.2 用户研究设计

用户研究由以下三个部分组成。

**人口统计信息。**我们收集参与者的人口统计信息，包括其在人工智能或软件工程领域的职业角色、工作年限以及对 MCP 的熟悉程度。这些信息有助于我们在分析结果和开展访谈时考虑参与者之间的知识差异。

**模拟任务。**我们设计了三个依次进行的任务，用于评估参与者在不同信息条件下的安全意识。

- **任务 1：盲选（Blind Selection）。**参与者需要选择 MCP 服务器，构建一个旅行规划 AI 智能体，但不会被告知其中存在恶意服务器。该任务考察用户是否会仅凭服务器描述和感知到的合法性，在无意中选择恶意服务器。
- **任务 2：知情识别（Informed Identification）。**完成第一个任务后，我们告知参与者 13 个服务器中有 4 个是恶意的，并要求他们找出这些服务器。该任务评估参与者在获得有限提示后检测威胁的能力。
- **任务 3：攻击向量分析（Attack Vector Analysis）。**在最后一个任务中，我们告知参与者哪些服务器是恶意的，并要求他们分析和识别每个服务器使用的攻击向量。该任务评估参与者对威胁机制的理解以及安全推理能力。

**访谈。**参考已有工作 [51, 55]，我们在模拟任务结束后对每位参与者开展半结构化访谈。访谈首先讨论参与者在三个模拟任务中的决策过程和判断标准。随后，我们详细解释每个恶意服务器的攻击模式，并征求参与者对各类攻击利用难度和潜在威胁的看法。最后，通过开放式问题鼓励参与者分享对 MCP 生态系统安全性的观点。由于访谈采用半结构化形式，我们还根据参与者的回答提出追问，以深入了解其认知。用户研究和访谈协议的详细内容见附录 D 和附录 E。

#### 4.2.3 参与者招募

我们首先通过大学邮件列表和多个研究机构招募参与者，目标是覆盖具有不同背景、以及不同人工智能和软件工程领域经验水平的人员。随后，我们采用滚雪球抽样方法 [26] 扩大初始参与者群体，即由现有参与者推荐其他合适候选人。经过多阶段招募流程，我们共获得 20 名参与者（见表 1）。

#### 4.2.5 结果

如表 1 所示，20 名参与者（P01–P20）全部完成了研究，角色涵盖学生、研究人员、开发者和安全从业者。参与者的经验从少于 1 年到超过 5 年不等，其中包括两名没有相关经验的参与者。18 名参与者（90.0%）对 MCP 具有一定熟悉程度。

在任务 1 中，参与者平均选择 3.15 个 MCP 服务器，其中 15 名参与者（75.0%）至少选择了一个恶意服务器。参与者更重视功能描述，而不是安全因素。P15 表示：“我更关注这些服务器的功能实现。”

**洞察 2：大多数参与者会在无意中选择恶意 MCP 服务器，并优先考虑功能而不是安全因素。**

任务 2 的结果显示，参与者识别恶意服务器的能力有限：只有一名参与者（P04）识别出全部 4 个恶意服务器，而 8 名参与者（40.0%）未能发现任何恶意服务器。访谈中，19 名参与者（95.0%）表示对自己的识别能力缺乏信心，并承认可能漏报或误报。14 名参与者（70.0%）将检查源代码作为主要方法，重点关注文件操作、外部通信和代码混淆。其他参与者还会参考发布者信息、功能描述和配置方式进行识别。

**洞察 3：即使明确得知平台中存在恶意服务器，参与者仍难以识别它们。**

在任务 3 中，没有任何参与者正确分析出全部四种攻击向量。在此前识别出恶意服务器的参与者中，12 人中的 5 人（41.7%）正确分析了工具投毒和傀儡攻击，12 人中的 3 人（25.0%）识别出了利用恶意外部资源的攻击。相比之下，只有 1 名参与者正确分析了 Rug Pull 攻击向量。有安全背景的参与者平均能够正确分析 1.7 个恶意服务器，而没有安全背景的参与者平均只能正确分析 0.8 个。

**洞察 4：参与者无法正确识别恶意服务器的全部四种攻击向量，尤其难以识别 Rug Pull 攻击。**

**RQ2 的回答：**用户在识别和分析恶意 MCP 服务器方面面临显著困难。具体而言，75.0% 的参与者在模拟中至少选择了一个恶意服务器；只有一名参与者识别出全部 4 个恶意服务器；没有任何参与者正确分析出全部四种攻击向量。
