## 摘要

大语言模型（LLM）正越来越多地负责模型上下文协议（Model Context Protocol，MCP）系统中的工具调用。在这类系统中，对抗性影响可能通过用户指令、工具模式、工具输出或协议消息进入。现有基准通常评估已经部署的智能体，因而将模型自身的易感性与安全护栏、编排机制及一般任务能力混杂在一起。我们提出 **COPEX**（**CO**ntext **P**rovider **EX**ploitation，上下文提供方利用），这是一个受控基准：固定周边智能体栈，仅改变负责工具选择的模型，从而隔离模型作为 MCP 客户端时的行为。COPEX 覆盖 25 类攻击，将其实例化为 125 个场景，涉及四种攻击入口面：模型/智能体、客户端、服务器/工具和传输层。在 9 个模型和 3,375 次试验中，平均攻击成功率为 64.4%，各入口面的平均值介于 58.3% 和 71.4% 之间。一些客户端层和传输层攻击部分或完全发生在模型的观测范围或控制能力之外，从而可以区分系统暴露程度与模型易感性。在包含 8 类攻击的防御子集上，与无防御设置相比，联合输入扫描和上下文扫描使平均攻击成功率降低了 48.8%。该基准已发布于 <https://github.com/inspire-center/copex>。

## 1 引言

大语言模型（LLM）正越来越多地通过工具调用接口执行操作。模型上下文协议（Model Context Protocol，MCP）（Anthropic，2024a）提供了一种将模型连接到外部工具和数据的标准化方式。在支持 MCP 的智能体中，模型并非只依据用户指令行动。它的决策还依赖由主机和客户端组装的上下文，其中包括服务器发布的工具模式，以及工具调用返回的值。由于这些输入来自用户提示词之外的来源，它们为对抗性影响提供了额外路径（Greshake 等，2023；Hou 等，2025）。

MCP 系统还包含客户端、服务器和传输层操作；这些操作可能影响执行过程，却不会出现在模型可见的上下文中。因此，安全评估必须区分两类攻击：一类进入模型能够观测的上下文，另一类则在模型观测范围之下运行。前者可能影响模型决策，后者则可能无论模型如何响应都使系统失陷。由此产生了本文的核心问题：在支持 MCP 的智能体中，应如何评估对抗性上下文，同时区分模型易感性与下层系统失陷？图 1 展示了一个模型可见响应与执行轨迹结果出现分歧的案例。

**图 1. 端到端远程访问攻击。**恶意服务器在打开反向 Shell 的同时报告操作成功；执行轨迹检测到了这一行为。

现有的 MCP 安全评估尚不能完整回答这一问题。MCPSecBench（Yang 等，2025）等基准评估已经部署的智能体产品。其结果除了反映底层模型，还反映了产品的系统提示词、安全护栏、用户界面和编排机制。因此，在一个部署中得到的结果未必能推广到使用相同模型的另一种部署。另一个局限是将任务完成度作为主要结果指标（Kutasov 等，2025；Zong 等，2025）。任务完成度是一个系统层指标，除了模型之外，还取决于规划、记忆、编排和工具执行。任务失败可能源于智能体栈错误，而不是模型对对抗性上下文的响应；任务完成也可能掩盖模型在中间步骤中遵循了对抗性指令。这样的评估设置既不能隔离模型如何处理不可信上下文，也不能区分模型本可以抵抗的攻击与模型根本没有观测到的攻击。

要弥补这一空白，需要一个固定周边智能体栈、并评估与具体攻击相关结果的受控环境。我们提出 **COPEX**（**CO**ntext **P**rovider **EX**ploitation，上下文提供方利用），这是一个固定智能体循环、编排逻辑、场景逻辑、工具环境和执行预算，仅改变负责工具选择的 LLM 的基准。该设计使模型能够在相同执行条件下进行比较，同时还能够识别部分或完全发生在模型观测范围之外的失陷。表 1 将 COPEX 与近期 MCP 安全基准进行了比较。

我们在 3,375 次试验中评估了 9 个模型。四种攻击入口面的平均攻击成功率介于 58.3% 和 71.4% 之间，表明易感性并不局限于用户提示词：通过工具模式和工具响应进入的攻击，其成功率与其他攻击相当，甚至更高。在 6 类攻击的匹配配置上进行评估时，确定性轨迹谓词和语义评估器得到的攻击成功率不同，说明测得的成功率取决于评分方法。在包含 8 类攻击的防御子集上，联合输入扫描和上下文扫描使平均攻击成功率相对于无防御设置降低了 48.8%；但它们无法影响通过未被扫描的上下文进入的攻击。这些结果表明，评估效果和防御有效性都取决于可观测的证据或协议表面。

本文的主要贡献如下：

- **提出 COPEX。**我们提出 COPEX，这是一个受控基准：按照攻击入口面对 MCP 攻击进行组织，并将模型对可见对抗性上下文的易感性与发生在模型观测范围之外的系统失陷区分开来。
- **实现 25 类攻击。**我们在 16 个 MCP 服务器上实现了 25 类攻击，将其构造成 125 个场景。这些服务器通过本地和网络传输提供 75 个工具和 7 个资源；每个场景都采用针对攻击特点的确定性评分或语义评分。
- **开展大规模评估。**我们在 3,375 次试验中评估了 9 个模型，并刻画攻击成功率如何随模型、攻击族、攻击入口面和评分方法而变化。同时，我们在受控观测边界下评估了输入扫描和上下文扫描。
- **比较智能体架构。**我们在相同 MCP 环境中对“推理与行动”（Reasoning and Acting，ReAct）和 Reflexion 进行了受控比较。通过固定模型、攻击、工具、评分方法、防御配置和执行预算，该比较隔离了推理架构对对抗性易感性的影响。

## 2 相关工作

### 2.1 工具调用智能体的安全基准

AgentDojo（Debenedetti 等，2024）和 InjecAgent（Zhan 等，2024）评估智能体在执行合法用户任务时抵御间接提示词注入的能力。ASB（Zhang 等，2025b）将评估范围扩展到系统提示词、用户输入、工具和记忆。SHADE-Arena（Kutasov 等，2025）评估智能体在完成无害任务的同时追求隐藏有害目标的情况。这些基准揭示了工具调用智能体中的重要安全故障。然而，它们并非围绕 MCP 的攻击入口面进行设计，评估结果主要反映固定 MCP 栈之外的端到端智能体行为，而不是固定 MCP 栈下的模型行为。

### 2.2 MCP 安全分析与基准

MCP 安全研究考察涉及客户端、服务器、工具和传输层的威胁（Guo 等，2025；Hou 等，2025；Hasan 等，2025；Rostamzadeh 等，2026）。MCPTox（Wang 等，2025）研究真实 MCP 服务器中的工具投毒攻击。MCP-Universe（Luo 等，2025）在现实的多服务器环境中评估任务完成度；MCP-SafetyBench（Zong 等，2025）在此基础上评估攻击下的不安全行为。MSB（Zhang 等，2025a）在端到端 MCP 工作流中衡量任务性能和攻击成功率。MCPSecBench（Yang 等，2025）则评估针对已部署 MCP 产品的攻击，包括 Cursor 和 Claude Desktop。

COPEX 在实验控制和结果度量两方面都与这些工作不同。它固定周边智能体栈，仅改变负责工具选择的 LLM，从而能够在四种攻击入口面之间进行受控比较。它还根据每类攻击适合的方式进行评分：当成功可以从执行轨迹中直接观测到时，使用确定性轨迹检查；当成功取决于模型响应的语义时，使用 LLM 判定器。

## 3 威胁模型与观测边界

COPEX 在一个由场景定义的受控环境中，评估通过 MCP 客户端行动的 LLM，即模型 $M$。在第 $t$ 轮中，主机和客户端组装模型可用的上下文：

$$
c_t = (h, p, S_t, R_{\leq t}),
\qquad
a_t \sim M(\cdot \mid c_t),
$$

其中，$h$ 是固定的系统指令，$p$ 是用户任务，$S_t$ 是第 $t$ 轮可用的工具模式集合，$R_{\leq t}$ 包含在该轮之前及该轮中通过工具调用返回的工具响应。模型根据这一上下文选择动作 $a_t$。

上下文 $c_t$ 定义了模型的观测边界。客户端状态、服务器行为和传输状态可能影响执行过程，却不会出现在 $c_t$ 中。因此，攻击可能操纵模型能够观测的内容，也可能在观测边界之下运行并独立影响系统。COPEX 同时记录这两种情况，但按照攻击入口面对结果进行报告，从而避免将下层失陷误解为模型易感性。

攻击者可以控制表 2 所列的四种入口面之一。我们假设攻击者不能修改模型权重或固定系统指令。每个场景都规定攻击者能力、预期的安全违规行为和成功标准。根据攻击类型的不同，成功可能表现为不安全的工具调用、敏感信息泄露、接受被操纵的内容，或者客户端、服务器或传输层行为遭到破坏。

**表 2. COPEX 考虑的四种攻击入口面及其在图 2 中的标记。**

| 入口面 | 攻击者可控制的组件 |
| --- | --- |
| 模型/智能体（*ma*） | 用户任务以及 $p$ 中的上游内容 |
| 客户端（*cl*） | 客户端解析、元数据和上下文组装 |
| 服务器/工具（*st*） | 工具模式、工具响应和服务器端行为 |
| 传输层（*tr*） | 传输中的数据、端点解析和连接状态 |

## 4 方法

COPEX 提供了一个受控环境，用于评估通过支持 MCP 的智能体的不同入口面进入的攻击。本节介绍执行环境和防御措施的部署位置，解释攻击场景如何构造，并规定攻击成功的度量方式。

**图 2. COPEX 执行环境。**YAML 清单配置场景、模型、服务器、防御措施和评分方法。编排器执行一个有界的智能体循环并记录轨迹；红色虚线箭头表示模型/智能体（*ma*）、客户端（*cl*）、服务器/工具（*st*）和传输层（*tr*）攻击入口面。

### 4.1 执行环境与防御措施

图 2 展示了 COPEX 的执行环境。每次试验都由一个 YAML 清单定义，其中指定模型、用户任务、攻击配置、所需的 MCP 服务器、防御模式、执行预算和评分方法。编排器实例化环境，在有界的智能体循环中运行所配置的模型，并记录完整轨迹。

默认使用 ReAct 作为推理架构（Yao 等，2023）。在 Reflexion 配置（Shinn 等，2023）中，模型会在选择下一步动作之前，针对当前轨迹生成一段明确的反思。这段反思会被加入下一轮使用的上下文中。比较实验固定模型、场景、工具、防御模式、评分方法和执行预算，从而能够在匹配条件下考察推理架构的影响。

在不同模型之间，COPEX 固定场景、服务器行为、编排逻辑、执行预算、防御模式和评分方法。该环境包含 16 个 MCP 服务器，提供 75 个工具和 7 个资源。服务器通过标准输入/输出和 HTTP 进行通信。可流式传输的 HTTP 和由 Docker 隔离的传输服务支持代理、DNS 重绑定和远程访问场景。记录的轨迹包括模型输入和输出、工具发现、工具调用、工具响应、协议事件、相关环境状态、系统提示词、令牌数量以及模型最终响应。

COPEX 支持四种防御模式：不进行扫描、输入扫描、上下文扫描，以及联合输入和上下文扫描。每个扫描器都由一个不具备工具访问能力的守门模型实现，该模型返回 `Allow` 或 `Block`。输入扫描器在执行前检查一次用户任务。上下文扫描器在工具注册时检查每个工具模式，并在每个工具响应进入模型上下文之前检查该响应。

被阻断内容的处理方式取决于检测位置。被阻断的用户任务会以 `Detected` 状态结束试验，并被计为攻击失败。被阻断的工具模式会从工具目录中移除，随后试验继续执行。被阻断的工具响应会被替换为结构化错误，其中说明对应工具和阻断原因。然而，响应扫描发生在工具调用之后：它可以阻止返回内容进入模型，却无法撤销工具执行或服务器端产生的影响。

工具模式只在注册时进行扫描。因此，模式内容或服务器行为之后发生变化时，不会再次扫描。守门模型无法使用工具，所用提示词不会点名具体攻击类别，并且只检查长度受限的序列化内容。扫描器发生故障时会记录该故障并采取失败时放行（fail-open）策略。这些设计使实验能够同时识别每个扫描器提供的保护，以及落在其观测边界之外的攻击。

### 4.2 攻击套件与场景构造

表 3（附录中的攻击分类表）总结了模型/智能体、客户端、服务器/工具和传输层四个入口面上的 25 类攻击。每类攻击都被分配一个用于报告的主要入口面。这一分配标识了对抗性影响首次进入 MCP 执行路径的位置，并不意味着攻击只会影响该入口面。

每类攻击包含 5 个场景变体，共形成 125 个可执行场景。使用 $i$ 表示攻击类型，使用 $v \in \{1,\ldots,5\}$ 表示其变体。每个场景规定用户任务、所需服务器、攻击配置、预期的安全违规行为和评分方法。5 个变体保持相同的利用机制和安全目标，同时改变操作层面的表述、载荷参数或攻击阶段。应用场景包括金融、DevOps、医疗、发布管理、事件响应、合规、保险和教育。基础设施攻击则可能改变同一协议层利用的配置或阶段。

传输层攻击运行在由 Docker 隔离的网络环境中，而不是作为对模型上下文的进程内修改。例如，MCP 重绑定场景使用生存时间为零的 DNS 响应，将客户端从攻击者控制的端点重定向到目标 MCP 服务。攻击者一侧的日志随后记录客户端是否连接到该服务、是否枚举其工具，以及是否调用某个工具。

我们采用人工指导的流程构造攻击场景。对于每种攻击类型，我们规定攻击者能力、利用机制、操作环境、预期违规行为和成功标准，然后编写第一个变体。我们借助 LLM 起草其余变体，再由人工进行修改、执行和检查。只有当场景的执行轨迹确实触发预期攻击机制，且其评分方式符合所述成功标准时，我们才保留该场景。

### 4.3 评分方法与评估指标

我们根据执行轨迹中可获得的证据，为每个场景选择合适的评分方法。确定性检查直接从工具调用、协议事件、日志或环境状态中识别成功。对于需要解释模型响应或根据攻击目标判断所泄露信息的结果，则使用 LLM 判定器。除“恶意代码执行”外，每类攻击的所有变体都使用同一种评分方法；对于恶意代码执行，4 个变体使用基础设施检查，1 个变体使用 LLM 判定器。

令 $\tau_{M,i,v,n}$ 表示模型 $M$ 在攻击类型 $i$、变体 $v$ 和第 $n$ 次重复试验中产生的轨迹，每个变体重复 $N$ 次。令 $\mathcal{I}_{\mathrm{det}}$ 和 $\mathcal{I}_{\mathrm{sem}}$ 分别表示使用确定性检查和判定器评分的攻击类型索引集合，其中 $|\mathcal{I}_{\mathrm{det}}|=10$，$|\mathcal{I}_{\mathrm{sem}}|=15$。二元试验结果定义为：

$$
y_{M,i,v,n} =
\begin{cases}
P_{i,v}(\tau_{M,i,v,n}), & i\in\mathcal{I}_{\mathrm{det}},\\
J(q_{i,v},\tau_{M,i,v,n}), & i\in\mathcal{I}_{\mathrm{sem}},
\end{cases}
$$

其中 $y_{M,i,v,n}\in\{0,1\}$。这里，$P_{i,v}$ 是攻击类型 $i$ 和变体 $v$ 的程序化成功检查：当观测到所要求的轨迹条件时返回 1，否则返回 0。函数 $J$ 是固定的语义评估器，$q_{i,v}$ 是提供给它的、针对具体场景的成功标准。评估器接收该标准和完整轨迹（包括模型最终响应），并返回带有简短理由的结构化二元判定。完整的评估提示词见附录中的判定器提示词部分。

对于模型 $M$ 和攻击类型 $i$，攻击成功率在 5 个变体以及每个变体的 $N$ 次重复试验上取平均：

$$
\operatorname{ASR}(M,i)
=
\frac{1}{5N}
\sum_{v=1}^{5}
\sum_{n=1}^{N}
y_{M,i,v,n}.
$$

这一计算方式为每个场景变体和每次重复试验赋予相同权重。随后，可以按照模型、攻击族或攻击入口面对结果进行汇总，同时不改变试验层面的成功定义。

## 6 讨论

### 局限性

防御研究和其他次级研究对每个变体只运行一次，因此其中的降低幅度和评分差异属于点估计，应将其理解为具有指示意义的结果，而不是精确估计。此外，15 类攻击依赖 LLM 判定器，因此它们的攻击成功率反映的是判定器的决策边界，而非客观的真实标签。由于评估的攻击类型限定为 25 类、每类只有 5 个变体，研究结果的泛化能力也受到限制。最后，攻击成功率衡量的是攻击交付之后的易感性，而非现实世界中的可利用性；现实可利用性还取决于攻击出现的频率、攻击者获得访问权限的难易程度以及攻击成本。

### 研究影响

COPEX 通过将模型对可观测对抗性上下文的响应，与发生在模型观测边界之下的系统失陷区分开来，明确了 MCP 安全结果可以归因于哪些因素。这有助于进行更有意义的模型比较，也表明防御措施必须部署在其能够检查的入口面上。研究结果还提醒我们不要依赖单一的鲁棒性排名：在所评估的不同入口面上，没有任何模型始终具有抵抗能力，而且测得的攻击成功率还部分取决于评分方法。

## 7 结论

本文提出了 COPEX，这是一个用于评估支持 MCP 的智能体抵御对抗性上下文能力的受控基准。COPEX 包含 25 类攻击，将其构造成 125 个场景，覆盖模型/智能体、客户端、服务器/工具和传输层四种攻击入口面。在 9 个模型和 3,375 次试验中，攻击成功率会随着模型、攻击族和评估方法而显著变化：某些攻击直接取决于模型决策，而另一些攻击则利用模型观测和控制范围之外的客户端、服务器或传输层行为。确定性检查和 LLM 判定器能够捕获互补的成功形式；输入扫描和上下文扫描只会降低进入其所检查入口面的攻击的成功率。通过区分模型易感性与下层系统失陷，COPEX 为支持 MCP 的智能体安全评估提供了更清晰的归因方式。我们在 <https://github.com/inspire-center/copex> 发布了基准场景和评估代码；执行轨迹将添加到该仓库中。

## 伦理声明

所有传输层实验都在 Docker 隔离环境中，针对受控服务器开展。实验没有针对或点名任何第三方系统。我们发布基准场景和评估代码，并提供用于受控测试和协同披露的文档。
