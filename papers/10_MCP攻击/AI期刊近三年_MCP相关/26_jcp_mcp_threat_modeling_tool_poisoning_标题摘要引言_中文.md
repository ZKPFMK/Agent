# 模型上下文协议威胁建模：提示词注入与工具投毒漏洞分析

**原标题：**Model Context Protocol Threat Modeling and Analysis of Vulnerabilities to Prompt Injection with Tool Poisoning  
**作者：**Charoes Huang、Xin Huang、Ngoc Phu Tran、Amin Milani Fard  
**发表信息：**2026，*Journal of Cybersecurity and Privacy*，6，84。  
**DOI：**[10.3390/jcp6030084](https://doi.org/10.3390/jcp6030084)  
**发表日期：**2026 年 5 月 5 日。  
**原文：**[本地 PDF](./26_jcp_mcp_threat_modeling_tool_poisoning.pdf)。

## 摘要

模型上下文协议（Model Context Protocol，MCP）已经快速发展为连接 AI 助手与外部工具和数据源的通用标准。MCP 简化了 AI 应用与各种服务之间的集成，但也引入了严重的安全漏洞，尤其是在客户端侧。

本文使用 STRIDE（Spoofing，欺骗；Tampering，篡改；Repudiation，抵赖；Information Disclosure，信息泄露；Denial of Service，拒绝服务；Elevation of Privilege，权限提升）和 DREAD（Damage，损害；Reproducibility，可复现性；Exploitability，可利用性；Affected Users，受影响用户；Discoverability，可发现性）框架，对 MCP 实现中的六个关键组件开展威胁建模：MCP 主机、MCP 客户端、LLM、MCP 服务器、外部数据存储和授权服务器。

这项综合分析表明，工具投毒是客户端侧最普遍、影响最严重的漏洞。工具投毒是指将恶意指令嵌入工具元数据中。基于这一发现，我们将实证评估重点放在这一关键攻击向量上，系统比较七个主要 MCP 客户端如何验证和防御工具投毒攻击。

分析结果显示，由于静态验证不足、参数可见性有限，大多数受测客户端都存在严重安全问题。我们提出了一种多层防御策略，包括静态元数据分析、模型决策路径追踪、行为异常检测和用户透明度机制。

本研究弥补了 MCP 安全研究中的一个重要空白。既有研究主要关注服务器侧漏洞，而本文针对 AI 智能体生态系统的安全，提出了可执行的建议和缓解策略。

**关键词：**模型上下文协议；MCP 安全；提示词注入；工具投毒；AI 安全；LLM 漏洞；客户端安全；安全测试。

## 1 引言

人工智能的快速发展推动了能够与各种外部工具和数据源交互的 AI 助手不断涌现。这类 AI 智能体能够自主选择并执行工具。Anthropic 于 2024 年 11 月提出模型上下文协议（Model Context Protocol，MCP）[1]，用于连接 AI 主机/助手与外部工具和服务，常被描述为“AI 的 USB-C”。

MCP 架构由三个核心组件组成：

1. **主机（Host）：**用户直接交互的应用，例如 Claude Desktop、Cursor IDE 和 ChatGPT；
2. **客户端（Client）：**位于主机内部、负责维护与服务器连接的协议管理器；
3. **服务器（Server）：**通过标准化 API 暴露工具、资源和提示词的外部程序。

在短短一年内，MCP 已被业界广泛采用，MCP Market 上列出的服务器超过 18,000 个 [2]。OpenAI、Google、Meta 和 Microsoft 等主要科技公司也参与了这一扩张。MCP 的快速普及体现了其通过支持自主工具选择和执行，增强 AI 智能体处理复杂多步骤任务能力的潜力。

然而，能力提升也带来了严重的安全影响。MCP 生态系统创造了传统软件安全范式尚未充分覆盖的新攻击向量。与用户输入经过明确验证层的传统应用不同，MCP 系统引入了一个作为中间决策者的 AI 模型，从而产生了通过提示词注入操纵系统的机会。

### 1.1 问题陈述

尽管 MCP 发展迅速并拥有数百万用户，当前关于该领域的研究和安全分析主要集中在服务器侧漏洞 [3–7]、AI 智能体安全框架 [8–14]，以及防御方案和缓解策略 [15–19]。对 MCP 客户端的系统性安全评估仍然基本空缺，关于 MCP 客户端和主机安全 [20–24]，以及提示词注入和工具投毒 [4, 25–32] 的学术研究都相对有限。

考虑到 MCP 客户端实现中独特的信任模型漏洞，这一研究空白尤其令人担忧。

- **客户端侧验证不足。**大多数客户端直接接受服务器提供的工具描述和元数据，而没有进行严格验证。MCP 规范 [1] 并未要求客户端验证服务器提供的元数据；我们的实证测试也表明，七个受测客户端中有五个没有实现静态验证机制（第 6.3.2 节）。与具有强输入验证层的传统软件不同，MCP 客户端通常缺乏检测工具描述中恶意指令的健壮机制 [26]。
- **用户感知有限。**用户通常无法在执行期间看到完整的工具描述，这为隐藏恶意参数创造了机会。一些客户端（例如 Cline 和 Claude CLI）会在 MCP 配置页面中展示工具描述，但这些信息主要只在初始设置阶段可见。具有审批对话框的客户端（例如 Claude Desktop 和 Cline）虽然在技术上会展示全部参数，但用户需要横向滚动才能看到完整取值，因此恶意内容很容易被忽略。此外，审批疲劳也会加剧这一漏洞：在频繁调用工具的工作流中，用户可能形成不经仔细检查就习惯性点击“批准”的行为。第 5.1.1 节的攻击演示利用了这一人为因素弱点：恶意参数（例如包含窃取凭据的 `sidenote` 字段）虽然出现在审批对话框中，却位于需要横向滚动才能看到的位置，依赖用户不查看全部参数便点击“批准”。
- **新的攻击面。**将 LLM 集成为决策者引入了提示词注入这一主要攻击向量，该漏洞在 OWASP LLM 漏洞排名中位列第一 [33]。传统输入验证技术难以防御基于提示词的操纵 [25, 34]，因为此时遭到利用的不是应用逻辑，而是 AI 模型本身。

随着 MCP 被采用，传统软件的攻击面已经发生显著变化。在传统模型中，用户输入通常经过 Web 应用验证后流向数据库；而在 MCP 模型中，用户输入会经过验证较弱的 AI 模型，再流向缺乏验证的 MCP 客户端，最后进入 MCP 服务器和外部系统。这一扩大的攻击面要求开展全面的客户端安全分析，这也是本研究的核心目标。

具体而言，我们以工具投毒作为主要攻击向量，评估客户端安全性。工具投毒是间接提示词注入的一种具体形式：恶意指令被嵌入工具元数据（描述、参数、提示词）中，而不是嵌入用户输入 [26]。该攻击利用客户端—服务器信任模型：客户端从服务器接收工具定义，并将其传递给 LLM 进行决策，从而为恶意元数据操纵模型创造机会。

### 1.2 研究范围与威胁模型

本研究分为两个层次。

在**威胁建模层面**，我们使用 STRIDE 和 DREAD 框架，对整个 MCP 生态系统进行分析，覆盖六个组件（MCP 主机、MCP 客户端、LLM、MCP 服务器、外部数据存储和授权服务器），共识别出 57 个威胁。

在**实证层面**，我们聚焦客户端侧安全，测试七个 MCP 客户端抵御四类工具投毒攻击的能力。

**实证范围。**我们的测试涵盖：

- MCP 客户端实现；
- 客户端对服务器提供的工具元数据所采用的验证机制；
- 工具调用期间的用户界面透明度；
- 客户端对可疑行为的检测能力。

我们没有实证测试服务器侧漏洞（该问题由文献 [3] 处理）、LLM 训练安全性或传输层配置。

**威胁模型。**我们假设攻击者部署或攻陷一个 MCP 服务器，并将恶意指令嵌入工具描述中。用户可能在不知情的情况下连接到该服务器，并且由于审批疲劳，往往不会仔细检查就批准工具调用。攻击者的目标是操纵 LLM 执行非预期操作，例如读取敏感文件或外泄数据，同时不让用户察觉。

**工具投毒研究重点。**我们将工具投毒作为重点，是因为它在 OWASP LLM Top 10 中排名第一，并在 DREAD 分析中获得 Critical 级别的 46.5/50 分。我们的威胁建模全面覆盖 57 个威胁，而实证测试优先评估其中风险最高的工具投毒，以提供可直接应用于客户端安全的洞察。

本文研究以下问题：

- **RQ1：**MCP 面临哪些威胁？这些威胁的严重程度如何？
- **RQ2：**主要 MCP 客户端是否容易受到通过工具投毒实施的提示词注入攻击？
- **RQ3：**如何制定缓解策略来保护 MCP 客户端实现？

### 1.3 主要贡献

已有 MCP 安全研究考察了服务器侧漏洞 [3]，定义了工具投毒概念 [26]，并测量了 LLM 智能体的攻击成功率 [4]；然而，没有研究比较不同 MCP 客户端实现抵御这些攻击的能力。尽管工具在服务器侧执行，但漏洞完全发生在客户端侧。

MCP 服务器通过 `tools/list` 返回工具元数据（`name`、`description`、`inputSchema`）。客户端未经验证就将这些元数据传入 LLM 的上下文窗口。随后，LLM 将工具描述作为自然语言指令处理，使精心构造的恶意描述能够操纵其行为，例如外泄数据或执行非预期命令。执行动作发生在服务器侧，但利用过程发生在客户端侧的 LLM 推理中。这正是本文要弥补的研究空白，也使本文区别于服务器侧研究 [3]。

为弥补这一空白，本文作出以下贡献：

1. 使用 STRIDE（欺骗、篡改、抵赖、信息泄露、拒绝服务、权限提升）和 DREAD（损害、可复现性、可利用性、受影响用户、可发现性）框架，对六个关键组件开展 MCP 实现威胁建模：（1）MCP 主机；（2）MCP 客户端；（3）LLM；（4）MCP 服务器；（5）外部数据存储；（6）授权服务器。
2. 通过分析客户端侧针对工具投毒提示词注入的漏洞，对 MCP 客户端安全性开展全面研究。
3. 通过实证安全测试评估主要 MCP 客户端的安全状况，并识别其漏洞。
4. 提出保护 MCP 客户端实现的缓解策略。

本文的发现对 MCP 客户端开发者、部署 AI 智能体的组织，以及参与 MCP 协议演进的标准化机构都具有直接实践意义。

### 1.4 文章结构

我们使用 STRIDE 模型识别包含最多漏洞的威胁类别，并使用 DREAD 模型按照严重程度对威胁评分，帮助开发者理解并缓解这些威胁。基于威胁建模结果，我们发现客户端侧漏洞的严重程度最高，且相对容易被利用。因此，我们将工具投毒作为客户端侧最普遍、影响最大的漏洞，优先进行分析。

本文其余部分的结构如下：第 2 节回顾相关研究并总结已有工作；第 3 节通过威胁建模回答 RQ1，即 MCP 面临哪些威胁及其严重程度；第 4 节介绍工具投毒的架构和攻击流程；第 5 节介绍实验和评估，用于回答 RQ2（主要 MCP 客户端对工具投毒提示词注入的脆弱性）和 RQ3（保护 MCP 客户端的缓解策略）；第 6 节给出实验结果和分析；第 7 节讨论研究发现、影响、建议和局限；第 8 节总结全文并提出未来工作。

## 3 MCP 威胁建模

本节通过威胁建模回答 RQ1，即 MCP 面临哪些威胁以及这些威胁的严重程度。完整的威胁建模文档见论文 GitHub 仓库 [39]。我们在既有安全框架基础上，结合 AI 介导系统的独特特征开展分析：

- **STRIDE 和 DREAD 威胁建模。**我们使用 Microsoft 最初提出的 STRIDE 威胁建模框架，识别 MCP 架构中的潜在威胁；同时使用 Microsoft 提出的 DREAD 风险评估模型，根据威胁的严重程度和发生可能性对识别出的威胁进行评估和排序 [40]。
- **OWASP LLM Top 10。**用于理解 LLM 特有的漏洞 [33]。
- **零信任架构。**用于指导客户端—服务器信任关系的设计。
- **纵深防御。**用于指导多层缓解策略。

本节的威胁建模以及第 4–6 节的实证评估表明，工具投毒正是在以下边界处利用系统弱点：不可信的服务器元数据跨越边界进入 LLM 的决策过程，并进一步驱动工具调用。STRIDE/DREAD 分析覆盖整个 MCP 生态系统；实证分析则有意聚焦于客户端—LLM 和客户端—服务器这两个边界，因为它们既具有较高严重性，也尚未得到充分研究。

### 3.1 STRIDE 威胁建模

为了全面理解 MCP 实现的安全状况，我们使用 STRIDE 框架分析六个关键组件中的威胁：（1）MCP 主机；（2）MCP 客户端；（3）LLM；（4）MCP 服务器；（5）外部数据存储；（6）授权服务器。各表包含以下字段：

- **编号：**威胁的连续编号；
- **标题：**威胁的简短名称；
- **类型：**STRIDE 类别，包括欺骗（Spoofing）、篡改（Tampering）、抵赖（Repudiation）、信息泄露（Information Disclosure）、拒绝服务（Denial of Service）和权限提升（Elevation of Privilege）；
- **说明：**对攻击向量的详细解释。

**图 1. MCP 威胁模型。**该模型展示 MCP 系统组件、信任边界及其交互。图中包括用户、MCP 客户端以及承载外部工具的一个或多个 MCP 服务器；箭头表示用户查询、工具调用等数据流和控制流，虚线表示组件之间的信任边界。

威胁模型基于纵深防御和零信任安全原则建立，每条边界都代表一个验证检查点，从而确保某个组件被攻陷后不会自动扩散到其他组件。既有服务器侧研究主要关注服务器—外部资源和服务器—授权服务器边界；提示词注入和工具投毒研究主要关注 LLM 鲁棒性，并隐含假设客户端可信；AI 智能体安全框架和基准通常在模型边界或运行时执行边界上开展研究，没有将 MCP 客户端行为单独隔离出来。本文则把 MCP 客户端实现作为独立安全边界进行系统、实证评估。

### 3.2 DREAD 威胁建模

为了量化已识别威胁的严重程度和风险分数，我们将 DREAD（Damage、Reproducibility、Exploitability、Affected Users、Discoverability）模型与 STRIDE 结合使用。DREAD 是 Microsoft 开发的风险评估模型，用于评估和排序安全威胁，为威胁分析提供结构化、定量化的方法。它包含五个维度：

- **损害（Damage）：**威胁成功利用后可能造成的影响或伤害程度。评分为：0（无损害）、5（信息泄露）、8（个人非敏感数据被攻陷）、9（非敏感管理数据被攻陷）、10（目标系统或数据遭到破坏，或系统可用性丧失）。
- **可复现性（Reproducibility）：**攻击能够重复实施的难易程度或可能性。评分为：0（几乎不可能或非常困难）、5（复杂）、7.5（容易）、10（非常容易）。
- **可利用性（Exploitability）：**漏洞或威胁被利用的难易程度或可能性。评分为：2.5（需要高级技术技能）、5（需要可获得的工具）、9（需要 Web 应用代理）、10（只需要浏览器）。
- **受影响用户（Affected Users）：**威胁被利用后可能受到影响的终端用户数量。评分为：0（无用户受影响）、2.5（只有个别用户受影响）、6（少量用户受影响）、8（管理员用户受影响）、10（所有用户受影响）。
- **可发现性（Discoverability）：**攻击者识别或发现威胁的可能性。评分为：0（难以发现）、5（通过公开请求可以发现）、8（威胁已公开或可以找到）、10（很容易发现，例如存在于容易访问的页面或表单中）。

威胁的总体 DREAD 分数由五项评分相加得到，分级为：低风险（1–10）、中风险（11–24）、高风险（25–39）和严重风险（40–50）[48]。

我们对同样的六个关键组件应用 DREAD 框架：MCP 主机、MCP 客户端、LLM、MCP 服务器、外部数据存储和授权服务器。分析结果见表 7–12，字段含义如下：

- **编号：**威胁的连续标识符；
- **标题：**威胁的简短名称；
- **损害：**威胁可能造成的总体伤害或影响程度；
- **可复现性：**攻击实施或重复执行的难易程度；
- **可利用性：**漏洞或威胁被滥用的可能性或难易程度；
- **受影响用户：**威胁被利用后可能受影响的终端用户数量；
- **可发现性：**攻击者识别或发现威胁的概率；
- **总分：**威胁的总体严重程度分数。

## 4 工具投毒架构与攻击流程

威胁建模分析表明，客户端侧漏洞的严重程度最高。因此，我们将工具投毒作为客户端侧最普遍、影响最大的漏洞，优先进行分析。

工具投毒是间接提示词注入的一种形式：恶意指令被嵌入工具元数据（描述、参数规格或提示词）中，而不是直接嵌入用户输入。当 LLM 在工具选择或调用过程中处理遭到投毒的工具描述时，可能受到操纵，进而选择不适当的工具、传递恶意参数、执行非预期操作或外泄敏感数据。

### 4.1 攻击流程

一次典型的工具投毒攻击通常遵循以下步骤：

1. 攻击者准备一个包含投毒工具描述的恶意 MCP 服务器；
2. 用户将 MCP 客户端连接到恶意服务器，或者攻击者攻陷一个合法服务器；
3. 客户端在初始化期间向服务器请求工具列表；
4. 服务器返回嵌入恶意指令的工具定义；
5. 客户端未经验证便存储工具描述；
6. 用户向 AI 助手提出一个合法请求；
7. LLM 同时处理用户请求和遭到投毒的工具描述；
8. 投毒描述操纵 LLM 的决策过程；
9. LLM 使用恶意参数调用工具，或执行非预期操作；
10. 客户端执行工具调用，其中可能包含用户不可见的隐藏参数；
11. 敏感数据被外泄，或恶意操作完成；
12. 攻击在用户几乎没有察觉的情况下成功。

**迭代式和欺骗式攻击场景。**为了便于说明，上述攻击流程被描述为离散步骤；但现实中，针对 MCP AI 智能体的对抗性交互通常是迭代式的。攻击者可以在多次交互中不断修改投毒工具描述，观察模型响应，并逐步增强提示词的有效性。

实践中，这类攻击经常依赖欺骗策略，例如把恶意操作包装成学术研究、系统测试，或在隔离、离线环境中开展的操作。这种上下文包装能够降低模型的抵抗性，利用 LLM 对看似合法或具有安全理由的请求的服从倾向。

重要的是，当前 MCP 客户端缺乏理解工具描述真实意图的机制，也无法检测跨会话逐步升级的行为，因此特别容易受到这类迭代式攻击的影响。

### 4.2 安全 MCP 客户端架构设计

工具投毒攻击利用了多个架构弱点：

- **没有验证层。**客户端通常缺少依据安全策略验证工具描述的机制；
- **LLM 成为信任边界。**AI 模型成为工具选择的唯一裁决者，没有独立验证机制；
- **参数隐藏。**用户无法看到传给工具的全部参数；
- **隐式信任。**客户端默认相信服务器提供的元数据是良性的。

为缓解这些漏洞，我们提出一种纵深防御架构，包含四层关键安全机制。

#### 4.2.1 第一层：注册与验证

在服务器注册时，客户端应执行以下操作：

- 根据严格的 JSON Schema 验证工具定义；
- 在可用时验证数字签名；
- 扫描描述中的危险关键词，例如 `read`、`~/.ssh`、`password`；
- 分析权限请求是否存在异常；
- 维护经过批准的工具模式白名单。

#### 4.2.2 第二层：决策路径分析

在调用工具之前，客户端应执行以下操作：

- 使用决策依赖图（Decision Dependency Graph，DDG）追踪 LLM 为什么选择某个工具；
- 验证工具选择是否符合用户意图；
- 检测偏离预期模式的异常决策路径；
- 执行组织层面的工具使用策略。

#### 4.2.3 第三层：运行时监控

工具执行期间，客户端应执行以下操作：

- 在受限沙箱中执行工具，限制其文件系统和网络访问；
- 监控未经授权的资源访问；
- 采用速率限制，防止滥用；
- 记录包含完整参数细节的全部工具调用。

#### 4.2.4 第四层：用户透明度

在整个过程中，客户端应执行以下操作：

- 在执行前显示完整工具描述和全部参数；
- 对高风险操作要求用户明确确认；
- 提供关于工具能力的上下文警告；
- 维护用户可以访问的完整审计日志。

### 4.3 缓解策略

本文的缓解方案通过三类互补策略实现纵深防御。

#### 4.3.1 协议加固

协议加固的目标是在协议层面缩小攻击面。作者将其实施优先级评为“严重”，认为它应当作为基础措施优先实施。

| 缓解措施 | 实现方式 | 作用 |
| --- | --- | --- |
| 严格模式验证 | 对工具定义允许的字段设置白名单；拒绝包含未知属性的工具 | 防止元数据注入攻击 |
| OAuth 2.1/范围限定 Token | 为每个工具实施细粒度权限范围；要求明确授权 | 限制被攻陷工具可能造成的损害 [15] |
| 版本签名 | 要求对工具定义进行加密签名，并在注册前验证 | 防止部署后被篡改 |
| 不可变工具定义 | 工具注册后，未经重新注册不得修改其元数据 | 阻止运行时操纵 |
| 注册时静态扫描 | 在允许注册前，对工具描述中的可疑模式进行自动分析 | 尽早发现明显的恶意工具 |

#### 4.3.2 运行时隔离

为了限制恶意工具执行造成的损害，作者建议实施运行时隔离，并将其实施优先级评为“高”，因为它是生产部署的必要条件。

| 缓解措施 | 实现方式 | 作用 |
| --- | --- | --- |
| 沙箱执行 | 在隔离容器（Docker、gVisor）或虚拟机中执行所有 MCP 工具 | 防止主机系统失陷 |
| 文件系统限制 | 使用 seccomp、AppArmor 或 SELinux 策略限制文件访问 | 保护敏感文件，防止未经授权读取 |
| 网络限制 | 将允许访问的网络目的地加入白名单，默认阻断其他连接 | 防止数据外泄 |
| 资源限制 | 对工具执行施加 CPU、内存和 I/O 配额 | 防止拒绝服务攻击 |
| 执行监控 | 实时监控系统调用、文件操作和网络活动 | 支持快速检测与响应 |
| 速率限制 | 限制每个用户或会话的工具调用频率 | 防止大规模自动化利用 |

#### 4.3.3 持续监控与治理

持续监控与治理的目标是维持长期安全可见性。作者将其实施优先级评为“中到高”，认为企业部署需要这一层能力。

| 缓解措施 | 实现方式 | 作用 |
| --- | --- | --- |
| 全面日志记录 | 记录所有工具注册、调用、参数和结果 | 支持取证分析和合规审查 |
| 异常检测 | 使用基于正常行为模式训练的机器学习模型 | 识别零日攻击和新型技术 |
| 工具审查流程 | 定期审查已注册工具并周期性重新扫描 | 发现随时间变恶意的工具 |
| 安全告警系统 | 对高风险工具使用或异常行为实时告警 | 支持快速事件响应 |
| 用户教育 | 清晰记录风险，并透明展示工具能力 | 帮助用户做出知情决策 |
| 反馈闭环 | 将安全洞察反馈到模型决策策略中 | 持续提高防御有效性 |
| 合规追踪 | 为监管要求保留审计记录，例如 GDPR、HIPAA | 维护组织合规性 |

#### 4.3.4 缓解策略矩阵

表 16 给出了覆盖系统全部安全层的综合缓解策略。风险评估矩阵通常根据威胁的可能性和影响对威胁进行排序，而这里的缓解策略矩阵将重点转向纵深防御架构的实际运行。该矩阵的主要目标，是展示如何将覆盖预防、检测、响应和恢复的技术控制系统地应用于各功能层。通过关注缓解措施，而不只是风险排序，作者提供了一套主动的系统韧性方案，确保即使威胁绕过初始预防措施，后续检测和响应层仍然能够发挥作用。

| 安全层 | 预防 | 检测 | 响应 | 恢复 |
| --- | --- | --- | --- | --- |
| 注册 | 模式验证、签名验证 | 静态扫描 | 拒绝恶意工具 | 审查并更新策略 |
| 选择 | 策略执行 | DDG 分析 | 阻止未经授权的选择 | 向用户告警 |
| 执行 | 沙箱、访问控制 | 行为监控 | 终止可疑进程 | 取证分析 |
| 执行后 | 速率限制 | 异常检测 | 禁用遭到攻陷的工具 | 事件响应 |
