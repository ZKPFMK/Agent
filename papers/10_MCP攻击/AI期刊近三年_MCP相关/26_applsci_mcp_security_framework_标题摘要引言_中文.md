# 基于 MCP 的 SOC 多智能体安全框架设计

**原标题：**Design of a Security Framework for Multi-Agent Systems Based on Model Context Protocol in SOC Environments  
**作者：**Rodrigo Tavares de Pina Simões、Xavier Larriva-Novo、Carmen Sánchez-Zas、Victor A. Villagrá、Andrés I. Marín López  
**发表信息：**2026，*Applied Sciences*，16，7915。  
**DOI：**[10.3390/app16167915](https://doi.org/10.3390/app16167915)  
**发表日期：**2026 年 8 月 8 日。  
**原文：**[本地 PDF](./26_applsci_mcp_security_framework.pdf)。

**应用说明：**本文提出的框架可以作为即插即用的中间件层，部署在生产环境的安全运营中心（Security Operations Center，SOC）中，用于保护基于 MCP 的 AI 智能体流水线。该框架能够在不修改底层智能体或 MCP 服务器的情况下，防御工具投毒、提示词注入和混淆代理等攻击。

## 摘要

安全运营中心（Security Operations Center，SOC）依靠一级分析师处理不断增加的告警量，但告警疲劳和工具碎片化使这一工作面临压力。采用模型上下文协议（Model Context Protocol，MCP）的 LLM 多智能体系统正被用于自动化这些任务，但其自主性和工具访问能力也使其暴露于工具投毒、间接提示词注入和混淆代理等攻击。

为解决这一问题，本文提出一个面向 MCP 多智能体 SOC 流水线的安全框架。该框架以中间件层的形式实现，包括工具注册验证器和五个执行层：访问控制、速率限制、输入验证、输出验证和审计日志。框架被应用于一个连接 Wazuh SIEM 的“分诊—富化—响应”流水线，该流水线通过定制 MCP 服务器与 Wazuh 集成。

在基于 OWASP、MITRE ATLAS 和 ATFAA 等不同威胁分类体系构建的威胁模型中，本文共考虑 35 个攻击向量，其中 29 个可以在中间件层处理，并由框架控制措施覆盖。随后，研究者使用专门构造的恶意 MCP 服务器和测试工具中的定向注入开展实验验证，将测试组织为六个测试套件，共执行 600 次。评估威胁模型中的每一个攻击实例都被阻断，没有攻击绕过框架，测试范围内也没有合法调用被误拒绝。

不过，经过混淆的攻击变体能够绕过基于词法内容检查的控制措施，这限定了上述结果的适用范围。完整流水线演示进一步确认，框架能够保持正常的业务输出。结果表明，系统化的中间件控制可以在不修改底层智能体或 MCP 服务器的情况下，保护基于 MCP 的智能体 SOC 部署。

## 1 引言

安全运营中心（Security Operations Center，SOC）正面临网络威胁数量增加且复杂度不断提高所带来的压力 [1]。这一压力尤其集中在一级分析师身上：他们的工作很大一部分是对告警进行分诊，并在相互割裂的工具集中手动关联上下文信息。这种重复且信息密集的工作流会直接造成告警疲劳 [2, 3]，也会在响应启动前为攻击者横向移动或外泄数据创造机会。

基于安全编排、自动化与响应（Security Orchestration, Automation, and Response，SOAR）平台的规则自动化在一定程度上减轻了这一负担，但静态剧本难以应对新颖或模糊的攻击模式，因此仍然存在局限 [4, 5]。

人工智能（Artificial Intelligence，AI）已经成为下一阶段 SOC 自动化的重要推动力。LLM 正从被动的文本处理模型转变为能够规划、调用外部工具并跨会话积累上下文的智能体系统。这一转变使自动化一级分析师的重复性工作成为可能，同时保留了规则系统所缺乏的适应性 [6, 7]。

多智能体系统进一步扩展了这一范式：它将工作分配给多个专门化智能体，自然映射到人类 SOC 团队的分层结构；持久化共享记忆则允许智能体跨告警和跨会话积累运行上下文 [8, 9]。

要在实践中实现这一范式，需要一种标准化机制，将智能体连接到 SOC 运行所依赖的异构工具和数据源，包括 SIEM 平台、威胁情报源和工单系统。Anthropic 于 2024 年 11 月提出的模型上下文协议（Model Context Protocol，MCP）解决了这一需求：它用一个任何兼容客户端和服务器都可以实现的开放协议，取代原本一次性的定制集成 [10–12]。

MCP 发布后迅速得到产业界采用，包括与主要 LLM 提供商的集成，以及于 2025 年 12 月捐赠给 Linux Foundation 旗下的 Agentic AI Foundation [13, 14]。MCP 已经被应用于企业安全运营工作流 [15]。

然而，使基于 MCP 的多智能体系统对 SOC 自动化具有价值的自主性和工具访问能力，也使其暴露于传统软件安全中没有直接对应物的攻击类别。智能体依赖自然语言工具描述和外部检索内容来决定采取哪些行动，因此攻击者可以将恶意指令嵌入工具元数据或智能体检索的数据中，导致工具投毒、间接提示词注入以及跨会话的记忆操纵 [16–18]。

在多智能体部署中，这一风险还会进一步加剧。一方面，智能体之间存在信任利用：直接面对用户提示时失败的载荷，可能通过同伴智能体传递后成功执行 [19]。另一方面，还存在混淆代理攻击：攻击者操纵拥有较高权限的智能体，使其代表攻击者执行未经授权的操作 [20]。

包括 OWASP LLM 和智能体应用 Top 10 [21, 22]、OWASP MCP Top 10 [23]、MITRE ATLAS [24] 和自主 AI 智能体高级威胁框架（Advanced Threat Framework for Autonomous AI Agents，ATFAA）[25] 在内的多个分类体系，已经开始系统整理这些风险，但它们存在大量术语重叠，也没有形成将风险转换为可部署中间件控制措施的统一机制。

近期出现的 MCP-38 [26] 具有更细粒度的分类能力。它通过系统分解 MCP 规范，列举了 38 类威胁，并将其与 STRIDE 以及两个 OWASP 分类体系进行交叉映射，自称为一个统一的超集，用于整合碎片化的术语。由于 MCP-38 的协议层粒度超出了本文中间件层的处理范围，本文将其作为对第 1 节所选攻击向量的外部佐证，而不是五个主要威胁分类体系之一。

已有关于 MCP 多智能体安全运营架构的研究验证了若干关键架构模式，包括角色专门化、持久化共享记忆和信任边界强制执行；与此同时，其他研究也刻画了具体 MCP 攻击向量，并提出了智能体 AI 风险治理框架 [9, 15, 27–29]。

然而，目前还没有研究同时具备以下特征：将功能完整的多智能体 SOC 架构通过 MCP 连接到真实 SIEM 部署，并配套一个从已记录攻击面系统推导、且经过受控 MCP 攻击场景实证验证的安全框架。

本文通过提出一个面向 MCP 多智能体 SOC 流水线的安全框架来弥补这一空白。该框架以中间件层形式部署在智能体和 MCP 服务器之间。本文的主要贡献如下：

1. **MCP 多智能体 SOC 系统的威胁模型。**我们从五个威胁分类体系中，根据明确的架构相关性、实证基础和 SOC 适用性标准，选出 35 个攻击向量。
2. **三智能体 SOC 流水线。**我们设计了一个包含分诊、富化和响应三个智能体、带有持久化共享记忆的流水线，并通过定制 MCP 服务器连接真实 Wazuh SIEM 部署。
3. **五层安全框架。**我们设计访问控制、速率限制、输入验证、输出验证和审计日志五个安全层，并配套连接阶段的工具注册验证器。该框架覆盖 35 个攻击向量中的 29 个，这些攻击向量可以在中间件层处理。
4. **实验评估。**我们通过六个测试套件和 600 次执行开展实验评估，所有攻击实例都被阻断，没有攻击绕过框架，测试范围内也没有合法调用被错误拒绝。

本文其余部分的结构如下：第 2 节回顾安全运营多智能体架构和智能体 AI 安全框架相关工作；第 3 节介绍本文提出的架构、攻击面、安全框架及其实验室实现；第 4 节报告实验结果；第 5 节结合相关文献和研究局限讨论结果；第 6 节总结全文。

## 3 材料与方法

本节介绍所提出系统的设计与实现。第 3.1 节介绍多智能体架构并刻画其引入的攻击面；第 3.2 节介绍为应对该攻击面而设计的安全框架；第 3.3 节介绍实验室实现、技术栈以及第 4 节实验所采用的流水线执行流程；第 3.4 节介绍评估方法；第 3.5 节记录第 4 节实验所依赖的测试工具和攻击载荷目录。系统首先按照真实 SOC 的运行要求进行架构设计，随后刻画该架构暴露的攻击面，最后系统化地设计安全框架来处理这些攻击面，因为只有先理解架构暴露了什么，才能设计出必要且充分的控制措施。

### 3.1 架构

本文提出的系统采用顺序式多智能体流水线，由三个功能层组成：包含三个专用 LLM 智能体的智能体层、跨会话持久化的共享记忆层，以及管理到两个外部服务器并发连接的 MCP 集成层（见图 1）。智能体之间采用同步通信：一个智能体完成工作后，才会调用下一个智能体；因此，每条告警都会经历“分诊—富化—响应”（triage-enrichment-response）流程。

每个智能体都有专用系统提示词、受限工具允许列表和特定输出模式，从而通过角色专门化和最小权限工具分配来限制其能力。Wazuh MCP 服务器是在开源项目 `gbrigandi/mcp-server-wazuh` [32] 的基础上定制构建的，并增加了本文开发的两个工具 `get_wazuh_latest_alert` 和 `propose_wazuh_rule`，共暴露 16 个工具，覆盖告警、智能体、漏洞、集群健康状态、日志和规则等功能。其中，分诊智能体可以使用 3 个工具，足以获取触发告警并判断是否需要升级；富化智能体可以使用 7 个工具，覆盖主机画像、进程和端口枚举以及漏洞数据；响应智能体可以使用 6 个工具，其中包括 `propose_wazuh_rule`。后者是系统中唯一能够生成外部可执行产物的工具，也是唯一限制给单个角色使用的工具。工具调用到达 MCP 服务器之前就会执行访问边界检查，因此，即使某个智能体在语义上已经被攻陷，也不能通过调用受限工具来提升权限。

持久化共享记忆模块用于弥补独立 LLM 无法在调用之间保留知识的不足，并在三个存储区中跨会话累积结构化数据。

- **告警历史日志：**记录每条已处理告警的分诊和富化输出，使响应智能体能够参考同一主机过去发生的事件来校准当前紧急程度。该存储区与智能体知识库都以主机为键，并且有意跨会话保存。第 3.2 节引入的按会话隔离只适用于下文所述的上下文存储区。
- **智能体知识库：**以智能体名称为键保存主机特定信息，包括 IP 地址、操作系统、风险等级和已知漏洞。
- **上下文存储区：**保存运行时注入每个智能体系统提示词的键值条目，是安全敏感性最高的组件。由于基础架构会在未经验证的情况下加载其中内容，它构成了记忆投毒的主要攻击面；第 3.2 节介绍的输入验证器将处理这一漏洞。

系统同时连接两个 MCP 服务器，并将它们隔离在不同的 Docker 网络分段中，使恶意服务器不能直接访问受监控基础设施。合法的 Wazuh MCP 服务器连接真实 Wazuh SIEM 部署。恶意服务器是一个符合 MCP 规范的专用端点，用于在受控且可复现的条件下模拟已经记录的攻击向量：

- `get_wazuh_latest_alert` 与合法工具使用相同名称，从而制造工具影子（tool shadowing）条件；
- `get_threat_intelligence` 将对抗性指令直接嵌入描述字段，实现工具描述投毒；
- `get_vulnerability_feed` 返回包含注入指令的载荷，实现通过工具输出进行间接提示词注入；
- `get_compliance_report` 指示智能体使用攻击者控制的参数调用规则提议工具，实现混淆代理攻击。

连接时检测到被影子覆盖的 `get_wazuh_latest_alert` 名称冲突，构成第 3.2 节工具注册验证器设计的主要实证动机。

与 AI 辅助 SOC 部署所建议的混合模型一致 [5,33]，响应智能体从不直接执行操作。它只生成结构化计划，其中包含建议操作、人工审批标志和升级标志。系统中权限最高的操作 `propose_wazuh_rule` 只返回供分析师审查的格式化提议，在任何情况下都不会直接修改 Wazuh 实例。这样，即使响应智能体已经完全被攻陷，也不能在没有人工明确审查的情况下修改检测基础设施。

在应用任何安全控制之前，基础架构暴露出四个促成第 3.2 节安全框架设计的攻击面：

1. **工具调用机制：**它通过基于角色的可见性限制工具范围，但不会验证智能体传入已允许工具的参数，因此可能被混淆代理攻击利用。
2. **记忆持久化机制：**未经清理的上下文存储区引入了持久性攻击面；一次成功写入就可能影响三个智能体的所有未来会话。
3. **智能体间交接机制：**智能体输出以纯文本形式传递，缺少中间验证，使注入内容能够传播到下游智能体的上下文中。
4. **多服务器连接机制：**MCP 客户端会先将所有已连接服务器的工具汇聚到同一个命名空间，再呈现给智能体层，却没有执行逐服务器验证，因此工具发现阶段容易受到投毒。

### 3.2 安全框架

安全框架以中间件层实现，拦截智能体与 MCP 服务器之间的全部通信，并通过一个统一网关类来实现；任何智能体都不能直接调用工具（见图 2）。

该框架满足根据第 2 节文献研究提出的六项设计标准：

1. **统一的中间件拦截：**任何智能体都不持有 MCP 客户端的直接引用。
2. **工具元数据预接纳验证：**在工具描述暴露给任何智能体之前检查其内容。
3. **运行时基于角色的访问控制（RBAC）：**在每次工具调用时执行，而不是仅在初始化阶段进行静态过滤。
4. **多层输入和输出验证：**覆盖工具参数、智能体间交接、记忆上下文和外部获取数据。
5. **中间件执行上下文中的追加式审计日志：**对敏感值进行哈希处理。
6. **面向模型的失败信息隐藏：**无论哪个控制措施触发拦截，都返回通用错误消息，从而阻断逐层错误信息本来会暴露的诊断通道。

失败信息隐藏是一种缩减攻击面的属性，而不是已经验证能够抵御自适应攻击者的防御。它通过移除有助于迭代探测的信息来降低风险，但本身并不能保证自适应攻击者最终无法成功。本文对该属性的验证是结构性的：所有测试套件中，被阻断的调用都返回固定且与具体控制措施无关的消息；本文没有在威胁模型之外开展迭代探测实验（见第 5 节）。

框架将这些标准组织为两个阶段：每个服务器初始化时执行一次的**连接阶段**，以及应用于每次工具调用的五个连续层组成的**执行阶段**。其中，连接时的描述检查，以及输入和输出验证器（第 3 层和第 4 层）中的注入模式检查，均采用确定性的模式匹配，而不是语义分类或基于 LLM 的分类。这一选择有三个原因：

1. 语义内容分析只用于这些扫描，其余控制措施——运行时 RBAC、速率限制、JSON Schema 验证、清单和二进制哈希以及会话命名空间隔离——都是不依赖语义判断的确定性结构检查。
2. 如果将注入检测交给辅助语言模型，就会重新引入该框架试图关闭的提示词注入面，因为检测器本身也可能受到所检测攻击的影响；同时，安全决策会依赖模型行为，破坏失败信息隐藏和模型无关性标准。
3. 确定性匹配能够产生可复现且可以按模式归因的决策，这正是第 3.4 节评估协议和追加式审计日志所依赖的属性。

这种选择的代价是：固定模式对自适应攻击者不断修改载荷以逃避检测的鲁棒性有限，第 5 节将讨论这一限制。

#### 3.2.1 连接控制

在连接阶段、任何工具暴露给任何智能体之前，框架会对每个服务器返回的完整工具清单执行三项检查（见图 3）。

第一项检查是正则表达式扫描，检查每个工具的描述字段，寻找对抗性指令结构，包括命令式覆盖短语、胁迫性指令以及以数据外泄为目的的表达。一旦工具描述命中，工具就会被阻断，并在到达智能体层之前从清单中移除。

第二项检查是在不同服务器之间强制执行命名空间所有权：第一个注册某工具名称的服务器被记录为该名称的所有者，之后来自其他服务器的同名注册会被拒绝，而不是静默接纳，从而防止恶意服务器影子覆盖可信工具名称。

第三项检查是为每个服务器的完整工具清单计算 SHA-256（Secure Hash Algorithm，安全哈希算法）哈希，并在首次连接时将其固定为参考值。之后每次重新连接都会重新计算哈希并与固定值比较；如果不匹配，就发出警告，标记可能存在的“拉地毯”（rug pull）攻击，即服务器在首次建立信任后修改其工具定义。上述检查共同处理了第 3.1 节指出的多服务器连接攻击面。

#### 3.2.2 第 1 层：访问控制

访问控制层在每次工具调用时首先执行，为分诊、富化和响应角色分别实施基于角色的允许列表（见图 4）。来自未知智能体标识符的调用，或对不在该智能体允许列表中的工具的调用，都会被无条件拒绝。

该检查采用运行时强制机制，而不是只依赖智能体实例化时已经执行的静态工具过滤。静态过滤只能限制智能体能够发现什么，不能限制语义上被操纵的智能体被诱导去调用什么；运行时强制则无论智能体为何作出调用决定，都会拦截该调用。这一机制处理第 3.1 节所述的工具调用面，包括混淆代理和权限提升向量。

#### 3.2.3 第 2 层：速率限制器

速率限制层在滑动的 60 秒窗口内按智能体跟踪工具调用次数。考虑到富化智能体拥有更大的工具范围（7 个工具），各角色阈值分别为：分诊智能体 20 次、响应智能体 20 次、富化智能体 30 次。

此外，独立的流水线级限制器将响应智能体发出的人工审批请求限制为每个一小时滑动窗口最多 10 次。该限制针对监督饱和和同意疲劳攻击：攻击者通过大量请求淹没分析师，使其在未经审查的情况下直接批准请求（见图 5）。

#### 3.2.4 第 3 层：输入验证器

输入验证器处理四个输入面（见图 6）：

1. **工具调用参数：**首先根据被调用工具的 JSON Schema 进行结构验证，然后扫描字符串值中的注入模式。
2. **智能体间交接：**扫描相同的注入模式，并检查交接是否符合预期的“分诊—富化—响应”顺序；任何发往非预期智能体的交接都会被拒绝。
3. **记忆上下文：**从上下文存储区取出的条目在注入智能体系统提示词之前进行扫描，并按会话标识符命名空间化。这样，被投毒或跨会话的条目会被排除，而不会传播给所有智能体；同时，一次流水线执行也不能读取或破坏并发执行的上下文。
4. **外部获取数据：**采用扩展模式集进行扫描，除了标准注入模式，还覆盖内联脚本执行和 JavaScript 协议处理器等 Web 特有向量。

按会话隔离专门适用于上下文存储区，因为其中任意的、原样注入的键值条目构成第 3.1 节指出的记忆投毒面。该隔离有意不应用于告警历史日志和智能体知识库：这两个存储区以主机为键，并按设计跨会话保留，因为它们的目的正是让响应智能体根据同一主机的历史事件校准紧急程度。

这两个存储区不会重新引入记忆投毒向量，因为其中的内容不能来自未经验证的输入。与上下文存储区不同，它们只由框架写入，而且只写入已完成流水线运行的结构化分诊和富化输出；这些输出在存储之前已经通过输入和输出验证器。即使其中包含自由文本说明和摘要字段，也都是由只处理已验证输入的智能体生成的。因此，把这些按主机保存的记录重新注入后续运行，不会引入尚未经过验证的攻击者控制内容；它们的跨会话持久化不会扩大第 5 节所讨论的正则表达式逃逸限制之外的攻击面。只有可能携带未经验证外部内容的上下文存储区需要按会话隔离。

#### 3.2.5 第 4 层：输出验证器

输出验证器在服务器响应到达发起调用的智能体之前拦截响应，并执行两项检查（见图 7）。

第一项是正则表达式扫描，覆盖间接提示词注入、胁迫性工具调用指令、凭据和 API 密钥外泄模式、系统提示词提取尝试，以及会构成 AI 病毒的自传播指令。被归类为外部内容源的工具还会采用扩展模式集，额外覆盖内联脚本和 iframe 注入。

第二项是响应大小检查：无论内容是什么，只要响应超过 100 KB 就会被拒绝。这既限制了单次响应能够注入的对抗性内容量，也降低了拒绝服务（DoS）风险。

#### 3.2.6 第 5 层：审计日志

审计日志记录所有经过框架的工具调用，无论调用获准还是被阻断。记录字段包括 UTC 时间戳、会话标识符、发起调用的智能体角色、工具名称及其来源服务器、调用参数、结果或阻断原因，以及响应的 SHA-256 哈希。

敏感参数字段在写入日志前会替换为其 SHA-256 哈希，因此审计轨迹本身不会成为第二个数据外泄面。日志采用追加式写入，并按会话标记，使系统能够跨会话开展异常调用模式的取证分析，同时无需修改智能体或 MCP 客户端。

#### 3.2.7 横向控制与会话级控制

有两项控制措施适用于所有执行层，而不是某个具体层或某次调用。

- **安全错误处理：**只要任意层阻断调用，就向发起调用的智能体返回固定的通用消息，不透露究竟是哪个层或哪种模式触发了阻断。这可以关闭不同层返回不同错误消息所形成的诊断通道，减少迭代探测可获得的信息，但本文没有据此声称能够彻底击败自适应攻击者。
- **工具版本固定：**将连接阶段的清单哈希检查扩展到整个会话生命周期，持续监控工具命名空间，并显式暴露客户端原本可能静默接受的变化。

此外，还有三项控制措施作用于每次完整流水线执行：

1. **会话身份：**为每次执行分配一个 UUID（Universally Unique Identifier，通用唯一标识符），并将其传播到审计日志、记忆存储区的上下文命名空间和框架实例中，使每项安全决策都能追溯到特定执行上下文，并确保一次执行的完整性不会受到共享同一记忆存储区的并发执行影响。
2. **供应链验证：**将运行中容器获得的 Wazuh MCP 服务器二进制文件 SHA-256 哈希与连接时固定的参考值进行比较。如果不匹配，就拒绝服务器，并且不注册其任何工具。
3. **MCP 通道认证：**通过自定义请求头为每个请求附加共享密钥，并根据可信来源允许列表验证出站请求的 `Origin`（用于出站 CSRF/CORS 控制）以及入站响应的 `Origin`（用于防 DNS 重绑定）。

在本文评估的容器化部署中，允许来源变量未设置，因此响应侧 DNS 重绑定检查处于禁用状态。该部署通过两项拓扑级措施提供相应属性：Docker Compose 配置将每个公开容器端口都绑定到回环接口（`127.0.0.1`），并将容器间通信限制在隔离网络分段中。如果部署将这些端口暴露到本地主机之外，或部署跨越多台主机，就需要显式设置允许来源，以恢复应用层检查。

#### 3.2.8 攻击覆盖范围

本文从第 1 节回顾的更广泛威胁分类体系中选取 35 个攻击向量，并采用三个明确标准，使选择过程能够根据源分类体系复现。一个向量只有同时满足以下三个条件才会被保留：

1. **架构相关性：**该向量必须利用本文架构实际部署的能力，即持久化记忆、工具调用、智能体间通信或 MCP 协议本身；如果攻击路径不涉及这些攻击面，就会被排除。
2. **实证依据：**至少一篇被审查文献必须已经将该向量展示为真实攻击，而不能只把它当作理论可能性；没有报告实例的纯推测向量会被排除。
3. **SOC 适用性：**该向量必须能够对本文评估的、连接基础设施且具备响应能力的智能体形成可信攻击路径；如果其实现需要分诊—富化—响应 SOC 流水线不存在的能力，就会被排除。

这三个条件的合取有意排除了完全依赖语言模型内部推理的向量，例如越狱、推理路径劫持和奖励黑客攻击。这些攻击不满足第一个条件，因为其利用路径是模型的推理过程，而不是中间件可观察的攻击面；它们需要在训练或对齐层面进行干预，而不是在中间件层处理。

### 3.3 实现

实现由两个协同环境组成：一个运行 Wazuh SIEM 的 Vagrant 虚拟机（客户操作系统为 Ubuntu 22.04 LTS），以及在主机上通过 Docker Compose 运行两个 MCP 服务器、持久化安全框架和演示界面的部署环境（见图 9）。Wazuh SIEM 运行完整的 Wazuh 堆栈，包括 Manager、Indexer 和 Dashboard。合法 Wazuh MCP 服务器通过启动时加载的凭据连接 Wazuh API 和 Indexer，并使用 Streamable HTTP 传输暴露自身端点，MCP 协议版本为 2025-06-18。恶意服务器作为一个可独立访问的容器运行。

三个 Docker 网络分段共同协调该部署，保持第 3.1 节所述的隔离属性：一个网络连接 Wazuh MCP 服务器和框架，一个网络连接恶意服务器，第三个网络只由安全框架和两个 MCP 服务器共享。因此，只有框架同时连接两个信任域，满足统一中间件拦截标准。

安全框架和三个智能体作为持久化服务运行，并通过 FastAPI 应用暴露。第 3.2 节介绍的连接阶段控制在服务启动时执行一次，而不是每次流水线执行时重复执行。该服务提供 REST API，包括运行完整流水线、通过框架调用单个工具、获取或重置审计日志，以及查看记忆存储统计信息等端点。三个持久化记忆存储区保存在专用 Docker 卷中，因此累积的告警历史和主机知识能够在容器重启后继续保留。一个 Jupyter 容器为操作者提供界面，用于运行演示 notebook 和驱动第 4 节测试套件的评估 notebook。

智能体层和安全框架使用 Python 3.11 实现；三个智能体都由专用系统提示词、角色标识符和经过过滤的工具允许列表实例化。三个智能体使用的语言模型均为 GPT-4o mini（快照版本 `gpt-4o-mini-2024-07-18`），通过 OpenAI API 访问。三个智能体以相同方式调用，温度设为 0.1，其余采样参数保持 OpenAI API 默认值（`top_p = 1.0`，不固定随机种子，不显式设置最大 token 数）；工具选择采用自动工具选择策略，每个智能体的内部工具调用循环最多迭代 8 次。结构化 JSON 输出由系统提示词要求，并由框架解析，而不是通过 API 的 response-format schema 强制执行。

研究者选择 GPT-4o mini 作为具有代表性的、广泛部署的生产模型。使用闭源模型不会影响本文报告的安全属性，因为所有框架控制都作用于工具调用和响应层，并将模型视为黑盒；这些控制不依赖模型权重、内部状态或提供商（见第 5 节）。模型只负责产生受到保护的智能体行为，确定性的安全决策则由框架完成。

MCP 客户端实现了基于 HTTP 和 Server-Sent Events 的 JSON-RPC 2.0 客户端，符合 MCP 规范定义的 Streamable HTTP 传输，并为安全框架提供统一接口，而不暴露底层服务器差异。安全框架本身实现为单个类；输入验证器在初始化时加载全部 16 个 Wazuh 工具的 JSON Schema。共享持久化记忆模块实现为按会话命名空间划分的磁盘 JSON 存储。合法 Wazuh MCP 服务器使用 Rust 实现，是第 3.1 节引用的开源代码库的扩展版本 [32]；恶意服务器和框架服务使用 Python 实现；三者都运行在加固的非 root 容器中。

在连接阶段控制措施完成工具注册验证后，一次完整的流水线执行依次经过以下阶段：

1. **会话初始化：**框架分配会话标识符，并将其传播到安全框架、审计日志和记忆存储区的上下文命名空间。
2. **分诊：**智能体接收告警标识符和经过验证的上下文存储内容，通过安全框架调用其允许列表中的工具。框架会对每次调用执行访问控制、速率限制、输入验证和输出验证；其结构化分诊报告在传递给下一阶段之前会再次验证。
3. **富化：**智能体以交接形式接收分诊报告。只有在输入验证器确认交接符合预期顺序后，才会允许交接；随后富化智能体构建主机画像，并将其写入共享知识库。
4. **响应：**智能体接收分诊报告和富化摘要，并参考告警历史日志生成结构化响应计划，其中包含建议操作、人工审批标志和升级标志。设置审批标志前会先检查流水线级审批速率限制器；如果调用规则提议工具，则只返回供分析师审查的格式化提议，不会对 Wazuh 实例作出修改。
5. **持久化审计：**最后，将该会话的完整审计日志写入磁盘，敏感字段值先替换为哈希，以便通过会话标识符开展事后取证分析。

该安全框架可移植到线性（顺序式）智能体流水线，并且基本独立于流水线的其他具体实现，因为其安全层、会话控制和审计日志只作用于工具调用和响应面，不依赖底层语言模型、智能体数量或连接的 MCP 服务器身份。唯一明确假设特定拓扑的组件是交接顺序验证器，它强制执行线性顺序。因此，将框架移植到非顺序式、去中心化或分层拓扑时，需要对该组件进行泛化。

适配新的基于 MCP 的多智能体架构主要涉及四个配置点：将每个智能体角色映射到工具允许列表的角色权限注册表；交接顺序定义——非顺序拓扑需要将其从线性映射扩展为转换图；用于结构化参数验证的工具模式注册表——缺少模式时会平滑降级为仅执行模式扫描；以及用于供应链验证的可信二进制哈希表——未配置哈希时发出警告而不是阻断。其余组件，包括注入模式集、速率限制器、审计日志以及会话身份和命名空间隔离机制，都与流水线拓扑无关，无需修改。

完整源代码，包括智能体实现、安全框架、恶意 MCP 服务器和部署配置，已在项目仓库 [34] 公开。研究者使用生成式 AI 工具（Claude、Anthropic）仅进行语言编辑、语法修正和可读性改进；作者审阅并验证了全部科学内容、分析、解释和结论，并对最终稿件负责。

### 3.4 评估方法

评估采用受控实验协议，统一应用于六个测试套件。每个测试套件隔离一个特定框架组件，以及主要通过该组件暴露面的攻击向量子集，从而避免一个套件中的检测结果被归因于其他层的控制措施。

每个套件包含固定数量的不同攻击实例，每个实例在框架启用的情况下重复执行 `N = 20` 次；同时，测试将攻击输入与来自相同流水线阶段的合法工具调用结合起来，使可用性指标能够反映接近真实执行的条件，而不是人为构造的纯良性场景。六个套件共包含 25 个唯一攻击实例，每个实例重复 20 次。由于以下 4 个实例在一次执行中会评估多个载荷或产物——T00 中的工具描述投毒（两个被投毒工具）、T01 中的访问控制检查（分诊和富化两个低权限角色分别尝试调用受限规则提议工具）、T04 中的 Web 内容投毒（标准和扩展模式集下的两个载荷）以及 T05 中的人—智能体信任操纵（三个胁迫性响应计划）——六个套件总共产生 600 个独立的阻断决策。

由于框架控制是确定性的，这些重复执行不是控制行为的独立样本，也不会增加安全结果的统计效力。重复执行有两个目的：第一，作为可复现性检查，确认每项控制在不同执行中保持稳定；第二，对于其中合法样例会穿过智能体层的套件，在底层语言模型以非零采样温度调用的非确定性行为下执行这些样例，从而在真实模型变化条件下测量误阻断指标，而不是只对一次响应测量。攻击输入有两种来源：对于表现于工具调用或服务器响应面的向量，由专门构造的恶意 MCP 服务器发送；对于表现于记忆上下文、智能体间交接或会话状态的向量，则由测试工具直接注入相关组件。

每个套件记录三项指标：

- **攻击被阻断数：**被正确检测的攻击实例数量，预期值等于尝试总数；
- **攻击通过数：**绕过所有控制并到达智能体的攻击数量，预期值为 0；
- **误阻断数：**被错误拒绝的合法调用数量，预期值为 0。

### 3.5 测试工具与攻击载荷目录

本节补充第 3.4 节的评估方法，记录评估安全框架所使用的测试工具结构，以及第 4.1 节各测试套件所报告的攻击输入和合法输入。

测试工具实现在 `run_tests.py` 中，执行标记为 T00 至 T05 的六个测试套件，每个套件对应一个框架组件或控制组。每个测试执行 `N` 次，默认 `N = 20`；脚本也支持指定其他试验次数，或单独运行某个测试套件。

测试工具使用从威胁模型派生的一组固定代表性攻击实例，验证各框架控制的确定性行为；每个载荷在多次试验中保持不变。关于这一设计以及其对自适应输入的适用范围，仍采用第 3.4 节所确立的解释。

#### 3.5.1 测试工具执行模型

每个测试套件遵循相同的高层结构：

1. 初始化相关的框架组件、客户端、验证器或流水线状态。
2. 在存在可比较的未保护操作时，先在不启用安全框架的情况下取得基线测量值。
3. 在安全框架启用的情况下执行攻击案例。
4. 记录攻击是被阻断，还是到达受保护面。
5. 通过同一个框架组件执行对应的合法案例。
6. 记录合法操作是被接受，还是被错误阻断。
7. 重复执行上述过程 `N` 次。

测试工具同时记录安全性和可用性结果。安全性通过攻击被阻断数和攻击通过数测量；可用性通过误阻断数测量，即被框架错误拒绝的合法操作数。测试工具还报告 `legit passed`，即被正确允许的合法操作数。

#### 3.5.3 合法案例

每个攻击面都配有一个合法案例，用于验证框架在处理攻击后不会拒绝正常流量。合法案例包括：无害的工具描述、新的非冲突工具名称、未改变的清单、匹配的二进制哈希、经过授权的角色—工具调用、有效的 API 密钥配置、可信来源、未超过限制的速率请求、无害工具参数、干净的记忆上下文、有效的外部威胁情报文本、正确的交接顺序、无害服务器响应、大小较大但仍被允许的响应，以及说明清晰且不带胁迫性的响应计划。

如果合法案例在没有违反相应安全策略的情况下仍被拒绝，就会计为一次误阻断。因此，误阻断指标只应解释为测试工具所包含合法案例上的指标，而不能视为任意 SOC 流量的一般误报率。

#### 3.5.4 成功标准

当一个子测试同时满足以下条件时，视为测试成功：

- 攻击实例由预期框架组件阻断；
- 攻击没有到达受保护的智能体、MCP 服务器、记忆上下文或分析师审批面；
- 对应的合法案例被接受；
- 在设定的试验次数内结果保持稳定。

这些标准体现了本次评估的目标：在受控的实验室威胁模型下，验证每个框架层能够执行其预期安全属性，同时保持合法 SOC 流水线的正常行为。


这个过程我试过很多策略，包括让 Gemini review、让 Claude 和 Codex 互相 review。最后放弃了所有"互相 review"的方案。原因很简单：只要让两个模型互相审，它们永远能告诉你"还能怎么改进"、“还可以从哪个角度优化”。这个过程没有终局。一定要有一个角色来做最终决定，而不是让它们无休止地互相照应。

而且这样的流程下，最终选出来的 idea，一定是三个模型共同认可当前上下文中综合情况更适合的 idea。

但在真正进入实现之前，还有一件必须做的事：写 research contract。

在动手写任何代码之前，先把所有预期写清楚：hypothesis 是什么，什么结果算成功，什么结果算失败，每个 ablation 预期会看到什么。失败信号要独立写，不是"没达到成功"的反面。

为什么要这么较真？因为如果你不在实验之前把这些确定，模型一定会在结果出来以后帮你合理化。跑出来的数差了一点，它会告诉你"虽然主指标没达标，但从另一个角度看这个结果其实揭示了一些有趣的现象"。做科研最忌讳的就是先看到结果再编故事。

contract 写好以后，后面所有角色都以它为唯一的尺子。写代码的要严格对照里面的超参、metric、数据 split 来实现，有偏差不能自己决定，必须回来问。评审结果的时候先读 contract 再看结果，逐条判定每个信号是达标还是没达标。写论文的时候，每一条 claim 必须能对应回 contract 里的某个信号和对应的实验数据。

而且 contract 一旦写好，实验开始以后不能改。如果确实需要修正，产出一个 v2，写清楚改了什么、为什么改。不允许事后调整 success signal 去配合结果。
